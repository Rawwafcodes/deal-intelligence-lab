# Task 17.5 — Monitoring/Triggers in React
Status: complete
Authorization: founder directive, 2026-09-27 (Phase A5 of
`17.0-product-integration-program.md`, the last item in Phase A).
Dependencies: none beyond already-implemented `triggers.py` (M15.3).

## User outcome
From a deal, a user can open a new "Monitoring" deep page, see every
configured trigger (what future event it watches, which mandate
template it would fire, its owner, its budget limit, why it exists, and
whether it's active or disabled), configure a new opt-in trigger scoped
to the exact document or workspace it should watch, disable one, and see
every past firing attempt (success or failure) with the real
Mandate/Plan it created. **This is the first React surface `triggers.py`
has ever had** - unlike 17.1-17.4, there is no orphaned link to restore,
only a genuinely new screen for an existing, fully backend-tested
module.

## Required reading
`triggers.py`'s own module docstring in full (v1's exact two supported
event types and why the other three roadmap-listed ones aren't
supported yet; "every plan a trigger proposes still needs an explicit
approve_plan/execute_run call from a human"; `APPROVAL_POLICIES = {"manual"}`
only); `EVENT_TEMPLATE_COMPATIBILITY`; `Trigger`/`TriggerFiring`
dataclasses; `server.py`'s `_handle_create_trigger`/
`_handle_disable_trigger` (role-gated to reviewer/deal_lead) and the
item route's `firings` composition (~1284-1296).

## Scope
1. `frontend/src/lib/api.ts`: add `Trigger`/`TriggerFiring` types
   (mirror the backend exactly) plus `EVENT_TEMPLATE_COMPATIBILITY`
   mirrored as a plain object (for the create form's dependent
   template-key select - the server independently re-validates the same
   compatibility regardless of what the client offers), and
   `listTriggers`, `getTrigger` (includes `firings`), `createTrigger`,
   `disableTrigger`.
2. New `frontend/src/routes/Triggers.tsx`, a deep, project-scoped route
   (`/projects/:projectId/triggers`, no workspace picker - a trigger's
   scope is exactly one document or one workspace, chosen at creation,
   not the page's own context). Lists triggers with status/event/
   template/owner/budget/reason; a "New trigger" button (visible only
   when the current identity's deal role is `reviewer` or `deal_lead` -
   client-side convenience, server re-enforces); a create dialog whose
   template-key options are dynamically filtered by the chosen event
   type (client-side mirror of `EVENT_TEMPLATE_COMPATIBILITY`) and whose
   scope field switches between a document picker
   (`document_version_changed`) and a workspace picker
   (`decision_package_prepared`); a "Disable" action on active triggers
   (same role gate); an expandable firings list per trigger (fetched via
   `getTrigger` on expand, not eagerly for every row).
3. `App.tsx`: register the route. Link it from somewhere reachable -
   `DealOverview.tsx`'s header, alongside how other deep pages are
   reached, since Monitoring is deal-wide context, not specifically a
   Findings-page concern like 17.1-17.4 were.

## Exclusions
- **No new event types or templates invented** - only the two
  `event_type`s and their exact compatible `template_key`s the real
  backend supports (`document_version_changed` ->
  {`readiness`,`reassessment`}; `decision_package_prepared` ->
  {`readiness`}).
- **No approval-policy picker beyond "manual"** - `APPROVAL_POLICIES =
  {"manual"}` is the only value the backend accepts; not offering a
  choice that doesn't exist.
- No change to `triggers.py`/`mandates.py`'s firing orchestration.
- No "fire now" / manual-trigger button - firing only ever happens as a
  real side effect of the real event (a document version changing, a
  decision package being drafted) inside `mandates.py`'s own event
  hooks; inventing a manual fire button would be new backend-adjacent
  behavior, not reuse.

## Reuse
100% existing backend. Document/workspace picker patterns reused from
earlier Phase A tasks and `DocumentUploadDialog.tsx`'s own precedent.

## Security and intelligence boundary
No AI call in this task itself. Create/disable authorization is the
existing server-side reviewer/deal_lead check; client-side role check is
UX only. Every value the create form sends is independently re-validated
by `triggers.create_trigger` (event_type/template_key compatibility,
approval_policy) regardless of what the client offers - the UI cannot
create an invalid or unauthorized trigger the server would silently
accept.
