# Task 17.14 — Close M17 with centralized role-based authorization
Status: complete
Authorization: the founder's own 2026-09-27 "M17 final closeout"
directive, given directly after Task 17.13 (Phase F) disclosed two real
gaps without fixing them - the directive's own explicit approved role
interpretation for all four `identity.DEAL_ROLES`, its own required
authorization architecture ("one centralized backend policy layer"),
frontend requirements, documentation matrix, test list, and browser
verification list all govern this task's scope directly; nothing here
was improvised beyond ordinary implementation judgment calls the
directive itself reserved to the implementer ("exact function and
capability names are your implementation decision").
Dependencies: Phases A-F (Tasks 17.1-17.13), all complete. This is the
M17 program's own final closeout, not a new product milestone - see
D16 (`docs/10-decisions.md`).

## User outcome
Every deal-scoped route on the real server now enforces one centralized,
auditable, unit-tested policy instead of plain "is this caller a member
of this deal at all" gating. An `external_executive` can no longer
reach Findings, Documents, Work, Assertions, Readiness, Reassessments,
Triggers, or internal Mandate data through any route, direct URL entry
included - they see exactly what the approved role interpretation
authorizes: the restricted Deal Overview, approved decision packages,
and requests already sent to them (with real management-response
controls, now actually reachable in the UI, not only supported at the
API layer). An analyst can no longer even be shown Approve/Return
controls for work they can never legally approve. Every one of these
guarantees is backend-enforced first; the React frontend consumes the
same policy purely to avoid showing what a role cannot use.

## Scope
**Backend** - new `authz.py` (pure, dependency-free, importable and
unit-testable with no server or database): 25 capability constants,
one `(role, capability) -> bool` matrix covering all four deal roles,
`has_capability`/`capabilities_for`, and two object-level filters
(`request_visible_to`, `deliverable_visible_to`) expressing "explicitly
shared/approved" entirely in terms of fields the existing data model
already has (`workspaces.REQUEST_STATUSES`, `deliverables.
DELIVERABLE_STATUSES`) - no new sharing subsystem, no schema change.
`server.py`: new `_require_capability`/`_require_capability_only`
helpers built on top of the existing `_authorized_project` (left
unmodified and still used directly at its own 3 call sites where no
single capability applies - session-scoped and workspace/validation-
case-scoped shared lookups whose actual capability varies by caller);
every one of `_authorized_project`'s ~75 other call sites replaced with
the correctly-scoped capability check, verified against the real
routing dispatch (not assumed from memory - see Acceptance for the two
real mis-mappings this verification pass caught and fixed before they
ever shipped). `_deal_overview`/`_deal_overview_restricted` now return
`role`/`capabilities` (from `authz.capabilities_for`) and the
restricted branch also returns `requests` (every request across every
workspace in the project that `authz.request_visible_to` allows this
role to see). `_workspace_overview` (org-wide `/api/overview`) and
`_org_wide_mandates` (`/api/mandates`) now shape/filter per-project by
the caller's own role on each project, not just membership - closing
the aggregate-leak the directive's own routes list named.
`_handle_update_request` now branches: internal roles keep the
pre-existing full edit surface; `external_executive` may only touch
`management_response`, and only on a request whose current status
`authz.request_visible_to` already allows. `_handle_approve_memo`
gained a real role gate for the first time (`APPROVE_PUBLISH`,
deal_lead-only) - it had none before this task, an inconsistency with
its sibling `_handle_approve_deliverable` that undermined "one
centralized policy" if left as is; disclosed here as a real, small
behavior tightening, not a silent one.

**Frontend** - new `frontend/src/lib/dealAccess.tsx`:
`DealAccessProvider`/`useDealAccess`/`useCapability`/`RequireCapability`
- a server-provided capability set consumed by shared guards, no
frontend-only permission logic that could drift from `authz.py`.
`DealShell.tsx` now fetches `role`/`capabilities` alongside the
deal-name breadcrumb it already fetched, filters its own tab list by
capability (an `external_executive`'s sidebar simply never shows
Documents/Findings/Mandates/Activity), and provides the value via
context to everything it renders. `App.tsx` wraps every deep-page route
(documents, findings, decision-package, readiness, reassessments,
assertions, triggers, mandates list/detail, work, activity) in
`RequireCapability` - a denied role sees a clear "Not available for
your role" card and the guarded page's own component never mounts, so
its own data fetch never fires (no sensitive content is ever requested
before the decision is made). `Work.tsx`'s `WorkProductItem` now reads
`useCapability("review_work")` and renders Approve/Return only when
true. `DealOverview.tsx`'s `RestrictedDealOverviewView` gained a real
"Information requests" section - a small, explicitly-scoped addition
beyond the two disclosed gaps, since the approved role interpretation
itself lists "management-response controls needed to answer those
requests" as something `external_executive` may have, and the backend
already fully supported it with no frontend surface at all.

## Exclusions
- `identity.py`'s own role model (`DEAL_ROLES`, session/membership
  mechanics) is unchanged - this task adds a policy layer on top of it,
  per the directive's own "do not rewrite the existing identity
  architecture."
- No schema change of any kind.
- No new sharing/publishing subsystem - "explicitly shared" is
  expressed entirely through existing status fields (`sent`/`answered`
  for requests, `approved` for deliverables), per the directive's own
  "deny access by default rather than treating membership as consent to
  disclose it... do not add a broad sharing subsystem."
- Validation Lab routes (validation-cases/runs/answer-keys) bucketed
  under the existing `VIEW_INTERNAL_DOCUMENTS` capability rather than
  given a dedicated row - not named in the directive's own routes list,
  and behaviorally identical to internal-document-tooling access for
  every real role today.
- Reviewer's decision-package approval stays "recommend"-tier
  (`APPROVE_PUBLISH: False`), unchanged since Task 14.3, despite the new
  role description's "may: approve... where current domain rules
  support it" - that qualifier itself keeps this narrow, since no
  dedicated reviewer-approval endpoint exists to widen into.

  capability pair covered including "deal_lead has everything",
  "external_executive's denied and allowed sets partition the full

- **New HTTP integration tests**: `tests/test_authorization_matrix.py`,
  19 test methods against the real running server with four independent

  covering the directive's own required scenario list 1-23 and 25 (24,
  frontend action visibility, is a React-side concern verified live via
  Playwright instead - see below). All pass.

  to its actual route via direct source re-reading, not memory)

  do_GET route pairs (task/mandate/integrity-review/reassessment/
  trigger items and their collections) were each mapped to the *next*
  route's intended capability, a cascading one-position drift from
  reconstructing line numbers across several fragmented reads. Neither
  reached the committed state - both were found and fixed by the audit
  pass itself, then reconfirmed by the full test suite.
- Full backend suite: 910 tests (870 baseline + 40 new), 0 failures.
  mypy clean (`server.py`, `authz.py`, `identity.py`). Frontend `tsc -b`

  frontend/*.test.mjs` 5/5 (one pre-existing test's own regex updated
  to match the new `RequireCapability`-wrapped route JSX, still proving

- **Live browser verification**, real running app, four independent
  Playwright browser contexts with real session cookies, synthetic

  Overview (Documents/Findings/Mandates/Activity all correctly hidden);
