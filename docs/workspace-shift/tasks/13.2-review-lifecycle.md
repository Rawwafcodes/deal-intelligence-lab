# Task 13.2 — Version-specific review lifecycle
Status: complete
Authorization: roadmap M13.2 ("Version-specific review lifecycle. Implement
review → return for revision → resubmit → approval."). The founder said
"start m13.2" directly after the Integrity Review documentation-only
adoption; scoped and implemented directly, continuing the standing
instruction carried through this whole effort ("implement the tasks
you're performing, don't draft it").

Dependencies: 13.1 (`tasks.py`'s `Task`/`Comment`, `work_products.py`'s
`WorkProduct`/`SubmissionVersion` and its own already-built "submission
advances the task to `submitted`" mechanism, reused unmodified); 11.3b
(`identity.get_user`, `_authorized_project`); the Integrity Review
documentation adoption's own explicit guidance for this task (docs/
10-decisions.md's I01-I08 and docs/08-roadmap.md's M13.2 hook list) -
"every review decision identifies the exact SubmissionVersion," "approval
is version-specific and cannot silently transfer to a new version,"
"resubmission creates a new immutable version," "reviewer, timestamp,
decision and rationale are auditable" - all implemented as literal,
tested mechanisms in this task, not aspirational language.

## User outcome
A reviewer can approve or return a submitted task's current work-product
version, with a required rationale when returning it. Returning work does
not erase anything - the analyst sees exactly why it came back, resubmits
(a new immutable version, exactly as 13.1 already built), and the task
re-enters review automatically. An approval is pinned to the exact version
it was given for: if new content shows up later, the task is honestly
"submitted" again, not still showing as "approved" against content nobody
has reviewed. Every decision - who, when, approve or return, why - is
permanently visible in the work product's own review history, including
decisions that were later superseded by a later one.

## Scope
**1. New `reviews.py`** - `ReviewDecision` (task_id, work_product_id,
`submission_version_id`, reviewer_id, `decision` ["approved"|"returned"],
rationale, optional `related_comment_id`, timestamp). Append-only: no
update or delete function exists for this table at all - a decision, once
recorded, is permanent. `record_decision` requires a non-empty rationale
specifically for "returned" (a return with no stated reason isn't useful
to anyone); an "approved" decision may carry an optional note but doesn't
require one. **`is_current_version_approved(work_product_id,
current_version_id)`** is the literal mechanism behind "approval is
version-specific and cannot silently transfer to a new version": it
looks at only the *latest* decision for a work product and checks whether
its `submission_version_id` matches the *current* one - an older,
superseded approval simply doesn't match and correctly reports `False`,
with no special-casing anywhere. Deliberately does not import `tasks.py`
or `work_products.py` (same "neither module depends on the other" shape
13.1 already established for its own two modules) - `is_current_version_
approved` takes plain string ids rather than a `WorkProduct` object
specifically so this module never needs even a typing-only import.

**2. `tasks.py` extended** - `TASK_STATUSES` gained `"returned"` and
`"approved"`, both reachable only through new `mark_returned`/
`mark_approved` functions (mirroring `mark_submitted`'s own shape and
its "never revive a cancelled task" guard exactly), never through
`update_status` directly. `mark_submitted` itself needed no logic change,
but its existing behavior - unconditionally setting status to
`"submitted"` for any non-cancelled task - now does double duty as the
"resubmission creates a new immutable version [and] re-enters review"
mechanism: a genuinely new work-product version (13.1's own
`add_version`) or a new work product submission calls it exactly as
before, and an `"approved"` or `"returned"` task correctly flips back to
`"submitted"`, proven live (see Completion evidence).

**3. `server.py`**: two new routes, both behind the existing
`_authorized_project` gate - `POST .../work-products/<id>/review`
(records a decision against the work product's *current* version at the
moment of the call, then updates the owning task's status; rejects with
400 if the task isn't currently `"submitted"`, since there's nothing to
review otherwise; validates an optional `related_comment_id` actually
belongs to the same task) and `GET .../work-products/<id>/review` (lists
decision history, symmetric with the existing versions-listing route).
`_task_with_details` (13.1's own composition helper) extended to include
each work product's `review_decisions` (with reviewer display info
composed in, mirroring `_comments_with_authors`) and a
`current_version_approved` flag - no new round trip needed by the
frontend, same pattern 13.1 already established.

**4. Frontend**: extends the existing Tasks card (`static/project.html`/
`project.js`/`style.css`) with, per work product: a review-history list
(reviewer, decision, the exact version number decided on, timestamp,
rationale) and, only while the task is `"submitted"`, an "Approve"/
"Return for revision" control pair with a shared rationale field (the
"Return" button is disabled client-side, not just server-side, when the
field is empty). The task's own status pill and dropdown gained
`"Returned for revision"`/`"Approved"` labels and colors (amber for
`"submitted"` - reused the green success color from `"submitted"` for
`"approved"` instead, orange for `"returned"`, matching workspace.css's
own severity-color vocabulary rather than inventing a new one). Fixed one
piece of now-stale copy left over from Task 13.1's own hint text ("a full
review/approval workflow is still to come") to describe what actually
exists now.

## Exclusions
**No role-based enforcement of who may review** (docs/06-security-and-
collaboration.md's own proposed table: only an assigned reviewer or deal
lead should approve) - consistent with every task since 11.3b's own
disclosed exclusion, no task in this arc enforces role-differentiated
permissions beyond project membership yet; this is a repeated, disclosed
scope boundary, not new to this task. **No linking a review decision to
an Integrity-Review-produced finding** - the Integrity Review integration
package's own M14.2 spec places "link to an existing finding as duplicate
or supporting evidence" as a *human-checkpoint action on an Integrity
Review candidate*, not a general 13.2 feature; building an unused,
unvalidated `related_finding_id` column now, with nothing yet able to
populate it, would be schema speculation ahead of the feature that would
ever write to it. Linking to an existing task *Comment* is built (see
Scope) since Comments already exist and the reference is cheaply,
meaningfully validatable today. **No task-wide "all work products
approved" consensus state** - a task with several work products keeps
each one's review history fully precise and version-specific; the task's
own status label simply reflects whichever work product was most
recently reviewed (disclosed in `reviews.py`'s own module docstring),
not a new multi-work-product consensus rule nothing has asked for yet.
**No editing or deleting a review decision** - append-only, per docs/03's
own framing; not an oversight. **No deployment, no push, no
`git commit`** (per this effort's established default - commits happen
only when explicitly asked).

## Reuse
This task adds one new, small module and two new functions on an
existing one; everything else is composition. `work_products.add_version`
(13.1) is completely unmodified - "resubmission creates a new immutable
version" was already true before this task; 13.2 only added what happens
*around* that event (the task re-entering review). `tasks.mark_submitted`
(13.1) needed zero code change to also serve as the "un-approve on new
content" mechanism - its existing unconditional-except-cancelled
semantics already did the right thing once `"approved"`/`"returned"`
existed as statuses to override. The frontend reuses the exact comment-
list/comment-form styling already built for 13.1's own comment thread,
applied to review history instead of a new visual pattern. The Integrity
Review integration's own schema-hooks review (recorded in the prior
adoption's own STATUS.md entry) is directly validated as correct by this
task's actual implementation: `SubmissionVersion` ids were already stable
enough to be the review target with no schema change, exactly as
predicted.

## Security and intelligence boundary
No AI, no model call, no provider transmission anywhere in this task -
review decisions are an entirely local, human-authored record. Every new
route sits behind the exact same `_authorized_project` project-membership
gate every other route in this app uses - no new access-control surface.
`related_comment_id`, the one new cross-reference this task adds, is
validated server-side to actually belong to the same task before being
stored - never trusted as an opaque client-supplied id. Rationale text is
rendered via `textContent`, matching 13.1's own comment-rendering
discipline - no new XSS surface from reviewer-authored text.

row, or column altered. No backfill needed: no review decisions existed

pre-existing; the two new `tasks.py` status values (`"returned"`,
`"approved"`) are additive members of an existing TEXT column, not a
schema change of their own.
