## User outcome
A reviewer selects one immutable work-product submission under review,
one or more source-evidence document versions, and optionally peer
submissions from the same engagement - every selection an exact,
explicit version id, never "whatever is current." The mandate engine
runs a real Integrity Review and proposes candidate challenges - never
auto-published. Before anything reaches the shared findings register, an
authorized reviewer must explicitly accept, reject, edit, link as a
duplicate, or leave each candidate unresolved; only an accepted
candidate becomes a real, shared finding, carrying full lineage back to
the exact mandate/run, the exact target/source/peer versions used, and
who published it.

## Scope
**1. `integrity_review.py`** (new, pure adapter, no database access) -
mirrors `cross_format_analysis.py`'s already-proven shape exactly, and
directly reuses its module-level PDF/Excel transport, citation-parsing
(`_extract_segments`, `_parse_excel_parts`), citation-verification
(`_verify_excel_citations`), and Files API upload/cleanup functions
rather than reimplementing any of them. `MANDATE`/`STRUCTURE_
INSTRUCTIONS` are a new prompt asking Claude to identify material
assertions in one target submission and check them against source
evidence and peer submissions, producing one "## Integrity Candidates"
section per the spec's own required candidate fields (title,
classification, severity, assertion, conflicting/missing evidence, why
it matters, uncertainty, recommended resolution, deterministic-vs-
judgment flag). `validate_selection` enforces this v1's own format
boundary (target and peer submissions must be PDF; source documents may
be PDF or Excel, exactly like reconciliation) plus count/size ceilings
reused from `cross_format_analysis.py`'s own constants.

**2. `integrity_reviews.py`** (new, persistence) - `IntegrityReview` (the
write-once audit record: every selected id/version, model, tokens,
tool trace, Excel cleanup/verification - mirrors `CrossFormatAnalysis`
exactly) and `IntegrityReviewCandidate` (one row per parsed candidate,
**never inserted into the shared findings register** - `decision`
starts `"pending"` and is changed only by an explicit human decision via
`record_candidate_decision`: accept/reject/duplicate/unresolved, plus an
optional `edits` dict restricted to `title`/`classification`/`severity`/
`why_it_matters`). This module's own docstring states the security
property explicitly: a candidate becomes a shared finding through
exactly one path (`workspaces.publish_integrity_candidate_as_finding`),
called only from an explicit accept decision.

**3. `workspaces.py`** (generalized, not replaced) - `cross_format_

## Exclusions
**The selection UI defaults every target/source/peer pick to that
item's *current* version, with no in-UI override to an older one** -
the version actually used is always shown (e.g. "Valuation memo (v1)"),
and the backend itself pins exactly whatever version id it's given
(current or not, proven by `test_propose_plan_pins_the_exact_version_
selected_not_current`), but a human who specifically wants to review
against an *older* version of a multi-version submission or document
must currently do so via a direct API call, not this UI - a disclosed
v1 UI simplification, not a backend limitation. **Editing a candidate's
fields before accepting is not yet exposed in the UI** - the backend
fully supports `edits` (title/classification/severity/why_it_matters)
on an accept decision (proven by `test_edit_overrides_only_the_edited_
fields_on_publication`), but `IntegrityReviewPanel` only offers accept/
reject/leave-unresolved/mark-duplicate as-is; adding inline edit fields
is a small, disclosed follow-up. **No real paid call has been made** - every test
and the propose-time-only live check in Completion evidence below uses
either a mocked provider or makes no provider call at all; this task's
own "Live proof" and "Completion gate" requirements (a real run, a real
human review, at least one independently scored Validation Lab case)
remain outstanding and need explicit separate authorization before any
paid call happens. **Target and peer submissions must be PDF** - no
Excel-format or plain-text submission-under-review support in this v1
(disclosed in `integrity_review.py`'s own module docstring). **No LLM-
proposed integrity-review plans** - `_TEMPLATES_EXCLUDED_FROM_LLM_
PLANNING` keeps this template human-proposed only; extending 12.4's
planner to safely handle exact multi-role version selection is a
separate, unauthorized future task. **`duplicate_of_finding_id` is not
independently re-verified against every workspace in the project** - it
is checked to be a non-empty string, not that the referenced finding
actually exists somewhere in this project; a disclosed, low-severity gap
(visible to reviewers, not a security bypass) rather than building a
cross-workspace finding-existence search for this one edge case.
**Memo generation, workspace export, and the Deal Overview's own
reconciliation summary were not extended to integrity-review-backed
workspaces** - `_get_workspace_analysis` (the reconciliation-only memo/
export/full-summary path) now explicitly 400s for an integrity-review
workspace rather than crashing, but was not generalized further; an
integrity review's own findings are read through the new dedicated
`GET .../integrity-reviews/<id>` route instead. **No assertion-snapshot
ledger** - per the integration package's own I05 ("Persist only material
assertions used in real reviews... promote after validation"), this
task persists the candidate's own assertion text as part of its snapshot
but does not build a separate, reusable claims/assertion table.

## Security and intelligence boundary
Every identifier is re-verified twice, independently, against real
current project state - once at propose time (`_default_input_for_
stage`), once again at execution time (`_integrity_review_executor`) -
never trusted from the plan's own stored copy; `documents.get_document`/
`work_products.get_work_product` are themselves project-scoped, so a
forged or cross-project id resolves to nothing at either point (proven
by `test_propose_plan_rejects_forged_target`, `..._rejects_forged_
source_version`, `..._rejects_peer_from_another_project`,
`..._rejects_deleted_document_lookalike_cross_project`). The planner
cannot expand this capability's own access: it never sees this template
at all (`_TEMPLATES_EXCLUDED_FROM_LLM_PLANNING`), and even a
hypothetical model-proposed plan naming it would fail this capability's
own `input_schema` (empty stage input has no `target`/`documents`) and
be reported as `"unsupported"`, never executed. A candidate's own
`lineage`, once published, is built entirely from the plan's own pinned,
already-re-verified selection (`review.target_work_product_id`, `review.
source_document_ids`, ...) - never from the model's own candidate text -
so a candidate's prose cannot smuggle an unauthorized source into a
published finding's lineage even in principle. Human checkpoint before
shared publication is structural, not a status flag: a candidate simply
does not exist in `workspace_findings` until `publish_integrity_
candidate_as_finding` runs, which only ever runs from an explicit accept
decision (server.py's own handler, gated to analyst/reviewer/deal_lead).
Candidate-decision role enforcement resolves the caller's role server-
side (`identity.get_deal_role`), never from client input, matching every
other role check this session has built since Task 13.4.

## Data migration and recovery
Additive and metadata-only. `workspaces` table: `cross_format_analysis_id`
loses its `NOT NULL` constraint (a metadata-only Postgres operation - no
row rewrite, no data loss, every existing row's real value untouched)

additive, nullable columns (`mandate_id`/`run_id`/`attempt_id` - the
lineage fix found live, see Completion evidence) via the same idempotent
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern. No foreign-key
coupling to any existing table's own constraints. One targeted,
disclosed `UPDATE` backfilled the single real `integrity_reviews` row
this session itself created with its own already-known correct
lineage values - not a blanket migration, and touching no row this
session did not create. Rollback: drop the two new tables, the new
`integrity_review_id` column and its index, and (if ever desired)
restore the `NOT NULL` constraint on `cross_format_analysis_id` - safe
only once no integrity-review workspace exists, since every existing
reconciliation-backed workspace already satisfies it. No real
Universal Logic data was touched by this task in any way - no
