## User outcome
A deal lead opens a deal and sees one real-data summary - brief, task
counts and what needs attention, mandate counts and recent activity,
reconciliation/finding severity counts, workstream and document counts,
and a chronological feed of what actually happened (comments,
submissions, review decisions) - with links out to the existing surfaces
that own each kind of detail. From the workspace landing page, anyone
sees which of their own assigned tasks need a review or a revision,
across every deal they have access to, before ever opening a specific
project.

## Scope
**1. New `overview.py`** - deliberately pure functions only: no database
access, no import of any other domain module. `count_by_status` (real
counts keyed by whatever status strings the underlying records actually
use - never a renamed or synthesized category), `tasks_needing_attention`
(a real filter: status in `{"submitted", "returned"}`, most recently
updated first), `findings_summary` (real severity counts plus a real,
separately-tracked "open" count per severity, via the existing
`resolution_status` field - never collapsed into one score), and
`build_activity_feed` (sorts and caps a list of already-real, already-
timestamped events - never invents one). Kept pure specifically so the
counting logic - the part most worth getting exactly right, since a wrong
count here is a literal "fake metric" - is unit-testable with plain
Python objects, no Postgres, no HTTP server.

**2. `server.py`**: two new routes, composed the same way `_task_with_
details`/`_workstream_with_assignments` already compose other modules -
`GET /api/projects/<id>/overview` (the Deal Overview: brief, workstreams
with assignments, task counts + needs-attention list, mandate counts +
5 most recent, reconciliation count + aggregated findings summary across
every one of the project's real workspaces, document count, and a merged
activity feed built from real task comments, work-product submissions,
and review decisions) and `GET /api/overview` (the Workspace Overview: a
real, per-project engagement list with its own task/mandate counts, and
a "my attention" list - tasks assigned to the caller, specifically,
whose status means a specific action is expected next - scoped by the
exact same `identity.list_accessible_project_ids` boundary every other
cross-project read in this app already respects).

**3. Frontend (React scaffold, per D13)**: new `DealOverview.tsx` at
`/projects/:projectId` - finally giving `Home.tsx`'s own pre-existing,
previously-broken project-card link somewhere real to go. Reads and
summarizes; it does not duplicate editing UI that already exists
elsewhere - links out to the existing static project page (documents,
tasks, brief, workstreams - D13's own established home for that editing
surface) and the existing React Mandates list/detail routes for anything
that needs a closer look. `Home.tsx` gained a "My attention" card above
the project list, populated from the Workspace Overview endpoint,
linking each task straight to its own Deal Overview.

## Exclusions
**Not the fuller docs/05 vision, by explicit roadmap allowance** ("simple
overview shells... never fake metrics"): no "quick actions" panel (new
mandate/new deal/upload/assigned-reviews shortcuts), no restricted
external-executive view, no live-refresh polling (both overview pages
load once and require a manual reload - the same "start simple" posture
`docs/05-experience.md`'s own "Live behavior" section describes as an
acceptable starting point: "Begin with bounded polling and revision
checks"), no cross-deal merged activity feed (the Workspace Overview
shows per-engagement counts and "my attention," not every deal's own
activity feed merged into one). **No new domain data or table** - this
task is purely a read-side composition of Tasks 13.1/13.2's,
Milestone 7/9's, and M12's already-persisted records; nothing new is
ever written by either new route. **No task-wide review-status
consensus** for the Deal Overview's mandate/task counts beyond what
`reviews.py` (13.2) already exposed - unchanged from that task's own
disclosed scope boundary. **No AI-generated summary of any kind** -
every word and number on both new pages is a direct, real value from an
existing record; docs/05's own "An AI draft summary cannot impersonate
the lead's approved conclusion" is honored by there being no AI-authored
summary at all yet, not by disclaiming one. **No deployment, no push, no
`git commit`** (per this effort's established default).

## Security and intelligence boundary
No AI, no model call, no provider transmission anywhere in this task -
both overview endpoints are read-only aggregations of already-persisted
local data. `GET /api/projects/<id>/overview` sits behind the exact same
`_authorized_project` gate every other project-scoped route in this app
uses - no new access-control surface. `GET /api/overview` (workspace-
level, not project-scoped) uses `identity.list_accessible_project_ids`
to decide which projects' data the caller ever sees - the identical
boundary `GET /api/projects` already enforces, applied here for the
first time to a cross-project *aggregate* rather than a plain list, and
verified, not just assumed: a task assigned to a real seeded identity
(Jordan Lee, Reviewer) that has *no* real deal membership on the project
correctly produces zero rows in that identity's own "my attention" (see
Completion evidence) - the feature cannot leak a task's existence to
someone without real access to the project it belongs to, even when they
are literally the named assignee.
