## User outcome
A deal lead can create a task, optionally place it in a workstream and
assign it to someone, and the assignee (or anyone with access to the
deal) can comment on it and submit a work-product file. Every submitted
version is immutable and independently downloadable forever, exactly
like a source document's own version history. Submitting a work product
automatically marks the task "submitted" - a signal that something now
exists to be looked at, without yet building the review/return/approve
workflow that acts on that signal (Task 13.2's explicit job).

## Scope
**1. New `tasks.py`** - `Task` (title, description, optional
`workstream_id`, optional `assigned_to`, `created_by`, `status`,
timestamps) and `Comment` (task_id, author_id, body, timestamp).
`TASK_STATUSES = {"open", "in_progress", "submitted", "cancelled"}`, but
`update_status` (the human-facing action) only ever accepts `{"open",
"in_progress", "cancelled"}` - `"submitted"` is reachable only through
`mark_submitted`, a function called exclusively from the work-product
submission path, never exposed as a directly settable value. This is a
deliberate, disclosed scope boundary: the review/return/approve state
machine docs/03's ReviewDecision/Approval implies is explicitly Task
13.2's job, so a "submitted" task in this task's own scope has nothing
yet acting on it beyond existing to be reviewed later.

**2. New `work_products.py`** - `WorkProduct`/`SubmissionVersion`,
deliberately mirroring `documents.py`'s Document/DocumentVersion split
mechanically (stable parent, every version's bytes under their own
generated id, current-version fields denormalized onto the parent) but
kept as its own module/table per docs/03's explicit separate naming - a
WorkProduct's future lifecycle (review, return, approval) is different
from a source Document's, even though today's storage mechanics are
identical. Reuses `documents.ALLOWED_EXTENSIONS`/`sanitize_original_
filename` directly rather than re-declaring them. Repeats Task 11.4's own
fix verbatim: a second submission against the same task is always a
second, independent WorkProduct; adding a version is always an explicit
action against an already-known `work_product_id`, never inferred from a
filename match.

**3. `server.py`**: 8 new routes, all behind the existing `_authorized_
project` gate (no new authorization surface) - `GET`/`POST .../tasks`,
`GET .../tasks/<id>`, `POST .../tasks/<id>/status`, `POST .../tasks/<id>/
assign`, `POST .../tasks/<id>/comments`, `POST .../tasks/<id>/
work-products` (multipart, creates the WorkProduct + version 1, then
composes `tasks.mark_submitted` at the API boundary - `work_products.py`
never imports `tasks.py`, the same "neither module depends on the other"
shape `_assignments_with_users` already established for workstreams +
identity), `GET`/`POST .../work-products/<id>/versions`, `GET .../
work-products/<id>/versions/<id>/download` (reuses the existing, already-
generic `_send_stored_file` unchanged). New `_task_with_details`/
`_comments_with_authors` compose tasks.py + work_products.py + identity.py
+ workstreams.py inline, mirroring `_workstream_with_assignments` exactly,
so the frontend never needs a round trip per row.

**4. Frontend**: extends the existing static `project.html`/`project.js`/
`style.css` (D13's own precedent, reused again after 11.4b: new
collaboration surfaces on an existing project page, not a new React
screen) with a "Tasks" card - task list with expand/collapse (a real
`<button>` with `aria-expanded`, 11.1's own accessibility convention,
never a clickable non-interactive element), a new-task form (title,
description, workstream/assignee selects reusing the existing `/api/dev/
identities` endpoint), and per-task detail (status/assignee controls,
comments thread, work-product list with upload/add-version/version-
history). `openVersionsDialog` (previously documents-only) was
generalized to accept `{name, listUrl, downloadUrlFor, currentVersionId}`
so work-product version history reuses the exact same dialog markup and
function instead of a second, near-identical one - found necessary during
implementation, not planned going in.

**Bug found and fixed during implementation, not planned going in**: the
first working version's task list showed an assignee but never the
task's own workstream, even though the create-task form let a human pick
one - `_task_with_details` only composed `assigned_user`, not a
`workstream` object. Fixed by adding the same composition for
`workstream_id` (mirroring `assigned_user`'s own shape exactly) and
displaying it in the task's meta line; a corresponding endpoint test
assertion was added. **Second bug found and fixed live** (see Completion
evidence): `loadTasks()` re-fetches and fully re-renders the task list
after every action (a comment, a status change, a submission) - the
first working version reset every row to collapsed on each re-render,
which would make a comment thread unusable in practice (expand, comment,
watch it collapse, re-expand for the next message). Fixed with a
module-level `expandedTaskIds` `Set` that `renderTask` consults for its
initial `hidden`/`aria-expanded` state and the toggle keeps in sync -
proven fixed by commenting on an expanded task live in the browser and
confirming it stayed open.

## Exclusions
**No review/return/resubmit/approval workflow** - Task 13.2's explicit
job (docs/08-roadmap.md's own division: 13.1 is "assigned tasks/comments
and immutable work-product submissions", 13.2 is "review -> return for
revision -> resubmit -> approval; version-specific decisions"). A
"submitted" task today has nothing acting on it beyond existing.
**`docs/03-domain-model.md`'s ReviewDecision/Approval records are not
built** - deliberately deferred with the workflow they'd support. **No
change to `workspaces.py`'s own, pre-existing Request/Response** (the
per-finding information-request system from Milestone 9) - confirmed
during Baseline to be a genuinely distinct concept, not touched or
reused by this task. **No task deletion, no comment editing/deletion** -
not required by this task's own scope, and comments docs/03's own
"Append-only" framing for ReviewDecision/Approval suggests immutability
is the right default here too, not an oversight. **No cross-project task
references, no task-level access control beyond the existing project
membership gate** - a Task inherits exactly the same visibility as
everything else on the project page. **No deployment, no push, no
`git commit`** (per the founder's own established default - commits
happen only when explicitly asked, per the `921d14a` entry).

## Reuse
`work_products.py`'s storage mechanics (stable parent, immutable
per-version files under their own generated id, denormalized "current"
fields) are `documents.py`'s Task 11.4 pattern, reapplied, not
reinvented - including its own hard-won "never infer versioning from a
filename collision" fix. `_task_with_details`/`_comments_with_authors`
reuse `_workstream_with_assignments`/`_assignments_with_users`'s exact
API-boundary composition shape. The frontend's expand/collapse toggle
reuses Task 11.1's own accessible-button pattern (a real `<button>` with
`aria-expanded`, not a clickable `<tr>`/`<div>`). `openVersionsDialog`
is now shared by two entirely different record types (documents,
work products) through one generalized function and one dialog element,
not two near-duplicates. The multipart upload handlers reuse the exact
`multipart.parse_boundary`/`parse_multipart`/`_read_multipart_body`
sequence `_handle_document_upload`/`_handle_add_document_version`
already established.

## Security and intelligence boundary
No AI, no model call, no provider transmission anywhere in this task -
tasks, comments, and work-product submissions are entirely local
collaboration primitives. Every new route sits behind the exact same
`_authorized_project` project-membership gate 11.3b already built - no
new access-control surface, and in particular no task-level or
work-product-level permission beyond "has access to this project"
(matching this task's own explicit non-scope: a fuller Analyst/Reviewer/
Deal-lead permission table for task actions specifically is not built
here, consistent with `docs/06-security-and-collaboration.md`'s "proposed
first permissions" table remaining just that - proposed - beyond what
prior tasks already enforce). Uploaded work-product files go through the
identical `ALLOWED_EXTENSIONS` allow-list `documents.py` already enforces
- no new file-type surface. Comment bodies and task titles/descriptions
are rendered via `textContent`, never `innerHTML`, so no new XSS surface
from user-authored text.

`work_products`, `submission_versions` - four total) - no existing table,
row, or column touched. No backfill needed: a project with no tasks
before this task genuinely has none, nothing to reconstruct (the same
reasoning 11.4b used for its own new, backfill-free tables). Rollback is
a plain `DROP TABLE` on all four with no data-loss risk to anything
pre-existing.
