## User outcome
Given a mandate's objective (and a deal brief, if one exists), a human can
click "Propose with AI" and have a real model - instead of a human
hand-picking a template and, for reconciliation, a source document pair -
propose which registered capability fits and which of the project's real
documents form the right pair. The proposal is never trusted at face
value: every document id and template key is independently re-verified
against the real database before anything is created, and a proposal the
model itself isn't confident about (or that fails an independent check)
comes back as an honest "unsupported" outcome with a reason, not a
best-guess plan. The existing human approval gate (`approve_plan`) is
completely unchanged - a model-proposed plan sits exactly as
"proposed, not approved" as a human-proposed one, and a human can also ask
the planner to revise a proposal, which always creates a new, separately
approved plan revision rather than mutating the one already on record.

## Scope
**1. New `mandate_planning.py`** - the one module in this task's call
graph that talks to Anthropic, deliberately a pure function of its inputs
(no database access at all): given a mandate's objective, the project's
real document inventory (id/filename/extension only, never file bytes or
content), the currently registered templates, an optional deal brief, and
optional human feedback on a prior proposal, `propose_candidate_plan`
returns a structured, still-untrusted `PlanProposalOutcome`
(`status`: `"proposed"` / `"unsupported"` / `"error"`). Uses Anthropic's
structured JSON output (`output_config.format`, a JSON-schema-typed reply)
rather than prose-JSON parsing, since a planning call sends no document
content and therefore has none of the citations incompatibility every
other AI-calling module in this app works around. Mirrors `ai_client.py`'s
own provider-error taxonomy (`missing_api_key`, `invalid_api_key`,
`rate_limit`, `insufficient_credit`, `model_unavailable`, `network_error`,
plus a new `invalid_reply` for a schema-conformant-but-nonsensical or
truncated reply) so a real call's failure modes are handled the same way
every other AI-calling module in this codebase already handles them.

**2. `mandates.py` gained `propose_plan_llm`** - the untrusted-output
verification layer, run independently of, and before, anything the model
said is trusted:
   - Every document id the model names is looked up with
     `documents.get_document(project_id, ...)`, the same project-scoped
     lookup every other part of this app uses - a hallucinated id, or a
     real id belonging to a *different* project, resolves to `None` and
     rejects the *whole* candidate (never silently dropped and the rest
     kept).
   - The resolved documents are run through `cross_format_analysis.
     validate_selection` (the same structural PDF/Excel-mix check the real
     capability's own executor already uses) *before* any `PlanRevision`
     is created, not deferred to execution time.
   - The (now independently verified) template key and `stage_inputs` are
     handed to the *exact same* `propose_plan` a human's manual proposal
     already goes through - `validate_plan_stages` runs again there,
     unchanged, on this input like any other. There is one validation
     path, not two.
   - A candidate that fails any of the above, or that the model itself
     marked `"unsupported"`, or that names an unregistered template,
     comes back as `LlmPlanProposalResult(status="unsupported")` with a
     specific reason - **no `PlanRevision` row is created** for it.
   - `feedback` (optional): free text from a human who reviewed a prior
     proposal and wants a different one. Passed straight to the model as
     context; otherwise identical to a first call, including going
     through `propose_plan` again, which creates a **new** `PlanRevision`
     (a new `revision_number`) and marks whatever was previously
     `"proposed"` `"superseded"` - the prior row's own content is never
     mutated (docs/03's revision-counter pattern, unchanged).
   - This function only ever reaches `"proposed"` (never `"active"`) - it
     never calls `approve_plan`, never touches a run, and never resolves a
     `human_checkpoint` attempt. The model cannot mark its own human
     checkpoints approved because nothing in this function's call graph
     can reach that gate at all.

**3. `PlanRevision` gained two additive fields** - `proposed_by`
(`"human"` default / `"llm"`) and `planner_reasoning` (nullable) -
recorded purely for the human approver's own transparency (docs/04: plans
are "reviewed outputs", not a black box). Neither field affects
validation, execution, or the approval gate: `approve_plan` doesn't look
at them. `propose_plan` gained two new, defaulted parameters
(`proposed_by="human"`, `planner_reasoning=None`) to carry them - every
existing call site and test is unaffected by the defaults.

**4. `server.py`**: one new route, `POST .../mandates/<id>/plan/propose-ai`
(`_handle_propose_plan_llm`), behind the existing `_authorized_project`
gate - no new authorization surface. Status codes mirror
`_handle_reconciliation`'s own success/provider-error split: **201** for
a created plan, **200** for an honest `"unsupported"` outcome (a
considered planning judgment, not an error - no plan exists to return),
**502** for a genuine provider-side failure. Accepts an optional
`feedback` string in the request body.

**5. Frontend**: `frontend/src/lib/api.ts` gained `proposePlanWithAi` and
the `PlanProposalOutcome`/updated `MandatePlan` types.
`frontend/src/routes/MandateDetail.tsx`: a new "Propose a plan with AI"
card (shown alongside, not replacing, the existing manual "Propose
manually" card - both remain available) with a single "Propose with AI"
button; an inline banner on an `"unsupported"` outcome showing the
planner's reason and its own stated rationale, plus a feedback field and
"Try again" button; the "Proposed plan" card now shows a "Proposed by
AI" / "Proposed manually" badge, the planner's reasoning when present, and
- only for an LLM-proposed plan - a "Request a change from the planner"
feedback field that creates a new revision via the same `propose-ai` route.

## Security and intelligence boundary
The planner sees only metadata it is explicitly given: the mandate's own
objective, the project's document *inventory* (id, filename, extension -
never bytes or extracted content), the currently registered templates'
key/name/description, and (if one exists) the deal brief's free-text
fields - never a document's actual content, and never another project's
data (document lookups are project-scoped throughout). Its output is
untrusted at every layer described in Scope item 2 above; a
schema-conformant reply can still name a hallucinated document id or an
invented template key, and both are independently rejected, not trusted
because the JSON shape was valid. The model can only ever produce a
`"proposed"` (unapproved) plan or an honest `"unsupported"` outcome - it
cannot approve a plan, start a run, or resolve a human checkpoint; those
remain human-only actions through the completely unmodified
`approve_plan`/`reject_plan`/`execute_run`/`resume_run` functions. Document
access for the planning call itself is governed by the existing
`_authorized_project` project-membership gate on the new route - no new
access-control surface. This is the second task in the M12 arc to cross
the "real paid call" boundary (after 12.3), and does so with the same
explicit, prior, disclosed authorization discipline - see Authorization
above and "Live verification" below for the one discrepancy found and
disclosed rather than silently corrected.
