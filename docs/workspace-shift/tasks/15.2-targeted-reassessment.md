## User outcome
A reviewer picks a workspace Task 15.1 has already flagged potentially
stale because a source document changed. The mandate engine compares the
old and new document versions directly against the workspace's own
current findings and proposes, per finding, whether it remains valid,
changes materially, or needs a human's own judgment call - explaining
concretely what changed and why. A human works through every proposed
item; once every one is acknowledged, the workspace's staleness flag
clears automatically. No finding is ever created, mutated, or deleted by
this process - the reassessment is a new, separate, immutable record
that exists alongside the original findings, never a rewrite of them.

## Scope
**1. `reassessment.py`** (new, pure adapter, no database access) -
mirrors `integrity_review.py`'s PDF-transport and citation-extraction
machinery directly (the same duck-typed PDF-item shim, the same
`cross_format_analysis._extract_segments` reuse), but compares exactly
two versions of *one* document rather than a multi-document selection.
`build_digest`/`validate_digest` assemble a deterministic, app-authored
digest of the workspace's own current findings (never model-authored).
The mandate prompt asks Claude to address every finding in the digest
explicitly, classifying each `still_valid` | `materially_changed` |
`needs_human_reconsideration` with a concrete explanation and citation-
backed evidence of what changed (or "No relevant change located" if
nothing did - never silently omitted). v1 scope, disclosed: only a
staleness flag whose direct cause is a `document` (not a cascaded
staleness, not a superseded submission version) is supported - the
`documents.Document.extension` gate keeps this PDF-only, the same
restriction Integrity Review's own target/peer submissions carry, for
the same reason (an Excel-format reassessment needs the Files API/
code-execution apparatus applied a third time - separate future task).

**2. `reassessments.py`** (new, persistence) - `Reassessment` (the
write-once audit record: exact document/old-version/new-version ids,
mandate/run/attempt lineage, model, tokens, the two free-text sections)
and `ReassessmentItem` (one row per addressed finding, `decision`
starting `"pending"`, changed only by an explicit human `acknowledge_
item` call - this module's own docstring states the security property
plainly: acknowledging never creates or mutates a finding, only records
that a human looked at the proposal). `all_items_acknowledged` is the
one predicate `server.py` checks to decide whether to clear staleness.

**3. `version_dependencies.py`** - new `clear_staleness(dependent_type,
dependent_id)`, Task 15.1's own explicitly deferred "no un-staling"
boundary, resolved here and only here. Deliberately does not cascade: a
deliverable that had inherited staleness from this workspace stays
flagged - clearing it would silently declare something reassessed that
nobody actually looked at.

**4. `mandates.py`** - new `reassessment.compare_versions` capability
(`allowed_source_formats=(".pdf",)`) and a new `reassessment` template
(capability stage + `human_checkpoint`, the same shape 12.5/14.2/14.3
already proved). `_default_input_for_stage`'s new branch enforces the
precondition independently (never trusted from the plan's own stored
copy): the named workspace must currently be flagged stale, and the
direct cause must be a `document` - re-verified again at execution time
in `_reassessment_executor`, since staleness could in principle be
cleared by a separate reassessment between plan approval and run
execution. The executor looks up the exact old version via `version_
dependencies.get_pinned_version` (new query helper) and matches the
model's own reported finding titles against the workspace's real
findings (case-insensitive exact match), persisting a resolved
`finding_id` (or `None`, disclosed, never silently dropped) per item.

**5. `server.py`** - `GET /api/projects/<id>/reassessments[/<id>]` and
`POST .../reassessments/<id>/items/<id>/decision` (gated to analyst/
reviewer/deal_lead, the same docs/06 "Recommend finding disposition"
row Integrity Review's own candidate-decision endpoint uses). The
decision handler calls `reassessments.all_items_acknowledged` after
every acknowledgment and, once true, calls `version_dependencies.
clear_staleness("workspace", ...)` - the one and only path staleness is
ever cleared. `reassessments.init_reassessments_db()` added to `main()`.

**6. Tests** - `tests/test_reassessment.py` (16 tests: heading/item
parsing, `validate_digest`, persistence round-trip and item

rejection of a non-stale workspace and of an unknown/cross-project

## Exclusions
**Only document-caused staleness, v1** - a cascaded staleness (e.g. a
deliverable stale because its workspace is) or a submission-version-
caused staleness (the `review_decision` relationship 15.1 also tracks)
has no reassessment path in this task; both are disclosed, bounded future
extensions, not silent gaps (the precondition check reports exactly why
an unsupported cause is rejected, rather than crashing or guessing).
**No inline editing of an item before acknowledging** - matches Task
14.2's own precedent; acknowledging is accept-as-is, not accept-with-
edits. **Acknowledging never updates the target finding's own workflow
fields automatically** - a human who agrees a finding materially changed
records that separately, through the finding's own pre-existing update
endpoint; this task deliberately does not compose the two, since
auto-updating a finding's `resolution_status` from an AI-authored
reassessment without a distinct, explicit action would blur the line
this app's whole "AI proposes, human decides" design keeps sharp
elsewhere. **No cascade un-staling** - see `clear_staleness`'s own
docstring above. **Not offered to the LLM planner** - the same
"workspace selection" gap `decision-package`/`readiness` already have.

## Security and intelligence boundary
Every identifier (`workspace_id`, and internally the document/version
ids a staleness flag names) is independently re-verified against real,
current, project-scoped state at both propose time and execution time -
the same discipline every capability since Task 12.3 has followed. The
model's prompt explicitly instructs it to judge only the change it
actually finds, never invent one, and to treat document content as
untrusted data rather than instructions. Nothing a reassessment item
proposes is ever auto-applied: `create_items` always inserts
`decision="pending"`; only an explicit, separately role-gated `POST
.../decision` call - resolved server-side via `identity.get_deal_role`,
never from client input - can change that, and even then it changes
only the item's own row, never a finding.
