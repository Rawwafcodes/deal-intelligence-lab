# Task 17.8 — Org-wide Mandates destination + final nav-clarity pass
Status: complete
Authorization: founder directive, 2026-09-27 (Phase B3 of
`17.0-product-integration-program.md`, the last item in Phase B).
Dependencies: 17.6/17.7 (same reuse patterns); closes Phase B.

## User outcome
A real "Mandates" destination lists every mandate across every
accessible deal, each tagged with its own deal, filterable by status.
Separately, every deal-scoped page (Documents/Findings/Mandates/
Activity/Work, not only Deal Overview) now shows which deal you're in -
closing a real gap docs/product/02's B4 spec named explicitly
("Documents, Findings and Activity must make the selected deal
obvious") that was not true before this task.

## Required reading
docs/product/02's B3/B4 spec ("reuse existing per-deal mandate data.
Add only the smallest backend aggregation route if the frontend cannot
retrieve the data safely and efficiently through existing APIs";
"clearly distinguish organization-level context; deal-level context;
mandate-level context... Navigation must not unexpectedly drop users
into a different context"); the existing per-project
`_MANDATES_COLLECTION_RE` handler (the exact logic this task reuses,
not replaces); `DealShell.tsx`'s own prior state (no deal-name display
at all, confirmed by direct inspection before this task).

## Baseline
HEAD at `584638b` (Task 17.7). Full suite green (863 tests). Confirmed
by direct inspection: no organization-wide mandate route existed
(`/api/projects/<id>/mandates` only); `DealShell.tsx` rendered its tab
strip with no deal-identifying text anywhere above it, so every one of
`Documents.tsx`/`Findings.tsx`/`Activity.tsx`/`Work.tsx`/
`MandateList.tsx`'s own `<h1>` just said the section name, never which
deal.

## Scope
**Backend** (`server.py`, one new route, no new table): `GET
/api/mandates` (`_ORG_MANDATES_RE`) -> `_org_wide_mandates()`, which
iterates `identity.list_accessible_project_ids` exactly like
`_workspace_overview` already does and calls the same
`mandates.list_mandates(project_id)` the per-project route already
calls, tagging each result with its own project - the "smallest
aggregation" the spec's own wording anticipates, chosen over a client-
side fan-out because the per-project route returns no project context
to tag results with and a fan-out doesn't scale cleanly as deal count
grows.

**Frontend**:
1. `frontend/src/lib/api.ts`: `OrgWideMandate` type (`Mandate` +
   `project`), `listAllMandates`.
2. New `frontend/src/routes/MandatesHome.tsx` at `/mandates` - lists
   every mandate with its deal name, status badge, and a status filter;
   links to the existing deal-scoped Mandate Detail page (no duplicate
   detail view).
3. `App.tsx`/`AppSidebar.tsx`: register `/mandates`, add a real
   top-level "Mandates" sidebar link (alongside the already-added
   "Overview"/"Deals" from 17.6/17.7 - this task's own nav-clarity
   contribution completes that set).
4. **Nav-clarity fix**: `DealShell.tsx` now fetches the deal's own name
   once (via the already-existing `getDealOverview`, no new backend
   call) and renders a small "Deals / <deal name>" breadcrumb above the
   tab strip - since every deal-scoped route renders inside this one
   shell, this single change fixes the missing-deal-context gap for
   all five deal-scoped pages at once, rather than editing each
   separately.
5. `server.py`'s SPA-fallback rule (already touched once in 17.7 for
   `/deals`) extended to also cover `/mandates` - caught proactively
   this time via the exact same class of bug 17.7 found the hard way,
   with `tests/test_server.py`'s existing coverage list extended
   to include it before this task's own live check, not after.

## Exclusions
- No change to `mandates.py`'s domain logic, capability registry, or
  runtime - purely a new read-side composition and a new page.
- No mandate-level breadcrumb (e.g. "Deals / X / Mandates / Y") -
  deal-level context was the real, disclosed gap; mandate-level context
  is already unambiguous (`MandateDetail.tsx`'s own header shows the
  objective).
- `MandateList.tsx` (deal-scoped) is unchanged - it remains the
  creation/detail-linking surface; `MandatesHome.tsx` is read-only by
  design (creating a mandate needs a deal context, already covered by
  the deal-scoped page and Overview's own Quick Action).

## Reuse
`mandates.list_mandates`, `identity.list_accessible_project_ids`,
`getDealOverview` (already fetched by `DealOverview.tsx`, now also by
`DealShell.tsx`), `MANDATE_STATUS_LABELS` (17.6's shared extraction).

## Security and intelligence boundary
No AI. `_org_wide_mandates` adds no new authorization surface - it
iterates the exact same accessible-project list `_workspace_overview`
already uses.
