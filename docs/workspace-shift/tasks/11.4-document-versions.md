Dependencies: none beyond the existing `documents.py`/`server.py`.

## User outcome
A document that gets replaced with an updated file keeps its identity (the
same document row, the same place in every list/citation) while every
prior version's exact original bytes remain independently stored,
downloadable, and never overwritten. Uploading a document that happens to
share a name with an existing one still creates an unrelated new document,
exactly as before this task — replacing a specific document's content is
now a distinct, explicit action ("Replace…" on that document's own row),
never inferred from a filename match.

**Confirmed by direct inspection before writing code**: `documents.py`'s
`Document` was a single flat record — one row per upload, no version
concept, `find_duplicate` only ever compared byte-identical content across
the whole project (not filename/location). Stored bytes lived at
`originals/{document.id}{extension}`, so any versioning scheme had to
either move existing files or resolve through an indirection layer — the
latter was chosen (see Scope) specifically so **zero bytes on disk needed
to move**, real data included.

## Scope
1. **New `document_versions` table** (`id`, `document_id`, `version_number`,
   `size_bytes`, `sha256`, `uploaded_at`) plus two additive columns on the
   existing `documents` table (`current_version_id`, `version_number
   DEFAULT 1`) — the table itself is otherwise completely untouched.
2. **`documents.Document`** gains `version_number`/`current_version_id`.
   `size_bytes`/`sha256`/`uploaded_at` keep meaning exactly what they
   always meant to every existing caller (pdf_inspection, xlsx_inspection,
   workspace_exports, citations, the download handler) — "the current
   version's own values" — so none of those modules needed to change.
   `stored_file_path()` now resolves via `current_version_id` (falling
   back to the document's own id, which is what version 1 always equals),
   so it still resolves to the exact same path as before for any document
   that has only ever had one version.
3. **`documents.add_version(project_id, document_id, data)`** — the one
   and only way a new version gets created. Rejects byte-identical content
   (409, nothing to replace) with the same "duplicate" vocabulary
   `save_uploaded_file` already uses. Writes the new bytes under a fresh
   version id (old file untouched), inserts the new `document_versions`
   row, and updates the parent's `current_version_id`/denormalized fields.
   **Deliberately not wired into the ordinary bulk-upload path** — see
   Reuse and the note in `save_uploaded_file`'s own docstring for why an
   automatic "same filename = new version" heuristic was tried first,
   found to break ~89 existing tests that reuse generic filenames across
   independent fixtures, and replaced with this explicit action instead.
4. **`documents.list_versions`/`get_version`** (the latter scoped to its
   own `document_id`, so a version id can't be used to reach a different
   document's file by guessing) and **`version_file_path`**.
5. **New routes**: `GET .../documents/<id>/versions` (list),
   `POST .../documents/<id>/versions` (add a version — single-file
   multipart, one `file` field), `GET .../documents/<id>/versions/<vid>/
   download`. All three go through the existing `_authorized_project`
   gate from Task 11.3b — no separate access model needed for versions,
   they inherit the parent document's project-level authorization.
6. **Additive, idempotent real-data backfill**
   (`documents._backfill_legacy_versions`, run from `init_documents_db()`
   exactly like `identity.py`'s own backfill pattern from 11.3b): every
   pre-existing document (real data included) gets a synthesized version 1
   row **whose id equals the document's own id** — meaning
   `current_version_id` resolves to the file that was already on disk with
   zero file moves.
7. **Frontend** (`static/project.html`/`project.js`/`style.css` — the
   existing static page, not the React scaffold, since document
   management already lives there per D13): a small `v{n}` badge next to
   a document's name (only shown once it has more than one version), a
   "Replace…" action per row (a label-wrapped hidden file input, styled
   like the existing "Choose files" control), and a "Versions" action
   (shown once `version_number > 1`) opening a `<dialog>` — the same modal
   pattern already used for Inspect/Cross-analysis on this page — listing
   every version newest-first with size, timestamp, a "(current)" marker,
   and its own independent download link.

## Exclusions
The roadmap's other three M11.4 items are **not** part of this task and
remain fully open, not started: **versioned brief** (Deal/BriefVersion —
parties, objective, perspective, scope, periods, uncertainties; no such
concept exists in the app yet), **workstream assignments**
(Workstream/Assignment — configurable grouping and named responsibility;
likewise nonexistent), and **revision conflicts** (an optimistic
concurrency/revision-counter mechanism on mutable records like workspace
findings — today every update is still last-write-wins). "Narrow document
access" (DealDocumentLink-style *per-document* grants, narrower than a
project-wide deal membership) is also not built — this task's versions
inherit the same project-level gate every other document route already
uses from 11.3b, nothing finer-grained. No mandate/workstream/brief UI. No
deployment, no push, no `git commit`, no paid AI calls.

## Reuse
Reuses `server.py`'s existing `_authorized_project` gate, `multipart.py`'s
existing parser, and the existing `_send_stored_file`/`_content_disposition`
download machinery (lightly generalized from `_send_file_download` so both
the current-version download and the new per-version download share one
implementation). Reuses the static page's existing `<dialog class="modal">`
pattern for the new version-history dialog rather than inventing a new UI
primitive. `find_duplicate` (byte-identical dedup) is reused completely
unchanged as the first check in both `save_uploaded_file` and
`add_version`.

## Security and intelligence boundary
No AI/model code touched. Version routes inherit 11.3b's project-level
authorization unchanged — no new access-control surface, no new identity
concept. `get_version` is scoped to its own `document_id`, so a version id
alone (even if guessed or leaked) can't be used to reach a different
document's bytes through the download route — the route requires both ids
to agree, same "existence hidden behind the parent's own gate" property
the rest of the document routes already have.

## Data migration and recovery
Applied automatically on server restart (`init_documents_db()`'s call to
`_backfill_legacy_versions()`), the same "just restart with the new code"
shape 11.3b's identity backfill used, for the same reason: this backfill
only ever inserts new `document_versions` rows (one per pre-existing
document, its id chosen to exactly match the already-existing file on
disk) and sets a previously-`NULL` column — it never moves, renames, or
rewrites a single stored file, and never touches any column on `documents`
other than the two new ones. Verified directly afterward: all 63 real
Universal Logic documents show `current_version_id` set, `version_number
= 1`, and `documents.stored_file_path(doc)` resolves to a real, existing,
unmoved file for a sampled document. Rollback: dropping the
`document_versions` table and the two added columns restores exactly
today's pre-11.4 schema and behavior; no existing table, row, or stored
file is ever altered by this task.
