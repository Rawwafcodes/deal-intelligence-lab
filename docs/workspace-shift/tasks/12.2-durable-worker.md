## User outcome
Starting a mandate's run now returns immediately with a real, persisted,
merely-*queued* record — not a finished one. A genuinely independent
background worker (started from `server.py:main()`, not from any request)
executes it afterward, so closing the browser or losing the request mid-run
has no bearing on whether the run finishes. Killing and restarting the
server process itself no longer silently loses or corrupts run state: a
run interrupted cleanly between stages resumes and finishes on its own;
one interrupted with a capability call genuinely in flight is reported as
`outcome_unknown` (mandate moves to `under_review`) rather than guessed
at. Cancelling a run now actually stops its *next* stage from starting,
whether it is sitting queued or already being executed — not only one
already parked at a human checkpoint, which was all 12.1 could do. Every
run also carries a real, enforced budget ledger (`budget_limit`/
`budget_consumed`), checked before every capability call, even though
`fixture.echo`'s own cost is nominal.

## Scope
**1. `execute_run`/`resume_run` now only persist and hand off** —
`execute_run` inserts a `Run` row with `status="queued"` and returns it
immediately; no capability has executed by the time it returns.
`resume_run` records the human's decision on the paused `Attempt`
durably, then sets the run back to `status="queued"` with
`current_stage_index` advanced past the checkpoint, and returns — it does
not continue the run inline. In both cases, closing the request
connection immediately afterward has no bearing on whether the run
finishes (proven live — see Completion evidence).

**2. `mandates.Worker`** — a background thread, started from
`server.py:main()` (poll interval configurable via
`DEAL_LAB_MANDATE_WORKER_POLL_SECONDS`, default 0.5s), independent of any
HTTP request:
- `poll_once()` — one scan-and-process pass: finalizes any
  `cancel_requested` run that was never dispatched (or was left mid-cancel
  by a crash), then dispatches every `queued` run through the same
  `_run_stages` walk 12.1 built, just called from here instead of inline
  in the request. Exposed as its own method specifically so tests can
  force one deterministic step without sleeping or racing the background
  thread.
- `recover()` — called once, before the poll loop starts. Any `Run` still
  `running` at this point was left there by a *prior* process's worker
  (this one hasn't started its loop yet), so that state is definitionally
  stale. Two branches, per docs/04's own wording ("recovers or reports
  outcome_unknown"): (a) the last attempt is itself still `running` — a
  capability call was genuinely in flight when the process died, so the
  run is marked `outcome_unknown` and the mandate moves to `under_review`,
  never guessed at or silently retried; (b) every attempt is already
  terminal (or none exist yet) — safe to requeue, and the ordinary poll
  loop finishes it from `current_stage_index`.
- `start()`/`stop()` — thread lifecycle; `stop()` joins with a timeout.
  Wired into `server.py:main()`'s existing `try/finally` around
  `httpd.serve_forever()`.

**3. Cooperative cancellation, checked before every stage** —
`_run_stages` re-fetches the `Run`'s own row at the top of every loop
iteration (never trusts an in-memory copy) specifically so a concurrent
`cancel_run` call is noticed before the *next* stage starts. `cancel_run`
now accepts `queued` and `running` (in addition to `waiting_for_input`):
for those two it sets `status="cancel_requested"` — a real request, not
an immediate fact — and the actual stop happens either from
`_run_stages`' own check (if a stage is genuinely in progress) or from
`Worker.poll_once()`'s `cancel_requested` scan (if the run was still
sitting `queued`, never dispatched). A `waiting_for_input` run has nothing
in flight to stop, so it is still cancelled immediately, as in 12.1.

**4. Minimal, enforced budget ledger** — `CapabilityDescriptor` gained
`unit_cost: float = 0.0` (`fixture.echo` declares `1.0` — nominal, no
real-money meaning, disclosed as such). `Run` gained `budget_limit`
(optional, set via `execute_run(..., budget_limit=...)` /
`POST .../runs {"budget_limit": ...}`) and `budget_consumed`.
`_run_stages` checks `budget_consumed + unit_cost > budget_limit` *before*
calling a capability's executor — never after — and fails the run with a
clear "budget exceeded" error if so, recording an attempt that shows the
capability was never actually invoked.

**5. Attempts recorded before the call, not just after** — a capability
attempt is now inserted as `status="running"` *before* `descriptor.executor`
is called, then finalized to `succeeded`/`failed` once it returns
(`ATTEMPT_STATUSES` gained `"running"`). This is what makes `recover()`'s
two branches distinguishable at all: "the last attempt is still `running`"
is only meaningful because attempts are recorded before, not after, the
call they represent (docs/04, verbatim: "Record attempts before provider
calls").

**6. `server.py`** — `_handle_start_run` now returns **202**, not 201 (the
run is accepted for processing, not completed), and accepts an optional
`budget_limit` in the request body. `main()` constructs and starts a
`mandates.Worker`, stopping it in the existing shutdown `finally` block.
No new routes; no new authorization surface — every route still runs
through the same `_authorized_project` gate 11.3b established.

**7. Frontend (`MandateDetail.tsx`, `api.ts`)** — polls (`750ms`) while
any run is `queued`/`running`/`cancel_requested`, rather than assuming
`startRun`/`resumeRun` already reflect the finished run. Shows per-run
progress (`current_stage_index`/stage count) and budget usage when a
limit is set. "Cancel run" is now offered for *any* non-terminal run, not
only one parked at a checkpoint. An optional budget-limit input was added
next to "Start run".

app runs exactly one local server process at a time (docs/07-architecture.md),
so there is deliberately no `SELECT ... FOR UPDATE SKIP LOCKED`-style
cross-process contention handling; `Worker`'s own docstring discloses the
one narrow race this leaves (a `cancel_run` landing in the exact instant
between `poll_once()` reading a run as `queued` and `_execute()` writing
it to `running` can be silently overwritten — a repeat cancel immediately
after always succeeds, since the run is then genuinely `running` and
checked before its next stage). **No fine-grained mid-stage interruption**
— cancellation stops the *next* stage, never one already in progress
(there is nothing to preempt a synchronous Python function call with, and
docs/04 itself only asks for "stops future stages"). **No cost estimation
model beyond a flat `unit_cost` per capability** — real dollar-cost
estimation (tokens, cache categories, provider-specific pricing) is
12.4/AI-integration territory, not meaningful for a capability with no
real cost. **No deployment, no push, no `git commit`, no paid AI calls.**
