## User outcome
An authorized reviewer or deal lead configures a standing, named trigger:
which real event to watch, which mandate template to fire in response,
an owner, an optional budget, and a reason. When that real event actually
happens - a document gets a new version, a decision package is drafted -
every matching active trigger automatically creates a real, visible
Mandate with a real proposed Plan, exactly as if a human had proposed it
manually. Nothing runs unapproved: a human must still explicitly approve
the plan and start the run, the same as any other mandate. Every firing
attempt, whether it succeeded or failed its own precondition, is durably
recorded and visible - there is no silent monitoring and no possibility
of an event being watched without a trace of what happened when it fired.

## Scope
**1. `triggers.py`** (new, persistence + matching logic, a freestanding
leaf module - imports only `store`, deliberately never `mandates.py`, so
`mandates.py` can import it without a circular import). `Trigger`
(name, event_type, template_key, optional scope_document_id/scope_
workspace_id, owner, budget_limit, reason, approval_policy - `"manual"`
is the only value this v1 supports - status). `create_trigger` validates
`EVENT_TEMPLATE_COMPATIBILITY`: `document_version_changed` pairs with
`readiness` or `reassessment`; `decision_package_prepared` pairs with
`readiness` only (no version comparison to make). `match_active_
triggers` filters by project/event/status and, for a scoped trigger, the
exact document or workspace named. `TriggerFiring` records every attempt
(`"proposed"` or `"error"`), never silently dropped.

**2. `version_dependencies.py`** - new `list_dependents_of(source_type,
source_id, dependent_type=None)`, a plain reverse lookup ("every real
dependent currently recorded against this source") - used to find every
workspace a changed document affects, independent of `mark_superseded`'s
own staleness bookkeeping (a workspace is relevant to this trigger
whether or not it happens to be freshly stale from *this exact* change).

**3. `mandates.py`** - new `fire_triggers_for_event(project_id,
event_type, workspace_id, event_detail, document_id=None)`: matches
active triggers, and for each one calls the exact same `create_mandate`/
`propose_plan` a human's manual proposal already goes through (never a
separate, laxer path) - so a trigger-created plan is exactly as
unapproved as one a human typed in by hand. A failure proposing one
trigger's plan (e.g. `reassessment` fired but the workspace isn't
actually stale) is caught and recorded as an `"error"` `TriggerFiring`,
never raised - firing a trigger can never break the real request (a
document upload, a decision-package creation) that caused the event.
Called from `_decision_package_executor` directly (same module, no
import needed) for `decision_package_prepared`.

**4. `server.py`** - `_handle_add_document_version` now looks up every
workspace depending on the just-changed document and calls `fire_
triggers_for_event("document_version_changed", ...)` for each -
`documents.py` itself stays completely unaware of mandates/triggers,
exactly as it stays unaware of every other higher-level concern; this
composition happens at the API boundary, the same shape this app already
uses everywhere else. New `POST /api/projects/<id>/triggers` (create,
gated to reviewer/deal_lead), `GET .../triggers[/<id>]` (list/detail with
its firings), `POST .../triggers/<id>/disable`. `triggers.init_
triggers_db()` added to `main()`.

**5. Tests** - `tests/test_triggers.py` (19 tests: `create_trigger`
validation including the event/template compatibility matrix, `match_
active_triggers` scoping, firing persistence, and `mandates.fire_
triggers_for_event` itself - a real mandate/plan created and correctly

## Exclusions
**Only two of the roadmap's five example event types** - `submission_
submitted`, `returned_work_resubmitted`, and `cross_workstream_review_
requested` are not supported: none of the first two has a single,
unambiguous `workspace_id` a template could consume without new
inference logic (a work-product submission isn't inherently tied to one
analytical workspace), and the third has no existing action in this app
to hook at all - building a genuine "request cross-workstream review"
feature first is a separate, larger, unauthorized task, not an
oversight. **`approval_policy` is always `"manual"`** - the field exists
and is recorded (matching the spec's own required field list) but this
v1 implements no automatic-approval path; a future task extending it to
a real auto-approve mode is a distinct, larger trust decision. **Budget_
limit is recorded but not automatically threaded into the eventual run**
- a human approving a trigger-created plan still specifies the budget
explicitly at `execute_run` time, the same as any other mandate; wiring
the trigger's own recorded budget through automatically is a small,
disclosed follow-on. **No trigger editing** - a trigger can be created or
disabled, never updated in place; reconfiguring means disabling the old
one and creating a new one, matching this app's own "editing creates a
successor, not a mutation" convention elsewhere.

## Reuse
`fire_triggers_for_event` calls the exact same `create_mandate`/
`propose_plan` every other proposal path already uses - no new mandate-
creation code, no new validation path. `readiness`/`reassessment`'s own
`{"workspace_id": ...}` input shape (already the entire input contract
for both templates) is exactly what let a single, generic firing
function serve both event types without per-template special-casing
beyond the one `_TRIGGER_TEMPLATE_STAGE_ID` lookup naming each
template's own stage id.

## Security and intelligence boundary
Configuring a trigger is gated to reviewer/deal_lead (docs/06's own
"Create mandate... Yes within workspace policy" role pair, applied to a
more consequential, standing action than one manual mandate). A
trigger's own effect is bounded by construction: it can only ever
propose a plan using one of its own two pre-validated, already-existing
templates against a workspace the real event actually names - it cannot
invent a capability, select arbitrary documents, or approve its own
plan. `identity.get_deal_role` resolves the caller's role server-side,
never from client input, matching every other role check in this app.
