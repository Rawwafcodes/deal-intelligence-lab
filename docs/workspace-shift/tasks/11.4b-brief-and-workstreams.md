## User outcome
A deal now has an actual brief — parties, objective, perspective, scope,
periods, uncertainties — editable from the project page, with every past
version kept and viewable, never overwritten. The same page lets someone
carve the deal into named workstreams (e.g. "Financial diligence",
"Legal") and say who's responsible for each, in plain free-text roles —
purely organizational, with no effect on who can actually open a document.

## Scope
**1. `deal_briefs.py` (new module)** — `BriefVersion` (six free-text
fields + `version_number`/`created_at`/`created_by`), one `brief_versions`
table. Simpler than Task 11.4's `DocumentVersion`: no file storage, so
"current" is just the newest row by `version_number` — no
`current_version_id` pointer needed. `create_version` never requires
every field: an omitted field carries forward from the current version
unchanged (so updating just "scope" partway through diligence doesn't
blank out "objective"), and the very first version starts every omitted
field blank. `get_version`/`get_current_version` both scoped to their own
`project_id`.

**2. `workstreams.py` (new module)** — `Workstream` (name, description,
per project) and `WorkstreamAssignment` (workstream, user, free-text
`role_label`, `revoked_at`). `assign()`/`revoke_assignment()` mirror
`identity.py`'s `DealMembership` shape exactly (Task 11.3b): revoking
never deletes the row, re-assigning after a revocation inserts a new
active row rather than reviving the old one. Deliberately has **no**
access-control concept of its own — confirmed by a dedicated test
(`test_assignment_does_not_grant_or_restrict_document_access`) that
assigning someone to a workstream never changes their
`identity.has_deal_access` result.

**3. `server.py`** — routes for both: `GET`/`POST /brief`,
`GET /brief/versions`, `GET /brief/versions/<id>`;
`GET`/`POST /workstreams`, `GET`/`DELETE /workstreams/<id>`,
`POST /workstreams/<id>/assignments`, `DELETE /workstreams/<id>/
assignments/<user_id>`. All behind the existing `_authorized_project`
gate — no new authorization surface. Workstream responses compose in each
assignment's resolved `identity.get_user(...)` display info inline, so
the frontend never needs a second round trip per row.

**4. Frontend (`static/project.html`/`project.js`/`style.css`)** — two
new cards on the existing project detail page (not a new screen — D13
keeps new *screens* on the React scaffold, but this is an addition to an
existing static page, same as Task 11.4's document-versioning UI):
- **Deal brief**: a form with the six fields, a "Save version" button
  that always creates a new version (never edits in place), a version
  label, and (once more than one version exists) a "Version history"
  dialog reusing the same `<dialog class="modal">`/`.version-list`
  pattern Task 11.4 already established for document versions.
- **Workstreams**: a list of workstream cards, each showing its roster
  (assignee name + role label + "Unassign") and an inline
  assign-someone form (a `<select>` populated from the existing
  `/api/dev/identities` endpoint, a role-label text input, "Assign") —
  reusing the identity list the React nav's dev-switcher already
  fetches, not a new identity source.

## Exclusions
No mandate/composer integration yet (`docs/04-mandate-engine.md`'s
"Context and originals" describes the brief as something a *future*
mandate composer reads — that composer doesn't exist until M12). No
per-workstream document scoping or narrower-than-deal-level access of any
kind — WorkstreamAssignment stays purely organizational, by the domain
model's own explicit instruction. No structured validation of brief
content (parties/objective/etc. are free text; nothing here checks them
against documents or enforces required fields) — the domain model calls
the brief context, not evidence, so this task never tries to verify it.
No workstream-scoped document lists, task boards, or activity feeds. No
deployment, no push, no `git commit`, no paid AI calls.

the brief (simplified, since there's no file storage to indirect

unchanged — no new access-control code anywhere in this task. Reuses the
existing `/api/dev/identities` endpoint and the document-versioning UI's
dialog/version-list CSS rather than inventing new patterns for either.

## Security and intelligence boundary
