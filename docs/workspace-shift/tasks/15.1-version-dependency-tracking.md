## User outcome
The moment a document or a submission gets a new version, every real,
already-tracked dependent - the workspace an analysis or integrity
review produced, a decision package built from that workspace, or a
work-product's own approval decision - is automatically flagged
`potentially_stale`, with a plain-English reason naming exactly which
source and which superseded version caused it. Nothing is mutated:
findings, review decisions, and deliverables keep their exact original
content forever: the flag lives entirely in a separate side table. No AI
call happens anywhere in this process - it is a deterministic, structural
consequence of uploading a new version, not something a user has to
request or wait for.

## Scope
**1. `version_dependencies.py`** (new, freestanding - imports only
`store`, so any layer can record or query a dependency without a
circular import). Two tables: `dependency_edges` (one row per real
dependency - `dependent_type`/`dependent_id` -> `source_type`/
`source_id`, plus an optional `pinned_version_id`) and `staleness_flags`
(one row per currently-flagged dependent, upserted in place - never
duplicated, and never loses its original `first_marked_at` on a repeat
supersession). Two kinds of edge: **leaf** edges (`pinned_version_id`
set) compare a real version id on `mark_superseded`; **cascade** edges
(`pinned_version_id` is `None`) propagate unconditionally whenever their
source is itself marked stale - the mechanism that lets one generic
`mark_superseded` walk the spec's entire relationship chain breadth-
first instead of a hand-written propagation function per relationship.
Self-healing: `record_dependency` immediately flags a brand-new
dependent if its source is *already* stale at the moment the edge is
recorded (e.g. drafting a fresh decision package from an already-stale
workspace) - the invariant holds at every point in time, not only at the
instant a version first changes.

**2. `cross_format_analyses.py`** (additive fix, not new scope) - new
`pdf_document_version_ids`/`excel_document_version_ids` fields
(idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, defaulting to an
empty list for every pre-existing row), populated by both reconciliation
entry points (the mandate capability and the older static-page route)
from the exact version each selected document was at when analyzed -
closing the baseline gap above.

**3. `mandates.py`** - `_reconciliation_executor` and `_integrity_review_
executor` now each record leaf dependency edges for the workspace they
materialize (and, for reconciliation, for the mandate `Run` itself -
directly satisfying "MandateRun -> every version it consumed" as its own
explicit relationship, independent of whichever workspace the run
happened to produce). `_decision_package_executor` records one cascade
edge from the new `DeliverableVersion` to its source workspace.

**4. `documents.py` / `work_products.py`** - `add_version` now calls
`version_dependencies.mark_superseded` immediately after committing the
new version row - the one real trigger point for the whole mechanism,
guaranteed to fire regardless of which caller (HTTP route, script,
future capability) creates the new version.

**5. `reviews.py`** - `record_decision` now records one leaf edge
(`review_decision` -> the target `work_product`, pinned to the exact
`submission_version_id` the decision targeted) - the spec's own
"SubmissionVersion -> approval decision" relationship, independent of
the document-version chain above.

**6. `workspaces.py`** - new `list_workspaces(project_id)`, a small,
real helper needed to surface staleness project-wide without the caller
already knowing each workspace's id via its own analysis/review record
first.

**7. `server.py`** - `GET .../workspaces/<id>` now includes a
`staleness` field (`version_dependencies.get_staleness("workspace",
...)`); `GET .../workspaces/<id>/deliverables/<id>` (detail only, not
the list, to avoid an N+1 lookup per list item) likewise; the Deal
Overview (`_deal_overview`) gained a `stale_items` array - the roadmap's
own completion-gate step 6 ("A lead sees the change... in Deal

## Exclusions
**15.2 (targeted reassessment) and 15.3 (trigger policy) are not this
task** - a `potentially_stale` flag here is purely informational; nothing
in this task ever "reassesses" whether a stale conclusion still holds,
and there is no mandate template, capability, or trigger of any kind
registered by this task. **No "un-staling"** - once flagged, a dependent
stays flagged until 15.2's own reassessment logic (not yet built)
addresses it; there is no manual dismiss/clear action in this task.
**Workspace-level granularity for reconciliation/integrity-review
findings, not per-finding** - every finding in one workspace shares the
same source/version set in practice, so dependency edges are recorded
once per workspace rather than once per finding; a disclosed, honest
simplification, not a per-finding capability this task lacks.
**Deliverable and review-decision staleness surfaced via existing read
routes only** - no dedicated "list everything stale in this project"
endpoint beyond the Deal Overview's own `stale_items` (which today only
covers workspaces, not review decisions) - a reasonable v1 scope
boundary, not a gap in the underlying tracking (`review_decision`
staleness is fully recorded and queryable via `version_dependencies.
get_staleness`, just not yet wired into a dedicated UI-facing route).

## Security and intelligence boundary
This task makes no external call of any kind, transmits nothing, and
reads only identifiers this app already generated and already trusts
(document/work-product/workspace/deliverable/review-decision ids) -
there is no new document-access surface, no new citation or evidence
concept, and no AI-authored content anywhere in this mechanism. A
staleness reason string is built entirely from ids and version ids this
app itself minted; it never echoes user- or model-supplied free text, so
there is no injection surface introduced by exposing it in an API
response.

**Limitations**: everything under Exclusions above. Workspace-level (not
per-finding) dependency granularity means a finding whose *own* specific
source is unaffected but shares a workspace with one that changed will
still show the whole workspace as stale - a coarser signal than a
finding-level system would give, disclosed rather than silently
oversold. `stale_items` in Deal Overview covers workspaces only, not
review decisions, in this v1.
