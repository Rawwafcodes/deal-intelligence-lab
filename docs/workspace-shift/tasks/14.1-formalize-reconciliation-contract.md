## User outcome
A future capability author (starting with M14.2's own
`integrity.review_work_product`, not built in this task) has one real,
enforced contract shape to follow - `input_schema`/`output_schema`/
`allowed_source_formats` on `CapabilityDescriptor` - instead of having to
infer one from scattered, capability-name-keyed `if` checks. A model-
proposed or human-proposed plan whose stage input does not match its own
capability's declared contract is rejected before a run is ever created,
with a clear, contract-referencing error message. A capability whose
real output drifts from its own declared contract fails loudly at
execution time rather than silently propagating a malformed shape.
Anyone who wants to know exactly what the existing reconciliation
capability promises and does not promise - evidence semantics, supported
formats, outputs, limitations - has one document to read
(`docs/12-reconciliation-capability-contract.md`) instead of piecing it
together from three source files.

## Scope
**1. `mandates.py`** - `CapabilityDescriptor` gained three new fields:
`input_schema: dict`, `output_schema: dict`, `allowed_source_formats:
tuple[str, ...] | None` (defaulting to empty/`None` so existing
callers - none outside this module construct one directly - are
unaffected). A new minimal, hand-rolled schema validator
(`_validate_against_schema`/`_validate_field` - object/required/
properties/type/items/minItems only, deliberately not a general JSON
Schema engine or an added `jsonschema` dependency) is the one place both
schemas are actually enforced: at propose time (inside
`_default_input_for_stage`, replacing the prior ad hoc `if capability ==
"reconciliation.cross_format":` presence check with a call to the
capability's own declared `input_schema`) and at execution time (inside
`_run_stages`, immediately after every `descriptor.executor(...)` call
succeeds, against the capability's own declared `output_schema` - a
schema violation is treated exactly like any other executor exception:
the attempt and run both fail with a clear error). Both registered
capabilities (`fixture.echo`, `reconciliation.cross_format`) now declare
real schemas; `reconciliation.cross_format` additionally declares
`allowed_source_formats=(".pdf", ".xlsx", ".xls")`.

**2. New `docs/workspace-shift/docs/12-reconciliation-capability-
contract.md`** - the actual "pin its contract, evidence semantics,
supported formats, outputs and limitations" formal spec the roadmap
calls for: capability identity, the exact input/output schema (matching
the code verbatim), evidence semantics (native PDF citations, the
Excel citation convention and multi-workbook label resolution, the
"cite both sides of a conflict" prompt requirement), supported formats
(PDF/XLSX/XLS only, at least one of each), outputs (the
`CrossFormatAnalysis` record, workspace/findings materialization, the
finding classification/severity taxonomy), error/retry behavior, source
handling (the two independent re-verification points - propose time and
execution time), usage accounting, and a dedicated Limitations section
(document/byte ceilings, no OCR/scanned-PDF distinction, model judgment
rather than deterministic reconciliation, no staleness awareness yet -
that is M15's own scope, best-effort Files API cleanup, all-or-nothing
selection validation, English/transaction-shaped prompt).

**3. `docs/10-decisions.md`** - new D14, recording the schema-on-
`CapabilityDescriptor` pattern as binding on every future capability,
explicitly naming M14.2's own `integrity.review_work_product` as the
next capability that must follow it.

**4. Tests** - `tests/test_mandates.py` gained a new `CapabilityContractTests`
class (10 tests, no database) proving both capabilities declare
conforming schemas and that the validator itself correctly accepts/
rejects representative inputs and outputs; two new tests in
`ReconciliationCapabilityTests` proving an empty or non-string
`document_ids` is rejected via the schema path specifically (not merely
the old presence check); one new test in `MandateLifecycleTests`
(`test_output_that_violates_its_own_declared_schema_fails_the_run`)
proving output-schema enforcement against a deliberately non-conforming
throwaway test capability, mirroring the existing `test_a_failing_
capability_fails_the_run_and_mandate`'s own registration pattern.

## Exclusions
**No new capability.** M14.2 (`integrity.review_work_product`) is not
implemented, not started, and remains explicitly gated on this task plus
a separate future authorization - nothing here is a step toward its
executor logic. **No behavior change to reconciliation itself** - the
same document-count/byte limits, error taxonomy, prompt text, citation
conventions, and finding taxonomy that existed before this task are
exactly what the new contract document describes; `MANDATE_VERSION` and
the capability's own `version` field are both still `"1"`. **No general
JSON Schema engine or new dependency** - `_validate_against_schema` is a
deliberately minimal, bounded validator covering only what this app's
own two capabilities actually need (object/required/properties/type/
items/minItems), not `anyOf`/`oneOf`/pattern/format/nested-`$ref`
support or any other JSON Schema feature this app has no present use
for. **No schema versioning/migration mechanism** - a capability's
`version` field is unchanged by this task; deciding how a stored plan
proposed against schema version N behaves once a capability's schema
moves to N+1 is left for whenever that first actually happens. **No
deployment, no push, no `git commit`** (per this effort's established
default).

## Reuse
The validator enforces exactly the same rule the old `_default_input_
for_stage` branch already enforced ("a non-empty document_ids list of
strings") - reformulated as a declared, reusable schema rather than
duplicated logic, not a new rule. `_reconciliation_executor` itself is
completely unchanged; only the *checking* of its own return value is
new. The contract document draws every factual claim (limits, error
codes, prompt structure, citation format) directly from `cross_format_
analysis.py`'s own existing code and docstrings - no new limit, prompt
wording, or behavior was invented for the document.

## Security and intelligence boundary
No AI, no model call, no provider transmission anywhere in this task's
own code changes - every new/changed line is local validation logic and
documentation. The one live-verification propose-time call (see
Completion evidence) creates a `PlanRevision` only; it was never
approved and no run was ever started, so no paid Anthropic call occurred
at any point in this task. Output-schema enforcement is itself a
security-relevant hardening, not merely a data-quality one: a future
capability whose executor is compromised, buggy, or simply edited
carelessly to return a different shape now fails immediately and
visibly (attempt/run marked failed) rather than having its malformed
output silently persisted and composed into whatever the frontend or a
later stage reads next.

## Data migration and recovery
None. `CapabilityDescriptor`'s three new fields default to an empty
dict/`None`, so no existing persisted data (Mandates, PlanRevisions,
Runs, Attempts) needed any migration - the fields live only on the
in-memory capability registry, rebuilt fresh from code on every server
start, never persisted to a table. Rollback is reverting `mandates.py`'s
own three edits (the new dataclass fields, the two validator functions,
the two call sites) and deleting the new contract document; nothing else
in the application depends on any of them.
