# Task 11.5 — Revision conflicts on workspace findings
Status: complete (scoped slice — see Exclusions)
Authorization: roadmap M11.4's fourth item, "revision conflicts" — not
started by Task 11.4 (which scoped to source versions only). The founder
said "do so" in response to this session's own closing recommendation on
11.4 ("recommend revision conflicts next"), under the same standing
instruction from earlier in this session to implement directly rather
than draft and wait.
Dependencies: none new — extends the existing `workspaces.py` finding
workflow (Milestone 9) and 11.3b's authorization layer (reused unchanged).

## User outcome
Two people editing the same finding at once can no longer silently
clobber each other. Whoever saves first wins outright; the second save
gets an explicit, honest conflict response instead of quietly overwriting
the first person's work — and the app tells them so in plain language and
points at reloading, rather than failing silently or corrupting state.

## Required reading
`docs/03-domain-model.md` ("Mutable records carry a revision counter.
Updates supply expected revision; conflicts return a recoverable conflict
response, never silent last-write-wins"), `docs/05-experience.md`'s Live
behavior section ("Concurrent writes produce an explicit conflict and
allow reload/reapply"), `docs/09-acceptance.md` T06 ("simultaneous edits
cause an explicit revision conflict"). Also read `workspaces.py`'s
existing `update_finding_workflow` and `server.py`'s `_handle_update_
finding` directly — the exact function and route this task extends.

## Baseline
HEAD at `fd59122`, unchanged by this task. Before implementation:
`./venv/bin/python -m unittest discover -s tests` → `Ran 380 tests ... OK`
(11.4's own baseline); `./venv/bin/python -m mypy $(ls *.py) tests` →
`Success: no issues found in 48 source files`.

**Confirmed by direct inspection**: `workspace_findings` had no revision/
version counter of any kind. `update_finding_workflow` did a plain
merge-UPDATE with no read-then-write guard — two concurrent callers could
each read the same row, each compute their own `changed` dict, and the
second UPDATE would silently overwrite whatever the first one just wrote,
with no error, no log entry distinguishing the collision from an ordinary
sequential edit, and no way for either caller to know it happened.

## Scope
1. **Additive `revision INTEGER NOT NULL DEFAULT 1` column** on
   `workspace_findings` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, same
   idiom as every prior additive migration in this codebase). Every
   pre-existing finding (real data included) gets `revision = 1` via the
   column default — no backfill script needed, unlike 11.3b/11.4's
   backfills, because a single unconditional default value is correct
   for every existing row (there's no historical revision count to
   reconstruct; "1" is simply true).
2. **`workspaces.FindingRevisionConflictError`** — new exception carrying
   `current` (the finding's real, already-merged current state) so a
   caller can show the user what actually won, not just "conflict."
3. **`update_finding_workflow(..., expected_revision: int | None = None)`**
   — when supplied, must match the finding's current `revision` or this
   raises the conflict error *before* touching the database; nothing is
   ever written on a stale call. On a successful write, the SQL `SET`
   clause now includes `revision = revision + 1` atomically alongside the
   other changed columns, so the increment can't itself race. Omitting
   `expected_revision` (`None`) skips the check entirely — exact
   pre-11.5 behavior, so nothing existing broke by adding this.
4. **`server.py`**'s `_handle_update_finding`: reads an optional
   `revision` (must be an int if present, else 400) from the request
   body, passes it through, and turns `FindingRevisionConflictError` into
   `409 {"error": ..., "current": <finding dict>}` — the recoverable
   conflict response the domain model asks for, not a bare failure.
5. **`static/workspace.js`**: the finding-editor's Save button now sends
   the `revision` it loaded the finding at, and specifically recognizes a
   409 response with a clear, distinct message ("Someone else updated
   this finding since you opened it. Reload the page to see the latest
   version before saving again.") instead of the generic failure text
   used for other errors.
6. `revision` was added to every finding dict `list_findings`/`get_finding`
   already returns — no new endpoint needed to read it.

## Exclusions
Scoped to **one** mutable record type (workspace findings) — the most
actively concurrently-edited record in the app today. Not extended to:
the executive memo (`update_memo`), information requests
(`update_request`), or duplicate-marking (`set_duplicate`) — all three
remain last-write-wins, same mechanical pattern available for a follow-up
task. Notably, `set_duplicate` mutating a finding's `is_duplicate`/
`duplicate_of` fields does **not** bump `revision` in this task, so a
concurrent workflow-field save racing a duplicate-marking wouldn't be
caught by this mechanism — disclosed, not silently glossed over. No
optimistic-concurrency UI beyond the plain error message (no diff view,
no auto-merge, no "your changes" draft preservation across the reload the
message asks for) — docs/05's "allow reload/reapply" is satisfied at the
level of "tell the user clearly and let them reload," not a richer
conflict-resolution UI. The other M11.4 items (versioned brief, workstream
assignments) remain untouched, as they were after Task 11.4.

## Reuse
Reuses `workspace_findings`'s existing row shape, `_row_to_finding_state`/
`_merged_finding`, and the existing audit-logging call in
`update_finding_workflow` (a conflict never reaches that call, so no
audit-log change was needed — a rejected write was never a state change
to log). Reuses 11.3b's `_authorized_project` gate unchanged — revision
conflicts are a data-integrity concern layered inside an already-
authorized request, not a new access-control surface. Reuses the existing
`saveHint` error-display element in `static/workspace.js` rather than
building a new conflict-specific UI component.

## Security and intelligence boundary
No AI/model code touched, no new access-control surface (unchanged from
11.3b). The conflict response's `current` field returns exactly the same
shape `GET` on that finding already would for an authorized caller — no
new information is disclosed to someone who couldn't already read it via
the ordinary GET route.

## Acceptance
All tests run against isolated, disposable schemas — never the real
database.
- `tests/test_workspaces.py` (`HumanReviewWorkflowTests`, 4 new tests):
  a fresh finding starts at revision 1; a matching `expected_revision`
  succeeds and increments to 2; a stale `expected_revision` raises
  `FindingRevisionConflictError` **without writing anything** (verified by
  re-reading the finding afterward and confirming the winning write's
  value, not the losing one, is what persisted) and the exception carries
  the real current state; omitting `expected_revision` entirely never
  conflicts (backward compatibility).
- `tests/test_workspace_endpoints.py` (4 new tests, real HTTP server):
  the HTTP-level round trip of the same four scenarios above, including
  the 409 status code and the `current` field's presence in the response
  body; a non-integer `revision` in the request body is rejected (400).
- Full existing suite re-run: `./venv/bin/python -m unittest discover -s
  tests` → `Ran 388 tests ... OK` (380 baseline + 8 new).
  `./venv/bin/python -m mypy $(ls *.py) tests` → `Success: no issues found
  in 48 source files`.
- Frontend: `node --test tests/frontend/*.test.mjs` → 3/3 passing,
  unaffected (`buildFindingUpdatePayload` itself wasn't changed, only its
  call site).
- Browser, against the real running app, a genuine two-editor race rather
  than a simulated one: restarted the real server with this task's code;
  confirmed every real existing finding (Universal Logic included) was
  backfilled to `revision = 1` via the column default. Built a throwaway
  synthetic project/workspace/finding ("Revision Conflict Demo (safe to
  delete)") with one human-added finding, since exercising a *live* race
  against Universal Logic's real findings would mean actually mutating
  real review state, which this session avoids. In the real browser:
  expanded the finding's edit form (this is "Editor A," now holding
  revision 1 in the page's own state) and typed into "Assigned owner" but
  did not yet save; in parallel, issued a direct HTTP request as "Editor
  B" (`assigned_owner: "Editor B", revision: 1`) which succeeded and
  advanced the finding to revision 2; clicked the real Save button in
  Editor A's still-open browser tab and got back exactly the message
  users will see: "Someone else updated this finding since you opened it.
  Reload the page to see the latest version before saving again." —
  rendered in the page's existing danger-color error styling, no console
  exception (the only console entry was the expected 409 network log).
  Re-fetched the finding directly afterward and confirmed `assigned_owner`
  was still "Editor B" at revision 2 — Editor A's stale save never
  overwrote it.

## Data migration and recovery
Applied automatically on server restart: the additive `revision` column
with `DEFAULT 1` requires no backfill logic (unlike 11.3b/11.4, every
existing row's correct starting revision is simply 1 — there's no prior
count to reconstruct). Verified directly on the real database afterward:
a sample of real `workspace_findings` rows (Universal Logic's own
findings included) all show `revision = 1`. Rollback: dropping the one
added column restores exactly today's pre-11.5 schema and behavior; no
existing column, row, or table was altered.
