# Task 17.4 — Targeted Reassessment in React
Status: complete
Authorization: founder directive, 2026-09-27 (Phase A4 of
`17.0-product-integration-program.md`).
Dependencies: 17.1 (document/finding cross-reference pattern, reused
again here for `document_id`).

## User outcome
From a deal's Findings screen, a user sees a staleness banner whenever
the currently-selected workspace has a live staleness flag (data the
backend has computed and returned since Milestone 15, never rendered
anywhere until now), linking to a new "Reassessments" deep page. There,
every targeted-reassessment run for the deal is listed with its exact
document/version-change lineage, its AI-drafted `executive_summary`/
`what_changed`, and its per-finding items - each acknowledgeable by an
analyst/reviewer/deal lead, with the workspace's staleness flag clearing
automatically, exactly as the backend already does it, once every item
is acknowledged.

## Required reading
`reassessments.py`'s own module docstring (explains acknowledgment never
mutates a finding, only records human review, and is the only path that
clears staleness) and its `Reassessment`/`ReassessmentItem` dataclasses;
`server.py`'s `_reassessment_with_items` (~575, composes items +
workspace staleness) and `_handle_reassessment_item_decision` (~2268,
role-gated to analyst/reviewer/deal_lead); `version_dependencies.
get_staleness`, already returned by `_handle_get_workspace` (the
Findings bundle endpoint) but never rendered by `Findings.tsx` until now.

## Baseline
HEAD at `db59c92` (Task 17.3 commit). Full suite green - see STATUS.md.
Confirmed by direct inspection: `_REASSESSMENTS_COLLECTION_RE` is
project-scoped (`/api/projects/{id}/reassessments`), not workspace-
scoped like Decision Package/Readiness - `list_reassessments` supports
an optional `workspace_id` filter internally, but the HTTP route never
exposes it as a query parameter, so this screen lists every reassessment

only ever produced by the `reassessment.compare_versions` mandate

## Scope
1. `frontend/src/lib/api.ts`: generalize the staleness type introduced
   in 17.2 (`DeliverableStaleness`, structurally identical to every
   other `StalenessFlag.to_dict()` call site) into a shared
   `StalenessFlag` type, and correct `WorkspaceBundle.staleness`'s
   existing type (previously narrowed to `{reason: string} | null`,
   which underclaimed what the backend actually returns) to the same
   shared type. Add `Reassessment`/`ReassessmentItem` types,
   `listReassessments`, `getReassessment` (item + `workspace_staleness`),
   and `decideReassessmentItem`.
2. `Findings.tsx`: render a staleness banner when `bundle.staleness` is
   present (already fetched, never shown before this task), linking to
   the new Reassessments page.
3. New `frontend/src/routes/Reassessments.tsx` (project-scoped list, no
   workspace picker): each reassessment shows the changed document
   (cross-referenced by id against `listDocuments`, same pattern as
   17.1's finding cross-reference), `executive_summary`/`what_changed`,
   and its items - each with finding title, explanation, evidence of
   change, and an acknowledge control (decision notes + submit) when
   still pending.
4. `App.tsx`: register `/projects/:projectId/reassessments`.
   `Findings.tsx`: link from the staleness banner and from the header,
   alongside Decision Package/Readiness.
