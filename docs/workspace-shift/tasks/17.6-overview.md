# Task 17.6 — Overview 5-component composition
Status: complete
Authorization: founder directive, 2026-09-27 (Phase B1 of
`17.0-product-integration-program.md`).
Dependencies: Phase A complete (17.1-17.5).

## User outcome
`/` becomes the real Workspace Overview the product docs describe: My
attention (unchanged, already real), a real cross-deal Mandates summary,
Active engagements (unchanged, already real - the existing project
list), genuinely useful Quick actions, and a real, permission-filtered
Material changes feed spanning every accessible deal - not the "simple
overview shell" the backend's own docstring has disclosed since M13.3.

## Required reading
`server.py`'s `_workspace_overview` (its own docstring explicitly named
this a deliberately incomplete shell per `docs/08-roadmap.md`'s
allowance) and `_project_activity_feed`; `overview.py`'s
`count_by_status`/`build_activity_feed`; `version_dependencies.
get_staleness`; docs/product/02's Overview spec (five named components,
"do not display invented deal-health percentages... do not fill
[Material changes] with low-value audit noise").

## Baseline
HEAD at `505c84e` (closes Phase A). Full suite green (858 tests before
this task's own additions). Confirmed by direct inspection:
`_workspace_overview` returned only `my_attention`/`engagements` before
this task - no mandate summary, no material-changes feed, no quick
actions (a pure frontend concern). `Home.tsx` combined "My attention"
and the full deal list into one screen with no Mandates summary, no
Quick actions, no Material changes at all.

## Scope
**Backend** (`server.py`, `_workspace_overview` only - no new table, no
new route): added `material_changes` to the existing `/api/overview`
response, composed by (a) reusing `_project_activity_feed` (the exact
function `Activity.tsx`/`DealOverview.tsx` already call per-deal) across
every accessible project, tagging each event with its project, and (b)
one synthetic `stale_workspace` event per currently-stale workspace
(a real read of `version_dependencies.get_staleness`, not a new kind of
persisted record), merged and capped via the existing
`overview.build_activity_feed`. The Mandates summary needed **no backend
change at all** - `engagements[].mandate_counts` already gave the
frontend everything it aggregates.

**Frontend** (`Home.tsx` rewritten as the real Overview):
- **My attention**: unchanged.
- **Mandates**: real counts aggregated client-side from
  `engagements[].mandate_counts` across every real `MANDATE_STATUSES`
  value (`draft`/`planning`/`awaiting_approval`/`active`/`under_review`/
  `completed`/`cancelled`/`failed`) - no invented category, no
  percentage.
- **Active engagements**: unchanged (the existing project-card list).
- **Quick actions**: three genuinely real, wired actions - "Create a
  deal" (the existing dialog, needs no deal context); "Create a
  mandate" and "Upload evidence" (both jump to the most recently active
  accessible deal's Mandates/Documents page respectively). Deliberately
  **not** built as separate "respond to a request"/"submit work for
  review" buttons - both would be redundant with My Attention, which
  already surfaces the exact item needing a response, more precisely
  than a generic action could.
- **Material changes**: renders the new feed, one row per event kind
  (comment/submission/review_decision/stale_workspace), each linking to
  its real project.

## Exclusions
- **No deal-picker dialog for Quick actions** - a disclosed
  simplification. "Create a mandate"/"Upload evidence" jump to the most
  recently active deal directly rather than presenting a chooser first.
  Fine at this product's current scale (few deals); revisit if real use
  shows this guesses wrong often enough to matter.
- Active engagements is not yet trimmed to a summary-with-link-to-Deals
  - that split happens in 17.7, once the Deals destination actually
  exists (avoids shipping a dead link in this commit).
- No change to `mandates.py`/`version_dependencies.py`/`workspaces.py`
  domain logic - only a new read-side composition in `server.py`.

## Reuse
`_project_activity_feed`, `overview.build_activity_feed`,
`version_dependencies.get_staleness`, `workspaces.list_workspaces` - all
unchanged, called more broadly.

## Security and intelligence boundary
No AI. `_workspace_overview` already scopes everything to
`identity.list_accessible_project_ids` - the new composition adds no new
authorization surface, since it iterates the exact same accessible-
project list the existing `my_attention`/`engagements` computation uses.
