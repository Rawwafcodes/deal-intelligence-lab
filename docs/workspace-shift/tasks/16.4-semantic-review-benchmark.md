Status: complete (bounded scope - see Authorization and Exclusions)

has two real problems: (1) benchmarking "retrieval-gated review" and an
"NLI-plus-model pipeline" for real means building exactly the
infrastructure the roadmap explicitly defers pending measured evidence

chose "Authorize a small bounded paid run now," with the option's own

## Scope
New script `semantic_review_benchmark.py` (a standalone, CLI-invoked
benchmark harness - not a persisted runtime module, and not registered
in `server.py`, since this is an experiment/measurement tool, not new
product functionality; mirrors `migrate_sqlite_to_postgres.py`'s own
"real script at repo root" precedent rather than the store-backed-module
pattern every other M16 task used):
1. Three `BenchmarkCase` fixtures, one per benchmarked defect type
   (`numerical_conflict`, `logical_contradiction`, `modality_escalation`),
   each hand-authoring a short submission text (the analyst's claim) and
   source text (the conflicting evidence) mirroring the corresponding
   golden_set seed case's own scenario as closely as a "submission under
   review vs. source evidence" structure allows (golden_set's own cases
   are framed as two co-equal documents; M14.2's review needs one
   privileged "target" submission), plus a pre-registered expectation
   written down before any call was made.
2. `_text_to_pdf_bytes` - real PDF generation via the system's own
   `cupsfilter`, identical to Task 14.2/14.3's own live-proof method.
3. `build_case_records` - creates one real Task, one real PDF
   work-product submission, and one real PDF source document on a
   caller-supplied project, returning `integrity_review.py`'s own
   `TargetSelection`/`SourceSelection` directly.
4. `main()` - a `--confirm`-gated CLI: without the flag (default),
   builds every real record/PDF and prints what would be sent, at zero
   cost; with `--confirm`, calls `integrity_review.run_integrity_review`
   for real, once per selected case, and writes full results to a JSON
   file for inspection.
5. `tests/test_semantic_review_benchmark.py` - exercises everything
   except the real network call (PDF generation, record creation,
   `integrity_review.validate_selection` acceptance, and a golden-set
   sync check confirming each benchmarked defect type actually has
   exactly one seeded golden case) - zero real Anthropic requests, per
   this codebase's standing convention.

## Exclusions
- **Retrieval-gated review: not built, not benchmarked.** Would require
  real retrieval infrastructure (at minimum a chunking/retrieval
  mechanism; the roadmap's own deferred list names "pgvector or a
  dedicated graph store" as the more specialized version of this).
  Building even a "cheap" stand-in was judged not worth doing under this
  session's authorized scope, which explicitly named skipping this leg.
- **NLI-plus-model pipeline: not built, not benchmarked**, for the same
  reason - "a separate NLI model" is explicitly on the roadmap's own
  deferred-pending-evidence list, and this task's authorization
  explicitly excluded it.
- **Only 3 of the golden set's 10 defect types were benchmarked**
  (numerical_conflict, logical_contradiction, modality_escalation),
  chosen for a deliberate spread (one with an exact classification-label
  match, two without) within a "small bounded" real-money authorization -
  not the full set. `unit_currency_mismatch`, `derivation_divergence`,
  `entity_conflation`, `unsupported_assertion`, `staleness`, and
  `comparator_specificity_mismatch` were not run.
- **No automated scoring.** Recall/precision below was scored manually
  by inspection against the pre-registered expectations, the same
  methodology Task 14.2's own live proof used (`docs/09-acceptance.md`'s
  metrics, recorded by hand) - building an automated semantic-match
  scorer would itself be exactly the kind of "infrastructure ahead of
  evidence" this whole milestone is supposed to avoid.
- **Minimal, sparse synthetic fixtures** (2-3 sentences per document,
  matching golden_set's own prose length) mean several returned
  candidates concern the fixtures' own evidentiary thinness (no date, no
  version, an unprovided term sheet) rather than the specific defect
  each case was built to test - disclosed explicitly under Completion
  evidence rather than silently counted as noise or as false positives.
- **No wiring into any workflow.** This is a one-off benchmark run, not
  a repeatable pipeline hooked into `mandates.py` or any route.

## Completion evidence

### Case 1: numerical_conflict - "Purchase price conflict"
Pre-registered expectation: a candidate classified `numerical conflict`
(severity high or critical) stating the USD 50,000,000 vs. USD
52,000,000 disagreement.

Result (9,046 input / 3,511 output tokens, 45.4s): top candidate -
`[numerical conflict, severity=high]` "Purchase price stated in memo is
USD 2,000,000 below source consideration total" - **exact match**, both
on substance and on classification label. Three further candidates
(medium/low severity) correctly and defensibly note the fixture's own
evidentiary thinness (unverifiable "cash at closing" claim, an
unprovided term sheet, no date/version) - real observations about the
sparse synthetic material, not fabricated facts.

**Verdict: full recall, exact classification-label match.**

### Case 2: logical_contradiction - "Exclusivity compliance contradiction"
Pre-registered expectation: a candidate flagging the compliance claim's
direct contradiction with the disclosed side term sheet.

Result (9,097 input / 4,597 output tokens, 58.5s): top candidate -
`[cross-workstream contradiction, severity=critical]` "Submission's 'no
third-party agreement' assertion contradicted by disclosed Third Party X
term sheet" - **exact match on substance**, correctly identified as the
most severe finding. **Classification-label mismatch, not a scoring
error**: `integrity_review.CLASSIFICATIONS` has no literal "logical
contradiction" entry - `golden_set.DefectType.LOGICAL_CONTRADICTION` and
this vocabulary were built at different times for different purposes and
were never reconciled. The model correctly chose the closest available
label (`cross-workstream contradiction`) rather than inventing one or
mis-filing it elsewhere - a reasonable choice given its actual options,
but confirms these two taxonomies are not the same vocabulary.

**Verdict: full recall on substance; no exact classification-label match
(none exists in the current vocabulary).**

### Case 3: modality_escalation - "Conditional LOI restated as a firm commitment"
Pre-registered expectation: a candidate flagging that "committed" (the
submission) escalates a conditional, non-binding LOI (the source).

Result (18,614 input / 5,039 output tokens, 69.9s, 2 code-execution
requests): top candidate - `[unsupported factual assertion,
severity=critical]` "Conditional LOI language restated as a firm
commitment" - the title names the exact defect verbatim. A second,
independent candidate - `[management or vendor claim presented as fact,
severity=medium]` "Buyer-side intention reported as verified transaction
fact" - captures the same underlying issue from a different angle rather
than duplicating it. **Classification-label mismatch, same root cause as
Case 2**: no "modality escalation" entry exists in `CLASSIFICATIONS`
either; the model split the one real issue across two of its closest
available labels instead of a single precise one. A sixth candidate
(`confirmed consistency`, informational) correctly notes the two
documents at least agree on parties/transaction - not an error.

**Verdict: full recall on substance (independently found via two
candidates); no exact classification-label match (none exists).**

### Summary
**3/3 substantive recall** across this narrow, pre-registered slice: the
current strong-model review correctly identified the core defect in
every benchmarked case, with no fabricated fact or citation on
inspection (every candidate is defensible given the actual, if sparse,
submitted content). **1/3 exact golden_set-label match** (numerical_
conflict only) - a real, measured finding, not a scoring artifact:
`integrity_review.CLASSIFICATIONS` (built for M14.2, before
`golden_set.DefectType` existed) has no literal entry for
`modality_escalation` or `logical_contradiction`, and (unverified this
task, since it wasn't one of the three cases run) plausibly none for
`comparator_specificity_mismatch` either.

**Per the spec's own instruction, no broader claim is made from n=3.**
This is one honest, real data point for the "current strong-model
review" baseline leg, on synthetic, deliberately minimal fixtures - not
a validated accuracy rate, not evidence for or against retrieval-gating
or an NLI pipeline (neither was benchmarked - see Exclusions), and not a
result that generalizes past these three specific cases.

**Limitations, disclosed rather than glossed over**:
- **No IntegrityReview/candidate rows were persisted** - this task calls
  `integrity_review.run_integrity_review` directly (the pure capability),
  not through `mandates.py`'s executor, which is the only code path that
  currently calls `integrity_reviews.create_integrity_review`/
  `create_candidates` to persist the result. The real API responses exist
  only in this task's own printed output and its local JSON results file
  (not committed - transcribed in full above), not in the application's
  own audit trail. Wiring this benchmark through the full mandate
  pipeline instead would have exercised already-proven orchestration
  machinery for no new insight, at extra real cost - the deliberate
  tradeoff this task made.
- **n=3, one model, one severity of fixture minimalism.** Nothing here
  measures how the same approach performs on realistic-length real
  documents, on a broader set of the golden set's ten types, or with a
  different model.
- **The taxonomy-gap finding is real but was not itself a designed
  research question** - it emerged from running the benchmark, not from
  a deliberate comparison. It is flagged as a candidate follow-on (make
  `integrity_review.CLASSIFICATIONS` a superset of, or map cleanly onto,
  `golden_set.DefectType`) rather than acted on in this task, which was
  scoped to the benchmark itself.
- **Retrieval-gated and NLI-plus-model legs remain completely
  unbenchmarked** - 16.4 is not "done" in the sense the spec describes
  (three legs benchmarked); only one of three exists, per this session's
  explicit, disclosed authorization boundary.
