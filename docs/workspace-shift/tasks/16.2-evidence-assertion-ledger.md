Status: complete

Dependencies: none on Task 16.1 (this task promotes M14.2's own real

## User outcome
An M14.2 Integrity Review candidate that a human has already accepted (the
same act that publishes it as a real shared finding) can be promoted into
a separate, versioned ledger record - stable identity, full provenance
(source documents/versions, citations, extraction model/prompt version),
and an explicit human confirmation/dispute lifecycle - independent of
`integrity_review_candidates`' own row, which stays exactly what it always
was (an immutable parsed record of one review run).

## Scope
New module `assertion_ledger.py`:
1. `AssertionLedgerEntry` dataclass and a new `assertion_ledger_entries`
   Postgres table covering every field the 16.2 spec lists: stable
   `entry_key` (a fresh uuid, never derived from the assertion's own
   content - the spec's "separate from content hashes" requirement)
   +incrementing `version_number` +`active`/`superseded` `status`;
   `source_review_id`/`source_candidate_id`/`target_work_product_id`/
   `target_version_id`/`source_document_ids`/`source_version_ids` (source-
   version and locator provenance, the latter via `pdf_citations`/
   `excel_citations` carried over verbatim); `assertion_text` (original
   wording) +`language` (defaults `"en"`; no detection logic exists
   anywhere in this codebase, so this is a stored, honestly-unpopulated
   field today, not a fabricated classifier - disclosed under
   Exclusions); `normalized_fields` (optional freeform dict, `None` by
   default - never mandatory, per the spec's own "never require...rigid
   subject-predicate-object triples"); `modality` (`firm`/`conditional`/
   `uncertain`); `verification_status` (`confirmed`/`disputed`) plus
   `confirmed_by`/`confirmed_at`/`disputed_by`/`disputed_at`/
   `dispute_reason` (human confirmation and dispute state);
   `extraction_model`/`extraction_prompt_version` (copied from the
   parent review at promotion time); `published_finding_id`
   (relationship to the shared finding, when one exists).
2. `promote_candidate(project_id, review_id, candidate_id, *, modality=
   "firm", normalized_fields=None, language="en")` - the only way a
   ledger entry is created. Requires `candidate.decision == "accepted"`
   (raises `CandidateNotPromotableError` otherwise) and that this exact
   candidate has no existing active entry (raises `AlreadyPromotedError`
   otherwise) - enforcing I05's "only after validation" and "no
   duplicate family" rules structurally, not by convention.
3. `dispute_entry(entry_key, *, disputed_by, reason)` /
   `confirm_entry(entry_key, *, confirmed_by)` - each creates a new
   version (supersession history) rather than mutating the current row;
   `dispute_entry` requires a non-empty `reason`, mirroring
   `reviews.record_decision`'s existing rationale requirement.
   `get_entry`/`get_entry_history`/`get_entry_by_candidate`/`list_entries`
   are the read surface, `list_entries` project-scoped with optional
   `target_work_product_id`/`verification_status` filters.
4. `server.py`: one new import, one new `init_assertion_ledger_db()`
   registration line.

## Exclusions
- **No auto-wiring into the live accept-decision path.** The natural
  integration point is `server.py`'s existing candidate-decision handler
  (whatever calls `integrity_reviews.record_candidate_decision(...,
  decision="accepted", ...)` today, part of the already-tested, real M14.2
  flow). Automatically calling `promote_candidate` from inside that
  handler would change already-shipped, already-verified production
  behavior on every future acceptance without a separate sign-off - not
  something to fold silently into a data-model task. `promote_candidate`
  is implemented, tested, and ready to be called from that handler, but
  the wiring itself is left as an explicit follow-on decision.
- **No HTTP route, no frontend surface** - same reasoning as Task 16.1:
  nothing consumes the ledger yet (16.3's reconciler and 16.4's semantic-
  review benchmark are the anticipated first real consumers, both via
  direct Python import, the same way `mandates.py` calls capability
  modules directly rather than over HTTP).
- **No automatic `modality` classification.** Inferring firm/conditional/
  uncertain from a candidate's own `uncertainty`/`deterministic_or_judgment`
  free text would be exactly the kind of semantic-review judgment call
  M16.4 is scoped to do (and benchmark before trusting) - this task
  defaults to `"firm"` and requires an explicit override, rather than
  guessing.
- **No language detection.** The `language` field exists (the spec
  explicitly asks for it) but nothing in this codebase currently detects
  a document's language; it is stored as a plain caller-supplied value
  (default `"en"`), never inferred.
- **No bulk-promotion tool.** Promotion is one candidate at a time,
  matching how M14.2's own accept decision is already one candidate at a
  time.

## Reuse
Reuses `integrity_reviews.py`'s existing `IntegrityReview`/
`IntegrityReviewCandidate` records as the sole source of promotable
content (no new extraction, no new model call) and this session's own
Task 16.1 versioning shape (`case_key`/`version_number`/`status` →
`entry_key`/`version_number`/`status`) for consistency. `dispute_entry`'s
required-reason rule reuses `reviews.py`'s existing rationale pattern
rather than inventing a new validation convention.

## Security and intelligence boundary
No new identity, input, or tool surface, and no LLM/paid call anywhere in
this module. The one access-control-relevant behavior -
`promote_candidate` only accepting an already-`accepted` candidate - is
enforced in this module itself (`CandidateNotPromotableError`) rather than
left to a caller's discipline. Ledger entries are project-scoped
(`list_entries` always filters by `project_id`); this task adds no route,
so no server-level authorization check was needed or added - the same
project-scoped authorization every existing route already enforces would
apply whenever a route is eventually built on top of this.

## Acceptance
`tests/test_assertion_ledger.py`, 13 tests, all passing (fixtures build
real `IntegrityReview`/`IntegrityReviewCandidate` rows via
`integrity_reviews.py`'s own public functions, not mocks):
- Promoting an accepted candidate captures every provenance field
  correctly (assertion text, citations, source ids, extraction model/
  template version, `published_finding_id`), defaults `modality="firm"`
  and `normalized_fields=None`.
- Promotion is refused for a `pending` candidate and for a `rejected`
  one (`CandidateNotPromotableError` in both cases).
- An invalid `modality` value is rejected.
- Promoting the same candidate twice raises `AlreadyPromotedError`.
- `normalized_fields`/`language`/`modality` pass through correctly when
  explicitly supplied.
- `dispute_entry` creates version 2 (status `disputed`), the original
  version 1 becomes `superseded` with its own content untouched and still
  readable via `get_entry_history`; `dispute_entry` with a blank reason
  raises; disputing an unknown `entry_key` raises
  `LedgerEntryNotFoundError`.
- `confirm_entry` after a dispute creates version 3 (`confirmed`),
  clearing dispute fields on the new version while the disputed version 2
  remains on the record exactly as it was.
- `list_entries` is scoped per-project (a second project sees none of the
  first project's entries), filters correctly by `target_work_product_id`
  and `verification_status`, and excludes superseded versions unless
  `include_superseded=True` is passed.

## Data migration and recovery
No migration: a new, additive table on the real local Postgres database,
created via `CREATE TABLE IF NOT EXISTS` the next time the real server
starts. Touches no existing row in any pre-existing table (including
`integrity_reviews`/`integrity_review_candidates`, which this task reads
but never writes to).
