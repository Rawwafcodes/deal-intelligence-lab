## User outcome
A reviewer picks one workspace and asks whether it is ready to sign off.
The mandate engine evaluates a fixed, named, fully documented checklist -
a deal brief exists, at least one source document is on file, no
critical/high finding remains open, no finding is left unreviewed, no
information request is awaiting a response, and either the executive
memo or a decision package has been approved - and reports pass/fail per
item plus an overall ready/not-ready verdict, instantly and at zero cost.
The assessment explicitly states what it does and does not claim: passing
means this one checklist is satisfied, never that the underlying deal or
diligence effort is complete in any broader sense.

## Scope
**1. `readiness.py`** (new, pure assessment logic, no database access) -
`SCOPE_DESCRIPTION` (a plain-English statement of exactly what is and is
not claimed, carried on every persisted assessment - the roadmap's own
"checklist scope explicit; no claim of universal completeness," made
literal rather than merely described) and `assess_readiness`, a pure
function over six named, ordered, documented items
(`CHECKLIST_ITEM_LABELS`): `has_brief`, `has_documents`, `no_open_
critical_or_high_findings`, `no_unreviewed_findings`, `no_open_
information_requests`, `position_approved`. Each item carries a boolean
`met` and a human-readable `detail` naming exactly which findings/
requests caused a failure, never a bare pass/fail with no explanation.

**2. `readiness_assessments.py`** (new, persistence) - one immutable
`ReadinessAssessmentRecord` per assessment run (mandate/run/attempt
lineage, same reserved-key injection every paid capability since 14.2
already uses). Simpler than `deliverables.py`: a readiness assessment is
a report, not a decision, so there is no status/approver field at all -
running it again just creates another row, and every prior one stays
visible exactly as computed at the time.

**3. `mandates.py`** - new `readiness.assess_scope` capability, the
first real (non-fixture) use of `side_effect_class="read_only"`:
`unit_cost=0.0`, not the nominal `1.0` every paid capability declares,
since no provider call is made and there is genuinely nothing to bill.
New single-stage `readiness` template - deliberately no `human_
checkpoint`: viewing an assessment commits nothing and publishes
nothing, so there is no decision here for a checkpoint to gate
(docs/04: "avoid approval bureaucracy for every internal thought").
`_default_input_for_stage`'s new branch verifies the workspace exists
but - unlike `decision_package.produce_draft` - checks no readiness
precondition before allowing the plan: the whole point of this
capability is to report whether a workspace is ready, so it must be
runnable precisely when it is *not* ready. Added to `_TEMPLATES_
EXCLUDED_FROM_LLM_PLANNING` for the same reason as `decision-package` -
it needs a `workspace_id`, and the planner has no "workspace selection"
concept today.

**4. `server.py`** - `GET /api/projects/<id>/workspaces/<id>/
readiness` (list) and `GET .../readiness/<id>` (detail). No `POST`
action of any kind - nothing here is approved, rejected, or published;
it is a read surface only, same authorization boundary
(`_get_owned_workspace`) as every other workspace sub-resource.
`readiness_assessments.init_readiness_assessments_db()` added to
`main()`.

**5. Tests** - `tests/test_readiness.py` (17 tests: every checklist
item's pass/fail branch individually, persistence round-trip and
multi-assessment preservation, capability/template registration
including the *absence* of a checkpoint stage, propose-time rejection of
an unknown or cross-project workspace, a run completing successfully
even when nothing is reviewed yet - proving no readiness precondition
blocks proposing it - and the budget ledger charging exactly `0.0` for a
real `read_only` capability) and `tests/test_readiness_endpoints.py` (6
tests, real HTTP server + real background Worker, **no mocking anywhere
in either file** - the first capability test suite in this codebase that
needs none, since there is no external call to mock: template listing;
propose requires `workspace_id`; the full lifecycle over HTTP completing
to `succeeded` with no checkpoint pause; a revoked member denied on
their very next request; project isolation; unknown assessment 404s).

## Exclusions
**Scoped to one workspace, never the whole deal** - the same "explicit,
bounded scope, not universal completeness" boundary `decision_package.py`
already established; a deal with several workspaces gets one assessment
per workspace, never a combined one. **No workstream-completion item** -
`workstreams.py` has no status field at all today (confirmed by
inspection); inventing one to support a checklist item would be new
domain state built ahead of any other consumer needing it, out of this
task's bounded scope (roadmap M14: "unsupported... becomes a separate
bounded task"). **Not offered to the LLM planner** - see
`_TEMPLATES_EXCLUDED_FROM_LLM_PLANNING` above. **No re-assessment
trigger** - unlike M15's own future "potentially stale" mechanism, a
readiness assessment is a point-in-time snapshot; nothing here
automatically re-runs it when a finding's review status later changes.
**No dedicated frontend panel** - reachable today via the same generic
mandate composer/detail screens every template without a bespoke panel
already uses (matching `MandateDetail.tsx`'s existing raw-output
fallback), not a purpose-built readiness dashboard.

## Reuse
The `readiness` template's single-`capability`-stage shape reuses Task
12.1/12.2's runtime completely unchanged - no new stage kind, no new
worker. `_run_stages`'s existing budget-ledger check (Task 12.2) is
exercised for real, for the first time, against a capability whose
`unit_cost` is genuinely `0.0` rather than a paid capability's nominal
placeholder. `position_approved` reads `workspaces.get_memo`
(Milestone 9) and `deliverables.latest_deliverable_version` (Task 14.3)
side by side as two equally valid satisfying conditions - no new memo or
deliverable concept invented, and no preference given to the newer
mechanism over the older one.

## Security and intelligence boundary
This capability's blast radius is the narrowest of any registered so
far: `allowed_source_formats=None`, no document of any kind is read, no
network request of any kind is made, and its `side_effect_class` is
`read_only` - there is no external transmission surface to defend at
all. Every identifier (`workspace_id`) is independently re-verified
against real, current, project-scoped state at both propose and
execution time, matching every other capability's own discipline, even
though nothing here could leak cross-project data through a forged id
beyond a 404 either way (`workspaces.get_workspace` is itself
project-scoped).
