## User outcome
A deal lead can see and manage exactly who has access to a deal and in
what role, from the same page they already use to manage workstreams.
An analyst who tries to approve their own submitted work is refused,
by role, not merely by task-status ordering. A reviewer or deal lead can
approve it instead, and the task moves to "approved" for real. Revoking
someone's access takes effect on their very next request. An external
executive granted access to a deal sees a genuinely smaller Deal
Overview - the brief and only the deliverables someone has actually
approved for them - never the internal task list, comments, mandates,
or activity feed.

## Scope
**1. `identity.py`** - additive only, nothing removed or renamed:
- `DEAL_ROLES` gained a fourth role, `"external_executive"`, alongside
  the existing analyst/reviewer/deal_lead.
- `_seed_defaults()` now also idempotently seeds a fourth dev identity,
  `external@local.dev` / "Morgan Reyes (External Executive)", as an
  organization member with no deal membership anywhere by default (real
  access must be explicitly granted, same as everyone else) - added to
  *both* of `_seed_defaults()`'s branches (the already-seeded early
  return and the fresh-seed path), since the real database had already
  run its one-time seed and takes the early-return path every server
  start.
- New `get_deal_role(project_id, user_id) -> str | None`: the caller's
  own real, currently-active role on a deal, or `None`. This is the one
  new primitive both role checks below are built on - always checked
  against the caller's own session-resolved identity, never a
  client-supplied role string.

**2. `server.py`** - three additions:
- **Deal-membership management routes**, the missing piece that made
  every other multi-identity check below possible at all: `GET
  /api/projects/<id>/memberships` (any authorized deal member),
  `POST /api/projects/<id>/memberships` (grant/change a role - deal_lead
  only, body `{user_id, role}`), `DELETE
  /api/projects/<id>/memberships/<user_id>` (revoke - deal_lead only).
  Composed the same way `_assignments_with_users` already composes
  workstreams.py with identity.py: a new `_memberships_with_users()`
  helper carries each member's display info inline.
- **Role enforcement on review decisions** (T04, literally): inside
  `_handle_review_work_product`, a caller whose `get_deal_role` is not
  `"reviewer"` or `"deal_lead"` gets a 403 before any review logic runs.
- **A genuinely restricted Deal Overview for `external_executive`**: a
  new `_deal_overview_restricted()` branch inside `_deal_overview`,
  selected when the caller's own real role is `external_executive`.
  Returns `{"project", "restricted": true, "brief", "approved_
  deliverables"}` - each approved deliverable being the task title, the
  work product record, and when it was approved - built from the same
  `reviews.is_current_version_approved`/`latest_decision_for_work_product`
  already reused elsewhere; no tasks, comments, mandates, reconciliation
  detail, or activity feed of any kind reaches this payload.

**3. Frontend**: a new "Deal access" card on `static/project.html`/
`project.js`/`style.css`, styled identically to the existing Workstreams
card (reuses its `.workstream-item`/`.workstream-header`/`.workstream-
roster` CSS classes rather than adding new ones) - roster list, a
grant form (identity + role select), and a revoke button per active
membership. `frontend/src/routes/DealOverview.tsx` gained a
`RestrictedDealOverviewView` branch, selected when the fetched payload
carries `restricted: true`, rendering only the brief and approved-
deliverables cards; `frontend/src/lib/api.ts` gained the
`RestrictedDealOverview`/`ApprovedDeliverable` types and widened
`getDealOverview`'s return type to the union of both shapes.

## Exclusions
**T05 is only partially addressed.** This task restricts exactly one
surface - the Deal Overview - for `external_executive`. Every other
route a deal member can reach (document download/inspect, task detail,
mandate detail, cross-format-analysis/workspace findings, search,
citations, exports) still uses the plain `has_deal_access` check and
returns its full, unrestricted content to *any* role including
`external_executive`, exactly as it did before this task. Closing T05
in full - "cannot obtain internal notes via overview/search/export/
citation" - would mean auditing and gating every one of those routes by
role, which is a materially larger task than "restrict the overview
page" and was not attempted here; disclosed rather than silently left
implied by the one restriction that was built. **No UI lockout of
disallowed actions** - the static page still renders review/approve
controls and the membership grant/revoke form to every viewer
regardless of role; the enforcement is entirely server-side (403), which
is correct for the security boundary but means an analyst or external
executive can still *see* controls that will refuse them, a UX
polish item left for later. **No protection against a deal lead
revoking their own only remaining `deal_lead` membership** (self-lockout
is possible; not addressed, since docs/06 does not require it and no
test scenario in this task exercised it). **No new capability, template,
or AI/model call of any kind.** **No deployment, no push, no `git
commit`** (per this effort's established default).

## Reuse
Every review-decision and membership check is a straight read of
`identity.get_deal_role`, added once and reused twice - no duplicated
authorization logic between the two call sites. The membership routes
reuse `identity.add_deal_membership`/`revoke_deal_membership`/
`list_deal_memberships_for_project` entirely unmodified - Task 11.3b
already built history-preserving grant/revoke semantics; this task only
gives them an HTTP surface and a role gate. The restricted overview
reuses `reviews.is_current_version_approved`/
`latest_decision_for_work_product` and `tasks.list_tasks`/
`work_products.list_work_products`, all unmodified. The "Deal access"
card reuses the Workstreams card's own CSS classes and its exact
"roster list + inline grant form + per-row revoke button" shape rather
than inventing new markup or styles.

## Security and intelligence boundary
No AI, no model call, no provider transmission anywhere in this task.
Both new role checks resolve the caller's role server-side from their
own session-bound identity (`self.current_user_id` -> `identity.
get_deal_role`) - never from a client-supplied role field, so a caller
cannot claim `"deal_lead"` in a request body to bypass either check
(verified live and by test: granting/revoking membership and recording
a review decision all check the real row in `deal_memberships`, not
request input). Membership mutation itself is gated to deal_lead only,
matching docs/06's "Change access: ... Authorized deal management ...
No [for external_executive]" row exactly. Revocation takes effect
immediately (verified live: the very next request after a `DELETE
.../memberships/<user_id>` from a different, already-revoked identity
returns 404, identical to the pre-existing 13.1-era revocation
behavior). The restricted Deal Overview is a strict allow-list (only
`project`, `restricted`, `brief`, `approved_deliverables` are ever
constructed for that branch) rather than a denylist over the full
payload, so a future field added to the full Deal Overview cannot leak
into the restricted one by omission.
