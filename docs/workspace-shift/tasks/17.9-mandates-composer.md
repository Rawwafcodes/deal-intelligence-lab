# Task 17.9 — Unified Mandates composer (Phase C)
Status: complete
Authorization: founder directive, 2026-09-27 (Phase C of
`17.0-product-integration-program.md`), begun once Phase A/B closed.
Dependencies: Phase A/B complete; reuses `MandateDetail.tsx`'s existing

## User outcome
Creating a mandate now starts with an explicit, guided choice - Flexible
(AI proposes the method), Review (checks a work product/conclusion
against evidence), Pipeline (a named professional template), or
Monitoring (a standing trigger for a future event) - each mapped to real
backend behavior, not four decorative labels. Choosing Pipeline shows
the real, currently-registered professional templates (reconciliation,
decision package, readiness, reassessment - not the two internal
`fixture-*` proof-of-concept templates, filtered out as a disclosed,
frontend-only display decision). Choosing Review pre-selects the real
`integrity-review` template. Choosing Flexible creates the mandate and
immediately invokes the existing AI-planning path. Choosing Monitoring
does not create a mandate at all - it hands off to the existing Phase A5
Triggers page, since that is what "reacts to future changes" already
means on this backend. Everything past this first choice - evidence
selection, the proposed plan, approval, budget/usage limit, execution -
is the same, already-built, already-tested `MandateDetail.tsx` flow,
unchanged.

## Required reading
`mandates.py`'s own `_TEMPLATES` registry (all 8 registered templates'
own docstrings - each already states, in its own words, what it does and
whether the LLM planner may propose it); `_TEMPLATES_EXCLUDED_FROM_LLM_
PLANNING`; `triggers.py`'s own module docstring (why Monitoring is a
trigger, not a mandate capability); the existing `MandateDetail.tsx`
(948 lines - AI proposal, manual template/stage-input selection, plan
approval, budget-limited run execution, all already real and tested);
docs/product/03's Mandates-and-intelligence spec (four starting
structures; "These are four ways of configuring a mandate, not four
unrelated products"; Controls "must affect real execution
configuration—not be visual checkboxes with no backend consequence").

## Scope
1. `frontend/src/lib/mandateTemplates.ts` (new, shared): categorizes the
   real template registry into the four starting structures by key -
   `review: ["integrity-review"]`, `pipeline: [every non-`fixture-*`,
   non-review key]`, and an explicit `hiddenFromComposer: ["fixture-
   echo", "fixture-echo-with-review"]` set, with the reasoning recorded
   inline (mirrors the templates' own disclosed "proves the runtime...
   registers no real analytical capability").
2. New `frontend/src/components/MandateComposerDialog.tsx` replacing
   `MandateList.tsx`'s bare objective-only dialog: step 1 (objective,
   unchanged validation) -> step 2 (four real starting-structure cards).
   Pipeline expands into the real, filtered template list (name +
   description straight from the registry, not rewritten). Monitoring's
   card is a direct link to `/projects/:id/triggers`, not a form field -
   selecting it does not create a mandate.
3. `createMandate` unchanged; on submit, the dialog navigates to the new
   mandate's detail page with `?structure=<flexible|review|pipeline>` and,
   for review/pipeline, `&template=<key>`.
4. `MandateDetail.tsx`: reads those two query params once on the first
   load after creation (a draft mandate with no plan yet). `structure=
   flexible` auto-invokes the existing `handleProposeWithAi()` exactly
   once. `template=<key>` pre-selects that key in the existing manual-
   template dropdown instead of defaulting to the registry's first
   entry. No other behavior in this 948-line file changes.
5. A small, static "Human approval is always required before
   execution" notice added next to the existing budget-limit input -
   `docs/03`'s own required "Controls" visibility, satisfied honestly
   for the one control (approval) that is fixed rather than
   configurable.

## Exclusions
- **No "require citations" control** - no real backend hook exists;
  inventing a checkbox with no effect would violate the spec's own
  explicit instruction.
- **No new Evidence-selection step ahead of the existing one** -
  `MandateDetail.tsx` already asks for document/version selection
  exactly when a chosen capability needs it (`CAPABILITIES_NEEDING_
  DOCUMENT_SELECTION`); duplicating that earlier in a wizard would be a
  second, competing evidence-selection UI, not reuse.
- **Monitoring never creates a mandate directly** - by design, matching
  how `triggers.py` actually works (a trigger creates a mandate later,
  only when its real event fires).
- No change to `mandates.py`, `triggers.py`, the capability registry, or
  the durable worker - this task is 100% frontend composition over
  already-real backend behavior.
