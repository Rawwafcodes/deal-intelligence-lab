Status: complete (scoped slice — see Exclusions)
Authorization: roadmap M12.1 ("Mandate/template/plan/run contracts and
fixture planner; shared composer/detail"). The founder said "go ahead" in
response to this session's recommendation to start M12 after M11.4 closed,
continuing under the same standing instruction to implement directly
("from now on I want you to implement the tasks you're performing, don't

task builds only 12.1's own scope — the runtime's plumbing, proven with a
deterministic planner and one fixture capability, never a real analytical
capability or an AI call. That mirrors the roadmap's own explicit
sequencing: **Gate A says not to register a second analytical capability
until the existing reconciliation one is proven through this runtime** —
which means the runtime has to exist and be trustworthy *first*, using
something safe to iterate on, before 12.3 ever touches
`cross_format_analysis.py`.

access-control surface); 11.4/11.4b (the "additive schema,
immutable-version-log, revocation-preserves-history" idioms this task's
Run/Attempt persistence follows).

## User outcome
A mandate can be commissioned with a plain-language objective, planned
(from one of two built-in templates), approved, and run — sequentially,
through registered capabilities — including a real "the plan pauses for a
human decision, then continues" path. Every step is a real, persisted
record (not a simulation): Mandate → PlanRevision → Run → Attempt, exactly
the shape docs/03-domain-model.md and docs/04-mandate-engine.md describe.
Nothing here is connected to Claude or to the app's real reconciliation
capability yet — that wiring is 12.3/Gate A's explicit job, deliberately
not done here.

## Scope
**1. Two in-memory, code-level registries** (docs/04: "Register each
capability with: name/version; input schema; output schema; ... side-
effect class; permission check; executor" — this describes registering
code, not persisting user data):
- **Capabilities**: `CapabilityDescriptor(name, version, side_effect_class,
  permission_check, executor)`. Exactly one registered:
  `fixture.echo` v1, `read_only`, always-permitted, echoes its input back
  with a timestamp. No real capability (reconciliation or otherwise) is
  registered — that is 12.3/Gate A's job, explicitly not done here.
- **Templates**: `Template(key, version, name, description, stages)`,
  stage shape matching `examples/reconciliation-template.json`'s own
  vocabulary. Two registered: `fixture-echo` (one capability stage) and
  `fixture-echo-with-review` (adds a `human_checkpoint` stage after it) —
  the second exists specifically to prove the "sequential steps and human
  waits" runtime shape docs/04 asks for, not because a checkpoint after an
  echo is a real workflow.

**2. Persisted domain records** (`mandates.py`, four new tables): `Mandate`
(status: draft/planning/awaiting_approval/active/under_review/completed/
cancelled/failed), `PlanRevision` (status: proposed/approved/rejected/
superseded; stages stored as JSON, each capability stage's `input`
filled in by a placeholder function standing in for what a real planner
would derive from selected sources), `Run` (queued/running/succeeded/
failed/interrupted/outcome_unknown/cancel_requested/cancelled/
waiting_for_input), `Attempt` (succeeded/failed/awaiting_human).

**3. Runtime functions**:
- `create_mandate` → starts `draft`.
- `propose_plan(project_id, mandate_id, template_key)` — "the fixture
  planner": always instantiates one of the two built-in templates, never
  a model call. Runs its stages through `validate_plan_stages` — the
  *same* untrusted-input validator a real (12.4) planner's model output
  would have to pass (duplicate/missing stage ids, unknown stage kind,
  unregistered capability, and — the "no DAG editor" rule from docs/04,
  enforced structurally, not just asserted — a dependency can only name
  an *earlier* stage in the list). Re-proposing while a plan is still
  `proposed` supersedes it rather than leaving two live proposals.
- `approve_plan`/`reject_plan` — the human gate. Approving sets the
  mandate `active` and its `current_plan_id`; rejecting returns it to
  `draft`.
- `execute_run` — **synchronous, in the same HTTP request that starts
  it** (see Exclusions: 12.2's durable async worker is a separate task).
  Walks the approved plan's stages in order. A `human_checkpoint` stage
  records an `awaiting_human` attempt and stops the run at
  `waiting_for_input` — **the mandate itself stays `active`** the whole
  time (docs/04, verbatim: "Active mandates can be waiting_for_input or
  paused" — a Run-level condition, not a separate Mandate status; an
  earlier draft of this task incorrectly moved the mandate to
  `under_review` here, caught by this task's own tests before it shipped
  — see Completion evidence). A capability stage with an unregistered
  name, a failed permission check, or a raised exception fails the
  Attempt, the Run, and the Mandate, and stops - no automatic retry.
  Completing every stage succeeds the Run and completes the Mandate.
- `resume_run(project_id, mandate_id, run_id, stage_id, decision)` —
  records the human's decision on the paused Attempt and continues
  executing the *same* run from the next stage - proving the actual
  "wait, then continue" lifecycle, not just a status field that happens
  to say so.
- `cancel_run` — only while `waiting_for_input` (there is no other
  in-flight state to cancel in this synchronous runtime; see Exclusions).

**4. `server.py`**: 11 new routes (templates list; mandate
create/list/get; plan propose/approve/reject; run start/get/list/resume/
cancel), all behind the existing `_authorized_project` gate — no new
authorization surface. Two small composition helpers embed each
mandate's plans/runs and each run's attempts inline.

**5. Frontend — the "shared composer/detail" UI, on the React scaffold
(`frontend/src/routes/MandateList.tsx`, `MandateDetail.tsx`)**: a list
view (objective + status per mandate, a "+ New mandate" dialog) and a
combined composer/detail view that walks the actual lifecycle in the UI —
template picker → propose → approve/reject → start run → per-attempt
output/error display → a decision textarea and Resume/Cancel controls
when a run is paused at a checkpoint. New standalone routes
(`/projects/:projectId/mandates`, `/projects/:projectId/mandates/
:mandateId`) rather than nested under a project-detail route, since none
exists yet on the React side (see Baseline). A small "Mandates →" link
was added to each project card on `Home.tsx`, placed as a sibling of (not
nested inside) the card's own pre-existing, already-broken `/projects/:id`
link, to avoid creating an invalid nested-anchor and without touching that
unrelated, pre-existing gap.

## Exclusions
**12.2's durable async worker is not built.** `execute_run`/`resume_run`
run synchronously inside the HTTP request that calls them — there is no
persisted "job" independent of the request, no heartbeat, no crash
recovery, and closing the browser mid-request would behave like any other
interrupted HTTP call, not like a durable job surviving it (docs/04's own
"Durable execution is local work" section is explicitly about the
opposite of what's built here). **12.3's real reconciliation adapter and
Gate A are not built.** `cross_format_analysis.py` is never invoked by
this module; the only registered capability is the fixture. Gate A itself
therefore has not been attempted, let alone passed — this task is the
prerequisite plumbing Gate A will later be run against. **12.4's LLM
planning is not built.** `propose_plan` never calls a model; the "planner"
is two hand-written templates. **12.5's second-capability reuse proof**
does not apply yet, since there is only ever one capability. No branching/
parallel execution (stages run strictly in the order stored - the "no DAG
editor" rule from docs/04). No budget/usage accounting, no source/document
selection into a plan (the placeholder `_default_input_for_stage` only
ever fills the one field `fixture.echo` needs). No mandate cancellation
while a capability attempt is actually executing (meaningless in a
synchronous runtime with no in-flight window - see Scope). No deployment,
no push, no `git commit`, no paid AI calls.

## Reuse
Reuses `_authorized_project` unchanged for every route - no new access-
control code. Reuses the additive-schema idiom from every prior task
(`CREATE TABLE IF NOT EXISTS`, no ALTER to any existing table). Reuses
11.3b's `DealMembership`/11.4b's `WorkstreamAssignment`
"revoke-preserves-history, re-grant inserts a new row" shape's *spirit*
for `PlanRevision`'s supersede-on-re-propose behavior (a superseded plan
is marked, never deleted or overwritten). Reuses `examples/
reconciliation-template.json`'s own stage vocabulary rather than inventing
a new one, so a *real* template built later (12.3) is a drop-in shape
match, not a rewrite. Reuses `frontend/`'s existing shadcn `Button`/`Card`/
`Dialog`/`Textarea` components and the plain-`<select>`-with-Tailwind-
classes pattern the AppHeader's identity switcher (Task 11.3b) already
established, rather than introducing a new form primitive.

## Security and intelligence boundary
No AI/model code touched anywhere in this task - the "fixture planner" is
two hand-written Python dicts, not a provider call. No new access-control
surface: every mandate route requires the same project-level
authorization every other route already does. The one registered
capability (`fixture.echo`) has no side effects (`side_effect_class:
"read_only"`) and touches no document, finding, or external system. The
capability-executor call in `_run_stages` is wrapped in a bare
`try/except Exception` specifically because an executor is untrusted,
third-party-shaped code by the model's own design (docs/04: "capabilities"
are meant to be extensible) - a raised exception fails the attempt
cleanly rather than crashing the request.

## Completion evidence
See Acceptance above for exact commands/results. Two real issues found
and fixed during this task's own verification, disclosed rather than
smoothed over:
1. **Mandate-status bug**: an early draft of `_run_stages` moved the
   Mandate to `under_review` when a run paused at a human checkpoint.
   `tests/test_mandates.py::test_execute_run_stops_at_human_checkpoint`
   was written to assert exactly this and failed immediately, which is
   what caught it - re-reading docs/04-mandate-engine.md's lifecycle
   section ("Active mandates can be waiting_for_input or paused") showed
   the pause belongs on the Run, not the Mandate; fixed before any other
   code was built on top of the wrong behavior, and confirmed again live
   in the browser afterward (the second mandate's "Active" badge while
   its run showed "waiting_for_input").
2. **Stale server bug**: the real backend server process running on port
   8765 was not restarted after this task's `server.py`/`mandates.py`
   changes landed, so the *first* live browser check hit the old code,
   which had no route for `/mandates` and fell through to the generic
   `/api/projects/<id>` handler - misinterpreting `<real-project-id>/
   mandates` as a bogus, nonexistent project id and returning a
   misleadingly plausible-looking `{"error": "project not found"}` 404.
   Caught by checking the actual HTTP response with `curl` against the
   real server rather than assuming the browser error toast ("Could not
   load mandates") meant an application bug; fixed by restarting the
   server, re-verified with the same `curl` call before returning to the
   browser.
