# Task 17.10 — Wire the assertion ledger (Phase D, part 1)
Status: complete
Authorization: founder decision D15 (`docs/10-decisions.md`, 2026-09-27),
given directly in response to this program's own required Phase D
procedure (inspect contract, document smallest integration, identify

Dependencies: none beyond already-implemented `assertion_ledger.py`
(M16.2) and the Integrity Review candidate-decision handler (M14.2).

## User outcome
Every real `accepted` Integrity Review candidate decision now also
promotes into the evidence assertion ledger - a persistent, versioned
record of the exact claim a human confirmed, with its own provenance,
modality and dispute/reconfirm history, distinct from the open findings
register. A new "Assertions" deep page shows these entries per deal;
an analyst/reviewer/deal lead can dispute one (with a required reason)
or re-confirm a disputed one, over the real HTTP surface.

## Scope
**Backend**: `_handle_integrity_candidate_decision` now calls
`assertion_ledger.promote_candidate(project_id, review_id, candidate_id)`
immediately after `integrity_reviews.record_candidate_decision`
succeeds, only when `decision == "accepted"` (mirroring the existing
publish-as-finding condition exactly). Three new routes: `GET
/api/projects/<id>/assertion-ledger` (list, project-scoped, reuses
`assertion_ledger.list_entries` verbatim), `POST .../assertion-ledger/
<entry_key>/dispute`, `POST .../assertion-ledger/<entry_key>/confirm` -
both reuse `dispute_entry`/`confirm_entry` verbatim, role-gated to
analyst/reviewer/deal_lead (the same "Recommend finding disposition"
pattern every other candidate/item-decision route already uses), and
both independently re-verify the entry's own `project_id` matches the
URL before acting - `assertion_ledger.py`'s own functions take no
project scoping at all (`entry_key` is globally unique), so this
handler-level check is the only thing preventing cross-project access.

**Frontend**: new `frontend/src/routes/Assertions.tsx`, a project-scoped
deep page (mirrors `Reassessments.tsx`'s pattern - no workspace picker,
since ledger entries are project-scoped, not workspace-scoped).
Cross-references `target_work_product_id`/`source_document_ids` against
`listTasksWithWorkProducts`/`listDocuments` (the same pattern every
earlier Phase A task established) rather than showing raw ids. Linked
from `Findings.tsx`'s header alongside Decision Package/Readiness/
Reassessments.

## Exclusions
- **Kept deliberately separate from the Findings register, not merged
  into it** - an assertion is a claim a human confirmed once; a finding
  is an open matter under review. Collapsing them would flatten a real
  distinction `docs/03-domain-model.md` itself draws (locator-valid vs.
  quoted-value-checked vs. calculation-reproduced vs. human-confirmed
  are different verification states). The published finding a promoted
  assertion originated from is linked to, not duplicated.
- No automatic `modality` classification (still M16.4-shaped judgment
  work, explicitly out of scope per `assertion_ledger.py`'s own
  docstring) - every promoted entry defaults to `modality="firm"`.
- **`reconciler.py` remains completely unwired** - the founder's chosen
  option did not extend to it, and no real fact-extraction pipeline
  exists to produce the `NumericFact`s it requires; building one would
  be new capability, not integration. Recorded in D15, not revisited
  here.
- No change to `assertion_ledger.py`/`integrity_reviews.py` themselves -
  pure reuse of already-tested functions.

## Reuse
`assertion_ledger.promote_candidate`/`dispute_entry`/`confirm_entry`/
`list_entries`/`get_entry` (all unchanged), the exact lineage data
`_handle_integrity_candidate_decision` already assembles,
`listTasksWithWorkProducts`/`listDocuments` (frontend cross-reference
pattern from earlier Phase A tasks).

## Security and intelligence boundary
No AI. `promote_candidate` only ever promotes an already-`accepted`
candidate (the same human act that already publishes a finding) -
never a raw model proposal. The handler-level `project_id` cross-check
on dispute/confirm is a real, tested authorization boundary
`assertion_ledger.py` itself does not provide.
