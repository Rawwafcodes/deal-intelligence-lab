## Scope
New module `golden_set.py`:
1. `DefectType(str, Enum)` - the ten types verbatim from the spec (numerical
   conflict, temporal/period mismatch, unit/currency mismatch, derivation
   divergence, entity conflation, modality escalation, unsupported
   assertion, staleness, logical contradiction, comparator/specificity
   mismatch), plus `DEFECT_TYPE_DESCRIPTIONS: dict[DefectType, str]` giving
   each a one-sentence definition - the taxonomy is genuinely defined
   semantically, not just ten opaque string tokens.
2. `GoldenCase` dataclass and a new `golden_cases` Postgres table:
   `case_key` (stable identity, generated once) + `version_number`
   (increments) + `status` (`active`/`superseded`), mirroring
   `documents.py`'s Document/DocumentVersion split - `create_case` starts a
   new family at version 1; `supersede_case` creates version N+1 and
   retires version N, carrying forward any field not explicitly
   overridden; `get_case`/`get_case_history`/`list_cases` are pure reads.
   `provenance` is constrained to `synthetic` / `authorized_real`.
3. Ten seeded synthetic cases (one per defect type), inserted idempotently
   by `init_golden_set_db()` the first time the table is empty (same
   idempotent-seed pattern as `identity._seed_defaults()`). Every seeded
   case's `scenario_text` is prefixed `[SYNTHETIC]` and uses an invented
   company/figures, and `provenance="synthetic"` - never real deal content,
   per the spec's own confidentiality instruction and this session's
   standing "never touch the real Universal Logic project" rule.
4. `server.py`: `golden_set.init_golden_set_db()` registered in `main()`
   alongside the other 21 `init_*_db()` calls, so the table and its seed
   data exist on every server start, same as every other store-backed
   module.

## Exclusions
- No HTTP route and no frontend surface. Nothing in the codebase consumes
  the golden set yet (16.3/16.4 will, by direct Python import - the same
  way `mandates.py` calls capability modules directly, not over HTTP).
  Adding an API ahead of a real consumer would be exactly the kind of
  ahead-of-evidence architecture the M16 gate text itself warns against;
  it will be added in whichever of 16.3/16.4 first needs a UI/API surface
  for it, once that shape is actually known.
- No editing/deletion UI, no bulk import tool, no per-organization scoping.
  The spec describes one shared reusable corpus, not a per-deal or
  per-tenant resource.
- No real/authorized-real cases were added, only synthetic ones - this
  session has no standing authorization to reuse content from Universal
  Logic (or any other real deal) outside its own workspace, and the spec
  requires explicit authority before doing so. `provenance="authorized_real"`
  is implemented and tested as a valid value so a future task can add such
  a case once that authorization exists, but none exists in the seed set.
- No change to `integrity_reviews.py`'s `classification` field or its
  prompt - wiring the new controlled taxonomy into the M14.2 capability's
  own output is 16.3/16.4 work (using the golden set to justify each rule),
  not this task's.

## Reuse
Structurally this task reuses two already-proven patterns rather than
inventing new ones: `documents.py`'s Document/DocumentVersion split (stable
key + incrementing version + status field) for the case-versioning model,
and `identity.py`'s idempotent seed-on-init pattern for populating default
reference data. No existing capability, executor, or schema needed
modification - this is purely additive, matching every M11-M15 task's own
default of new tables over altered ones wherever the data was genuinely
new.

## Security and intelligence boundary
No new identity, input, or tool surface: this module takes no user input at
runtime today (no route exists) and makes no LLM/paid calls. Its own
content boundary is the confidentiality rule from the 16.1 spec itself:
case content must never be real, unauthorized client material - enforced
here by construction (all ten seeded cases are synthetic, clearly labeled
in their own text) rather than by a runtime check, since there is no
input path yet for a caller to insert real content. Future authorized-real
cases will be a human decision made through whatever surface eventually
calls `create_case(provenance="authorized_real", ...)` - not automated.

## Acceptance
`tests/test_golden_set.py`, 10 tests, all passing:
- Seeding covers all ten defect types exactly once, and reseeding
  (`init_golden_set_db()` called twice) is idempotent (no duplicate rows).
- Every seeded case is `provenance="synthetic"` and its `scenario_text`
  contains the `[SYNTHETIC]` marker.
- `create_case` starts at version 1, status `active`; `get_case` finds it
  by `case_key`.
- `create_case` rejects an invalid `provenance` value.
- `supersede_case` creates version 2 (status `active`), retires version 1
  (status `superseded`, content otherwise unchanged and still readable via
  `get_case_history`), carries forward any field not explicitly
  overridden, and `get_case` now returns the new version as current.
- `supersede_case` on an unknown `case_key` raises
  `GoldenCaseNotFoundError` rather than silently creating a new family.
- `list_cases` excludes superseded versions by default but includes them
  with `include_superseded=True`; filters correctly by `defect_type`.
- `DEFECT_TYPE_DESCRIPTIONS` covers every `DefectType` member with a
  non-empty description.

## Data migration and recovery
No migration: this is a new, additive table on the real local Postgres
database (created via `CREATE TABLE IF NOT EXISTS` the next time the real
server starts, same as every other `init_*_db()` call), touching no
existing row in any pre-existing table. No backup/rollback procedure is
needed beyond dropping the new table, which nothing else references.

## Paid calls and external transmission
None. No LLM call of any kind in this task - the ten seed cases are
hand-authored fixture text, not model-generated, and nothing here calls
`ai_client`.

**Limitations, disclosed rather than glossed over**:
- Only synthetic cases exist right now; the taxonomy has never been
  checked against a single real defect pattern. Whether these ten
  categories and the seeded examples are actually the right shape to
  justify 16.3's reconciler rules or 16.4's benchmark won't be known until
  those tasks try to use them - this task cannot itself prove the taxonomy
  is *sufficient*, only that it exists, is versioned, and is queryable.
- One seed case per defect type is a minimal starting corpus, not a
  statistically meaningful "golden set" for benchmarking false-positive/
  false-negative rates (gate 5's own concern) - 16.4's benchmarking work
  will very likely need more cases per type, and possibly harder/
  ambiguous variants, before its own numbers mean anything.
- This task does not, on its own, close M16 gates 4 or 5 (recurring
  reusable assertions; measured failure modes) - it creates the
  *substrate* 16.3/16.4 would need to start closing them, nothing more.
