## Scope

### Walkthrough preconditions (checked once, before S01)
- Local Postgres running, backend test suite green, frontend built into
  `static/` (the same preconditions every M17 task already required -
  not new).
- All four dev identities seeded; `IdentityFooter`'s dev-identity
  `<select>` is how the walkthrough switches actor without a real
  sign-in (surface #5 is dev-stub-only, per the reconciliation - this is
  not worked around, it is the documented current mechanism).
- Decide before S01 whether to reuse the existing "Baseline Smoke Test
  Deal" (faster, but already has real history that could make S02/S05-S09
  read as "already done" rather than freshly observed) or create one new
  synthetic deal for this walkthrough (cleaner signal, slightly more
  setup). Recommendation: create one new deal for S02 onward, keep the
  existing baseline deal only for anything that specifically needs its
  pre-existing history (e.g. S17's "review material changes").

### S01 — Create or enter an organization
Role: `lead`. Starting state: signed in via dev-identity switcher.
Actions: (1) look for any in-app affordance to create a new
organization or view/edit the current one's settings; (2) confirm the
session's current organization is visible somewhere (sidebar footer,
`IdentityFooter`). Expected result, per the existing reconciliation
(surface #24, Organization Settings): **entering** an already-assigned
organization works implicitly (every session already carries one from
seed data); **creating** one has no UI and no HTTP route at all - this
is an already-known, already-assigned (M19 minimum, M23 full) gap, not a
new defect to log as a surprise. Record it as a confirmation.

### S02 — Create/open a deal
Role: `analyst` or `lead`. Starting state: `/deals`. Actions: (1) click
"+ New deal" (`Deals.tsx`); (2) fill name/description in the dialog,
submit; (3) confirm the new deal appears in the list; (4) click it to
open Deal Overview. Expected result: deal created under the caller's own
organization (server-side default, no org picker shown - consistent
with S01's finding), Deal Overview loads with an empty/near-empty brief.

### S03 — Establish users and roles
Role: `lead`. Starting state: the new deal's Overview. Actions: look for
any in-app "invite"/"add member"/"manage team" affordance on this deal
or its organization. Expected result, per the reconciliation (surface
#23, Team and Access): **none exists** - deal-level membership grant/
revoke is real but API-only, exercised only by tests/curl per every
prior M13/M17 task's own baseline setup, never a UI. Record as a
confirmation, not a new finding; note in the walkthrough record that
this blocks any *later* scenario that would need a second identity added
to this specific new deal (fall back to the pre-seeded "Baseline Smoke
Test Deal" for those, or grant membership via the real API as a manual
setup step outside the walkthrough's own UI-only scope).

### S04 — Create/edit the deal brief
Role: `lead` or `analyst`. Starting state: Deal Overview, the deal from
S02. Actions: (1) click "Edit brief" (`BriefEditorDialog`, opened from
`DealOverview.tsx`); (2) enter an objective; (3) save; (4) confirm the
brief section now shows the new version number and objective text.
Expected result: a new brief version is created and displayed; the prior
(empty) state is not silently overwritten in a way that loses history
(per D06's stable-history rule) - check whether a version history view
exists or only the latest version displays.

### S05 — Add workstreams and assignments
Role: `lead`/`analyst`. Starting state: the deal's Work destination
(`/projects/:id/work`). Actions: (1) create a workstream via the
workstream-creation control in `Work.tsx`; (2) confirm it appears; (3)
proceed to S07 for task assignment (assignment happens at the task
level, not a separate workstream-assignment screen - confirm this
matches the actual UI rather than assuming a separate assignment step
exists).

### S06 — Upload documents and document versions
Role: `analyst`. Starting state: `/projects/:id/documents`. Actions: (1)
open the upload dialog (`DocumentUploadDialog`); (2) upload a small
synthetic file; (3) confirm it lists with correct name/size/folder; (4)
upload a second file with the same relative path to produce a new
version; (5) click the document's inline `href` to confirm it opens the
raw file. Expected result for step 5, per the reconciliation (surface
#13, partial): a direct file view, not an in-app version-history/
citation panel - record this as the already-known partial gap, and use
this scenario's own live run as the concrete evidence for the open M18
founder decision on whether it needs to close before acceptance.

### S07 — Create tasks and comments
Role: `analyst`/`lead`. Starting state: `Work.tsx`. Actions: (1) open
the new-task dialog, assign it to the S05 workstream and to an
identity; (2) confirm it appears as a card; (3) add a comment on it; (4)
confirm the comment persists on reload.

### S08 — Submit work products
Role: the identity the S07 task was assigned to. Starting state: the
task card. Actions: submit a work product against the task (the
submission control inside `WorkProductItem`/`TaskCard`). Expected
result: status moves to `submitted`, immutable per D06.

### S09 — Review, return and approve work
Role: `reviewer` or `deal_lead` - confirmed via `authz.py`'s own matrix
that these are exactly the two roles holding `REVIEW_WORK` (`analyst`
and `external_executive` do not). Starting state: the submitted work
product from S08. Actions: (1) as `analyst` (the S07/S08 assignee),
confirm no Approve/Return control renders at all (Task 17.14's own fix -
verify it still holds, not only that it once did); (2) as `reviewer` or
`deal_lead`, return it with a rationale, confirm status changes; (3)
resubmit as `analyst`; (4) approve it as `reviewer` or `deal_lead`.

### S10 — Create and execute mandates
Role: `lead`/`analyst`. Starting state: the deal's Mandates destination.
Actions: (1) open the mandate composer (`MandateComposerDialog`); (2)
state an objective, select the deal's own evidence, pick a starting
structure; (3) submit for a proposed plan; (4) approve the plan; (5)
observe run progress through to completion or a clear in-progress state.

### S11 — Use Flexible, Review, Pipeline and Monitoring structures
Role: `lead`. Starting state: the mandate composer. Actions: repeat S10
once per starting structure (Flexible, Review, Pipeline, Monitoring),
confirming the composer actually offers all four and each produces a
plan whose shape differs appropriately (e.g. Monitoring should route
toward Triggers per `MandateComposerDialog.tsx`'s own
`navigate(".../triggers")` call, confirmed in the reconciliation).

### S12 — Review findings and evidence
Role: `analyst`/`reviewer`. Starting state: `/projects/:id/findings`,
after at least one mandate run (S10) has produced findings. Actions:
(1) select the relevant workspace from the picker; (2) expand a finding
row (surface #15's inline-expansion form); (3) confirm evidence/
citation locators are visible and, where the underlying document
supports it, clickable.

### S13 — Create and respond to information requests
Role: `analyst` (create) and `external_executive` (respond). Starting
state: a finding from S12. Actions: (1) as `analyst`, open
`RequestDialog` from Findings and send a request; (2) as
`external_executive`, confirm the request appears on their restricted
Deal Overview with a working response control (Task 17.14's own
addition - verify it still renders and persists a response, not only
that it once did); (3) submit a response; (4) confirm it persists on
reload.

### S14 — Use readiness and reassessment
Role: `lead`/`reviewer`. Starting state: Findings' own links to
Readiness/Reassessments (not a tab - per the reconciliation's corrected
form finding, these are reached via contextual links from `Findings.tsx`,
not the deal tab strip). Actions: (1) open Readiness, confirm a real
checklist renders against real deal state; (2) open Reassessments,
confirm it lists any stale/superseded items and can propose a targeted
reassessment.

### S15 — Use assertions and evidence status
Role: `reviewer`/`lead`. Starting state: Findings' link to Assertions.
Actions: accept an Integrity Review candidate (if one exists from a
prior mandate run) and confirm it appears in the Assertions view with
provenance/verification status (D15's own wiring).

### S16 — Produce/review a decision package
Role: `lead`. Starting state: Findings' link to Decision Package.
Actions: (1) open Decision Package; (2) compose/select the approved
material to include; (3) confirm the resulting package reflects only
reviewed/approved content, per D06/D14's own rules against unreviewed
material appearing as a position.

### S17 — Review material changes and activity
Role: any. Starting state: Overview (Material changes component) and
`/projects/:id/activity`. Actions: confirm every action taken in S02-S16
appears, correctly attributed to the identity that performed it, in
both views.

### S18 — Verify restricted external-executive experience
Role: `external_executive`. Starting state: signed in as this identity
on the walkthrough's deal. Actions: (1) confirm the nav strip shows only
Overview (Task 17.14's own fix); (2) attempt direct URL entry to
`/findings`, `/documents`, `/work` and confirm a real access-denied card
renders with no flash of the guarded page's real content or an
unauthorized fetch firing first.

### S19 — Verify restart persistence
Role: any. Actions: (1) note the exact state of an in-progress mandate
run (S10/S11) or a pending review (S09); (2) restart the Python server
process (or, if not feasible mid-walkthrough, close and reopen the
browser tab, which is the weaker but still meaningful check); (3)
confirm the same state is visible afterward - the durable worker (M12.2)
already claims to survive this; this scenario is the first time it is
checked from the actual React product's own screens, not only the
backend test suite.

### S20 — Verify concurrent identities and revision conflicts
Role: two identities on the same deal. Actions: (1) open two independent
browser contexts (matching Task 17.13's own method - separate contexts
with separate `dl_session` cookies, not one session switched in place);
(2) both open the same brief/task for editing; (3) have one save first,
then the other; (4) confirm the second save produces an explicit
revision-conflict signal rather than silently overwriting the first
(T06's backend guarantee - this scenario checks it is visible from the
UI, not only enforced server-side).
