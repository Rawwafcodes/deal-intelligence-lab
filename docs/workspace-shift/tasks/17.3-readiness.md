# Task 17.3 — Readiness in React
Status: complete
Authorization: founder directive, 2026-09-27 (Phase A3 of
`17.0-product-integration-program.md`).
Dependencies: 17.1/17.2 (same deep-page-linked-from-Findings pattern).

## User outcome
From a deal's Findings screen, a user can open a "Readiness" deep page
for the same workspace and see every readiness assessment ever run
(newest first, each an immutable snapshot - running the check again
never overwrites history), with an honest pass/fail verdict, the exact
scoped checklist that produced it (six named, explicit items - not a
percentage), which items are unmet and why, and a pointer to where to
act next (Findings/Requests, the two surfaces this checklist actually
checks).

## Required reading
`readiness.py`'s own module docstring in full (explains the checklist's
exact scope and explicitly warns against a broader "deal is done"
reading) and its `assess_readiness`/`ChecklistItem`/`ReadinessAssessment`
dataclasses; `readiness_assessments.py`'s `ReadinessAssessmentRecord`
and `list_readiness_assessments`/`get_readiness_assessment`;
`server.py`'s `_WORKSPACE_READINESS_COLLECTION_RE`/`_ITEM_RE` and their
handlers (~3426-3441, read-only, no create route).

## Baseline
HEAD at `b682d5c` (Task 17.2 commit). Full suite green modulo the
already-disclosed pre-existing worker-timing flake (unrelated, confirmed
in 17.2's own entry). Confirmed by direct inspection: no create route

## Scope
1. `frontend/src/lib/api.ts`: add `ReadinessAssessment`/`ChecklistItem`
   types (mirror the backend exactly) and `listReadinessAssessments`/
   `getReadinessAssessment` functions.
2. New `frontend/src/routes/Readiness.tsx`, a deep route
   (`/projects/:projectId/readiness`) nested under `DealShell`, same
   workspace-picker pattern as `DecisionPackage.tsx`. Lists assessments
   newest-first; each shows the overall ready/not-ready verdict, the
   `scope_description` (rendered verbatim, not summarized - the module's
   own point is that the scope must never be silently broadened), and
   every checklist item with its label, met/unmet state, and detail
   text. Unmet items get a short "see Findings" / "see Requests" pointer
   (generic, since the checklist itself carries no specific finding/
   request id to deep-link to - it is an aggregate check, not a per-item
   citation; not inventing a link the data doesn't support).
3. `App.tsx`: register the new route. `Findings.tsx`: add a link,
   alongside the existing Decision Package link.

## Exclusions
- **No percentage score, health meter, or traffic-light dashboard
  invented.** The backend gives exactly one boolean plus six named
  items - the UI shows exactly that, nothing synthesized on top.
- **No "run readiness check" button.** No create route exists; running
  the assessment is the `readiness.assess_scope` mandate capability's
  job, reachable once the Phase C composer exists.
- No change to `readiness.py`/`readiness_assessments.py`.
