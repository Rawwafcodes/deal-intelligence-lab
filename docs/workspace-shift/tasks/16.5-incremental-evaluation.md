Status: complete (detection only - see Exclusions)

## User outcome
An assertion ledger entry (Task 16.2) automatically becomes flagged
stale the moment one of its own source documents gets a real new
version - using the exact same, already-proven Task 15.1 mechanism every
other dependent in this app already relies on, with zero new schema. A
caller can also ask whether a specific entry was produced by the
model/prompt version still considered current, and combine both checks
into one answer: is this entry safe to reuse as-is, or does something
about it need a human's attention before being trusted further.

## Scope
Extended `assertion_ledger.py` (no new module, no new table):
1. `promote_candidate` now also calls
   `version_dependencies.record_dependencies("assertion_ledger_entry",
   entry.entry_key, [...])`, one leaf edge per
   `(source_document_ids[i], source_version_ids[i])` pair, immediately
   after inserting the new entry. Keyed on the entry's own stable
   `entry_key` (not the version row's own `id`), so staleness tracking
   survives a later `dispute_entry`/`confirm_entry` version bump
   unchanged.
2. `get_staleness(entry_key)` / `is_stale(entry_key)` - thin, honest
   pass-throughs to `version_dependencies.get_staleness("assertion_ledger_
   entry", entry_key)`. No new staleness computation exists - this reads
   back a flag Task 15.1's own `mark_superseded` already sets whenever
   `documents.add_version` (or any future caller) fires on one of the
   entry's real source documents.
3. `is_extraction_current(entry, *, current_model, current_prompt_
   version)` - the spec's other required cache-validity axis
   (prompt/model identity), which `version_dependencies.py` has no
   concept of. A pure comparison against caller-supplied "what's current
   now" values - this module takes no dependency on `integrity_review.py`
   (the executor) to answer this, keeping the existing storage/executor
   separation intact.
4. `is_reusable(entry, *, current_model, current_prompt_version)` -
   `True` only when both `not is_stale(...)` and
   `is_extraction_current(...)` hold. Detection only: never triggers a
   re-check itself.
5. `list_stale_entries(project_id)` - the spec's own "reevaluate only
   changed assertions" query surface: which of a project's current
   ledger entries actually need attention, filtered from `list_entries`.

## Exclusions
- **No automatic re-evaluation.** Nothing in this task re-runs an M14.2
  review, re-promotes a fresh candidate, or mutates a stale entry in any
  way. Per the spec's own "Full reassessment remains an explicit
  mandate," detecting that something needs attention and actually doing
  something about it are kept as separate, deliberately un-joined steps -
  the same boundary Task 15.1 drew for workspace staleness (resolved for
  that domain only by Task 15.2's own explicit reassessment flow,
  unchanged and untouched here).
- **No reassessment mechanism for the ledger analogous to
  `reassessments.py`.** Building "targeted reassessment for a stale
  assertion ledger entry" (re-running the review, presenting the human
  with old-vs-new, recording an acknowledgment) is real, separate work
  with its own real paid-call implications - explicitly out of this
  task's scope, left as a named follow-on.
- **`reconciler.py`'s findings (Task 16.3) are not wired into dependency
  tracking.** A `ReconcilerFinding`'s two `NumericFact`s each carry a
  `source_type`/`source_id`, and the same pattern used here could
  register them as dependents too - not attempted, since nothing
  currently produces `NumericFact`s from real, versioned sources (Task
  16.3's own disclosed limitation), so there is no real staleness
  scenario to wire up yet. Flagged as a natural, analogous extension for
  whenever `reconciler.py` gets a real caller.
- **No caching layer.** The spec's "Cache only when..." language
  describes a *condition* under which reuse is valid - this task answers
  that condition (`is_reusable`) but builds no cache itself (no memoized
  computation, no TTL, nothing stored beyond what already exists). There
  is nothing yet in this codebase that would consume a cache built ahead
  of a real need.
- **No HTTP route, no frontend surface** - same reasoning as every other
  M16 task so far: no real caller yet.

zero new module.

## Acceptance
Extended `tests/test_assertion_ledger.py` with 4 new tests (17 total in
the file, up from 13), all passing:
- A freshly promoted entry is not stale (`is_stale` false, `get_staleness`
  `None`) until `version_dependencies.mark_superseded("document", ...)`
  fires on one of its real source documents - the same real event
  `documents.add_version` triggers in production - at which point
  `is_stale` becomes true and `get_staleness` returns the correct,
  specific flag (matching source id and new version id).
- Staleness persists correctly across a `dispute_entry` version bump -
  the new version (a new row `id`) is still reported stale, because
  tracking is keyed on the stable `entry_key`, not the per-version row.
- `is_extraction_current` correctly distinguishes a matching vs.
  mismatched model/prompt-version pair; `is_reusable` is true only when
  both conditions hold, correctly turns false when either the source
  becomes stale OR the model/prompt is out of date (tested
  independently, including a second, entirely unaffected entry whose
  only problem is an out-of-date prompt/model - confirming the two axes
  are genuinely independent, not conflated into one check).
- `list_stale_entries` returns exactly the stale entries for the calling
  project and none for an unrelated project.
- One real test-isolation bug found and fixed while writing these tests:
  the pre-existing fixture hardcoded `"doc-1"`/`"doc-2"` for every
  created review, which would have made `mark_superseded` calls in one
  test retroactively flag entries created by *other* tests sharing the
  same document ids (since staleness is source-scoped, not
  entry-scoped). Fixed by adding optional `source_document_ids`/
  `source_version_ids` parameters to the shared `_make_review_and_candidate`
  helper (defaulting to the original literals, so the three pre-existing
  tests that assert on those exact values are unaffected) and giving
  every new staleness-related test its own unique document id via
  `uuid.uuid4()`.

## Data migration and recovery
No migration, no new table. `version_dependencies.record_dependencies`
inserts into the already-existing `dependency_edges` table (Task 15.1),
using `ON CONFLICT ... DO NOTHING` semantics that table already had -
promoting the same candidate twice (already prevented by
`AlreadyPromotedError`) could never double-insert an edge either way.

**Limitations, disclosed rather than glossed over**:
- **Detection only, exactly as scoped** - there is still no way, from
  this codebase alone, to act on a stale or non-reusable assertion
  ledger entry other than a human reading `list_stale_entries`'s output
  and deciding what to do about it by hand. This is the deliberate
  boundary the spec's own "full reassessment remains an explicit
  mandate" draws, not an oversight.
- **Only one of the two M16.2/16.3 modules is wired into dependency
  tracking.** `reconciler.py`'s findings remain outside this mechanism
  entirely - a real gap if/when `reconciler.py` gets a real caller
  producing versioned `NumericFact`s, flagged above under Exclusions
  rather than silently left for someone else to discover.
- **`is_extraction_current`'s "current" values must be supplied by the
  caller** - this task makes no claim about what "current" model/prompt
  version actually is right now in the live system (that would require
  either hardcoding `integrity_review.REVIEW_TEMPLATE_VERSION`/
  `DEFAULT_MODEL` into this module, coupling storage to the executor, or
  reading the live `ANTHROPIC_MODEL` env var, which Task 16.4 already
  disclosed can differ from a task's own stated authorization). Left as
  an explicit parameter rather than guessed.
