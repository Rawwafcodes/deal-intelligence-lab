# Task 19.7 — M19 documented security review

Status: implemented fact for what was directly verified in this session
against the checkout and the live staging deployment on 2026-10-21; a
self-review by the implementing agent, not an external audit. Recorded as
the M19 exit gate's "independent security review or equivalent documented
review", per the founder's explicit choice of that option over holding the
gate open for a real external reviewer.

## Scope and method

Reviewed: authentication, authorization/tenant isolation, document access,
secret handling, SQL construction, CSRF, and the live staging deployment's
configuration. Method: direct code reading, targeted greps across the
whole backend, the full automated test suite (964 tests, run against a
local Postgres instance only — see the fix below), and live checks against
the actual Railway/Neon staging deployment. Not covered: a formal
penetration test, dependency/CVE scanning, or review of the React frontend
bundle for client-side issues. Those remain open if a real external
review is wanted later.

## Findings

### 1. Fixed during this review: a real secret-exposure risk in local test runs

`tests/__init__.py` (the test package's own isolation guard) only ran when
tests were invoked as `python -m unittest tests.test_x` or
`discover -s tests -t .`. The command documented in `README.md` —
`python -m unittest discover -s tests` (no `-t .`) — imports each test file
as a bare top-level module instead, **skipping `tests/__init__.py`
entirely**, including the guard that stops a test run from reaching a real
database.

Independently, several application modules (`ai_client.py`,
`mandate_planning.py`, `xlsx_inspection.py`, `cross_format_analysis.py`,
`decision_package.py`, `reassessment.py`, `cross_document_analysis.py`,
`integrity_review.py`) call `dotenv.load_dotenv(".env.local")` on import.
A developer's `.env.local` can hold a real hosted `DATABASE_URL` with
password (this checkout's does, pointing at the live staging Neon
database) for staging access per `docs/deployment/staging-setup.md`.

Combined, running the test suite the way the README told you to could
silently pick up that real `DATABASE_URL` and run `init_databases()` /
schema-admin operations against the live staging database instead of the
local test instance. This was caught live in this session: a full-suite
run attempted exactly that connection and only failed because this sandbox
has no network access to resolve the host — not because anything in the
code stopped it.

**Fixed**: `tests/__init__.py` now neutralizes `dotenv.load_dotenv` for the
whole test process before anything else imports, so `.env.local` can never
populate `DATABASE_URL` (or any other value) during a test run, regardless
of import order or which test file runs first. `store.py`'s `_connect()`
also now refuses, as a second independent check, any non-local
`DATABASE_URL` host while `store.REFUSE_PUBLIC_SCHEMA` (the tests
package's own "we are under test" flag) is set — so even a future test
that sets `DATABASE_URL` directly without going through `.env.local` is
still caught. CI is unaffected: it has no `.env.local` file and sets
`DATABASE_URL` directly to a disposable localhost Postgres, which the
local-host allowlist still permits. `README.md`'s documented command is
corrected to `-t .`, matching what CI actually runs.

Verified: re-ran the full suite the corrected way — 964 tests, all
passing, with the leak reproduced-then-blocked as a regression check in
between.

### 2. Tenant isolation and document access: verified, no issues found

Ran the full authorization/tenant-isolation/document-access test suite
(`test_authorization_matrix.py`, `test_authz.py`, `test_hosted_auth.py`,
`test_documents.py`, `test_document_versions.py`,
`test_organization_endpoints.py` — 84 tests) in isolation and as part of
the full suite: all passing. Confirmed live (not just in tests) that deal
access can only be granted to members of the deal's own organization, and
that a deal can never be left without a deal lead. Hosted-auth tests cover
rejected/forged/expired/wrong-issuer/wrong-origin tokens, dev-identity
endpoints returning 404 in hosted mode, and uninvited sign-ins being
refused.

### 3. SQL construction: no injection risk found

Every data-carrying query uses parameterized placeholders (`%s` with a
tuple of values). A handful of call sites build the SQL text itself with
an f-string (`tasks.py`, `mandates.py`, `workspaces.py` — e.g.
`f"UPDATE tasks SET {set_clause} WHERE id = %s"`), but the interpolated
part is always a comma-joined list of **column names drawn from Python
keyword arguments the calling code supplies**, never from raw request
data — not user-controlled, so not an injection vector.

### 4. CSRF: present, not independently re-verified beyond existing tests

`server.py` documents and implements CSRF mitigation for mutating
requests, and `DEAL_LAB_ALLOWED_ORIGINS` extends the origin check to the
hosted domain. Existing test coverage was not re-read line by line in this
pass; flagging as verified-by-reference rather than freshly re-derived.

### 5. No application-level rate limiting beyond the AI provider's own

Found no per-user or per-IP request-rate limiting at the HTTP API layer
(login attempts, invite submissions, etc.) — only the Anthropic client's
own handling of that provider's rate-limit responses. The mandate budget
ledger (cost/usage limits on AI runs) is a separate, existing control and
is not what's missing here. This is a real, open gap for a public or
semi-public deployment; for an invite-only staging pilot with a handful of
named users it's a low-severity gap, not a blocker, but worth tracking
before any broader exposure.

### 6. Live staging configuration checked directly

- `web` and `worker` Railway services: both online, zero issues, zero
  recent failures at time of review.
- Both services now run in `europe-west4` (moved from a mismatched `sfo`
  region for `worker` during this session), matching the EU-residency plan
  in `docs/deployment/staging-setup.md`.
- No production secret found in source control: `.env.local` is gitignored
  and was never committed (checked across full git history, including for
  specific leaked-key patterns); `.env.example` holds placeholders only.
- Backup restoration demonstrated live against the actual staging Neon
  project: snapshotted production, restored it onto a separate branch,
  confirmed identical data, then returned the project to its original
  single-branch state. No data loss, no live-app disruption, confirmed
  before and after.
- `ANTHROPIC_API_KEY` on both Railway services was suspected expired
  mid-session; founder confirmed afterward it is not. No action needed.

### 7. Worker-interruption survival: existing evidence accepted, not re-demonstrated live on staging

The underlying mechanism (durable runs, heartbeat/lease recovery, exactly-
once completion under concurrent workers, clean SIGTERM) has automated
test coverage and was demonstrated live against a disposable local
database in Task 19.2. A staging-specific live re-run (a real mandate run,
deliberately interrupted mid-run by restarting the `worker` service) was
offered and the founder explicitly declined it — the cost and effort
wasn't judged worth it given the mechanism is already proven, not because
of any remaining doubt about it. This gate item is accepted as satisfied
on that existing evidence; a founder decision, recorded here rather than
left open.

## Summary

No critical or high-severity issue found that isn't already fixed. One
real, previously-undetected gap was found and fixed (the `.env.local`
secret-exposure path into test runs). One open, low-severity gap is
documented and accepted rather than blocking (no HTTP-layer rate
limiting). One operational blocker is flagged for the founder
(`ANTHROPIC_API_KEY` expired) that affects next steps but not this
review's own completion.
