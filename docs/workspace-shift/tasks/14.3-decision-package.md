## User outcome
A reviewer picks one workspace whose findings already carry real human
review activity and asks for a decision package. The mandate engine
drafts an executive summary, a recommendation, an evidence synthesis, an
outstanding-matters list, and a risks/limitations section - built only
from the workspace's own already-reviewed findings and open requests,
never from raw source documents. The draft pauses at a human checkpoint;
a deal lead must separately, explicitly approve one exact version before
it becomes anything more than a draft. Editing or redrafting later
creates a new version; an already-approved version stays visible and
approved regardless.

## Scope
**1. `decision_package.py`** (new, pure adapter, no database access) -
genuinely different in shape from `cross_format_analysis.py`/
`integrity_review.py`: sends no original PDF/Excel/work-product bytes to
the model at all. Its only input is a deterministic, app-assembled text
digest (`build_digest`) of a workspace's own already-persisted findings
(title, classification, effective severity, review status, resolution
status, recommended action, commercial relevance, uncertainty) and open
requests. `validate_selection` requires at least one finding and at
least one finding with `review_status != "unreviewed"` - the literal
operationalization of the roadmap's own "explicit reviewed... material."
A single plain-text `client.messages.create` call (no citations feature,
no Files API, no code execution - none of those apply to a capability
with no source documents); a plain heading-split parser (`_parse_
sections`) replaces the heavier segment/citation parser reconciliation
and Integrity Review need, since there is no citation stream to
reconstruct here.

**2. `deliverables.py`** (new, persistence) - `DeliverableVersion`: one
row per drafting attempt, `version_number` monotonic per workspace
(mirrors `PlanRevision.revision_number`), `status` draft/approved,
mandate/run/attempt lineage (same reserved-key injection Task 14.2's own
lineage fix established in `_run_stages`), full drafted content, the
reviewer's stated emphasis, and the exact source finding/request ids
considered. `is_current_version_approved`/`approve_deliverable_version`
mirror `reviews.py`'s exact-version-approval shape precisely: approving
targets one exact version id, refuses a version that is not the
workspace's current latest (a newer draft supersedes it), and refuses a
second approval of an already-approved version. Deliberately no separate
"decision-package run" audit table the way reconciliation/Integrity
Review each have one distinct from their own findings/candidates table -
a failed drafting attempt's own record lives on the mandate Attempt row's
`error` field, not a second persisted row (disclosed simplification,
proportionate to this capability's much lighter shape - see the module's
own docstring).

**3. `mandates.py`** - new `decision_package.produce_draft` capability
(`input_schema` requires `{workspace_id}`, optional `emphasis`;
`output_schema` requires `{deliverable_id, workspace_id, version,
model}`; `side_effect_class="external_paid_call"`;
`allowed_source_formats=None`, since this capability has no source
documents at all) and a new `decision-package` template (`draft`
capability stage -> `checkpoint` human_checkpoint stage - the exact
"capability then human_checkpoint" shape 12.5/14.2 already proved, zero
new runtime mechanism). `_default_input_for_stage` independently
re-verifies the workspace exists in this project and already has
reviewed material *before* a plan can be approved - not deferred to
execution. `_decision_package_executor` re-verifies again at execution
time (a workspace could in principle be deleted, or its review activity
theoretically altered, between approval and execution), builds the
digest, calls the adapter, and persists the `DeliverableVersion` only on
success. New `_TEMPLATES_EXCLUDED_FROM_LLM_PLANNING` entry for
`decision-package`: the LLM planner (`mandate_planning.
propose_candidate_plan`/`TemplateSummary`) has no concept of "workspace
selection" today, only "document selection" - extending it is a
separate, unauthorized future task, not attempted here.

**4. `server.py`** - `GET /api/projects/<id>/workspaces/<id>/
deliverables` (list), `GET .../deliverables/<id>` (detail), `POST
.../deliverables/<id>/approve` (gated to `deal_lead` only, per docs/06's
own "Approve decision package: No / Recommend / Yes / Explicit grant
only" row - a `reviewer`'s "Recommend" has no dedicated endpoint in this
v1, a disclosed scope simplification). No new route is needed to
*trigger* a draft - it reuses the existing generic mandate propose/
approve/run/resume lifecycle exactly as every other template already
does. `deliverables.init_deliverables_db()` added to `main()`.

## Exclusions
**No inline editing of a draft before approval** - a deal lead can
approve or decline to approve as-is; producing a revised draft means
proposing and running the capability again (a new, independent
`version_number`), not editing text in place. **No dedicated "reviewer
recommends" endpoint** - docs/06's own permission table gives a reviewer
"Recommend" rather than "No" on decision-package approval; this v1
refuses a reviewer exactly like an analyst (403), matching the pattern
disclosed in the endpoint test's own docstring, since building a genuine
recommend-vs-approve two-step is a separate, larger feature. **Not
offered to the LLM planner** - `_TEMPLATES_EXCLUDED_FROM_LLM_PLANNING`;
extending `mandate_planning.py` to a genuine "which workspace is this
objective about" selection is unauthorized future work. **No cross-deal
or cross-workspace digest** - one `DeliverableVersion` synthesizes
exactly one workspace's own findings/requests, never several workspaces
combined. **No real-dollar cost accounting** - `unit_cost=1.0` is
nominal, exactly like every other registered capability; the budget
ledger mechanism enforcing it is real (proven live and by test).

## Reuse

shape, and the whole propose/approve/run/resume mandate lifecycle beneath
it, is Task 12.1/12.2's runtime completely unchanged - no new stage kind,
no new worker, no new approval mechanism. Lineage injection

application of `reviews.py`'s own established pattern to a new record
type, not a new design.

## Security and intelligence boundary
This capability's blast radius is narrower than reconciliation's or
Integrity Review's by construction: it never touches a document, a
work-product file, or the Files API, and its `allowed_source_formats` is
`None` - there is no file-format surface to attack at all. Every
identifier (`workspace_id`) is independently re-verified against real,
current, project-scoped state at both propose time and execution time,
never trusted from the plan's own stored copy - the same discipline every
other capability in this app already follows. The model's prompt
explicitly instructs it to synthesize only from the supplied digest and
never introduce a new fact, and to treat digest content as untrusted data
rather than instructions (docs/06: "Source content is data, not
authority"). The draft is never auto-approved: `create_deliverable_
version` always inserts `status="draft"`; only an explicit, separately
role-gated `POST .../approve` call - resolved server-side via
`identity.get_deal_role`, never from client input - can change that.
