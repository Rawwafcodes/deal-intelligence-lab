## Real findings disclosed, not fixed
Both of the following are genuine, live-confirmed gaps. Neither is
fixed in this task: both are policy or UI-permission-model decisions,
which this program's own stop-and-ask conditions place outside a
verification task's authority to resolve unilaterally.

1. **The Task 13.4 restricted-view gap has grown, not shrunk.**
   Confirmed live: `GET /api/projects/<id>/workspaces` as the
   `external_executive` identity returns a real `200` with full
   findings-workspace data (checked directly against the real running
   server, real response). `server.py`'s workspace routes gate on
   `_authorized_project` - "is a member of this deal at all" - not on
   role. The one role-aware branch that exists is
   `_deal_overview_restricted`, and `Activity.tsx` (Task 17.6/this
   program) was written to explicitly re-check `overview.restricted`
   client-side before rendering - but Findings, Documents, Decision
   Package, Readiness, Reassessments, Assertions, and Triggers (all
   built across this program's Phases A-D) have no equivalent check,
   backend or frontend. An `external_executive` who should only see
   `{project, brief, approved_deliverables}` per Task 13.4's own design
   can currently reach the full findings register, evidence documents,
   readiness assessments, and assertion ledger of any deal they hold
   that role on. This is the same gap Task 13.4 disclosed
   (2026-09-17: "search/export/citation/task-and-mandate-detail remain
   fully visible to any deal member regardless of role") - not new, but
   materially larger in surface area now that seven more destinations
   exist. **Recommended as the next founder decision**: whether
   `external_executive` (and any future restricted role) should be
   role-gated per-destination, and if so, whether that's a shared
   `_authorized_project_by_role`-style backend helper plus a matching
   frontend guard, versus some other model.
2. **`Work.tsx`'s Approve/Return buttons render for every role**,
   relying entirely on the backend's real 403 to stop an unauthorized
   click rather than not offering the action at all - unlike what a
   role-aware UI would do. The backend guarantee itself is intact and
   already proven (Task 13.4); this is a UX-clarity gap (a user sees an
   action they cannot actually perform), not a security one. Also left
   unfixed here: building real per-role UI gating needs a "what is my
   own role on this deal" primitive that does not currently exist on
   the frontend (`api.ts` has no `getDealRole`/equivalent) - adding one
   is implementation work belonging to its own scoped task, not an
   improvised addition inside a verification phase.
