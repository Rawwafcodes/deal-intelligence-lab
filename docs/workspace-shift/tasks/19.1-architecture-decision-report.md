# Task 19.1 — M19 architecture decision report

Status: **for founder approval** (2026-09-27). Written per
`13-post-m17-roadmap.md` § "Required architecture decision report".
**Nothing has been provisioned, deployed, signed up for or paid for**, and
nothing will be until the founder approves a recommendation and its cost
(D20). Prices are list prices found on 2026-09-27 (sources at the end);
estimates are marked as such.

## 1. The short answer

- **Staging and an early non-regulated pilot:** the founder's working
  hypothesis holds up - **Railway** (a web service and a separate worker
  service) + **Neon** Postgres + **Cloudflare R2** for documents + **Clerk**
  for sign-in + **GitHub Actions** + **Sentry** - run in **European
  regions** (the closest these providers get to the Gulf). Render is an
  equally good alternative; the choice between them is close and cheap to
  reverse. Expected infrastructure cost: **≈ $20-45/month** for founder-only
  staging, **≈ $110-190/month** with one pilot customer.
- **The real cost is the AI, not the hosting.** Track B measured
  **$15-24 per full analysis** of a real deal on Claude Opus 5. A pilot
  running ten such analyses a month costs more in AI than all the hosting
  combined.
- **A Saudi residency-sensitive or regulated customer cannot be served
  in-Kingdom today by any architecture**, because Claude itself is not yet
  offered from a Saudi region on any platform. The app and its data can
  move into the Kingdom (AWS from December 2026, Azure from November 2026,
  Google Cloud now); the AI step still leaves the Kingdom. That is a
  customer-by-customer legal question (Saudi PDPL transfer rules), not an
  engineering one - and for government or critical-infrastructure customers
  it is likely a blocker until in-Kingdom Claude exists.
- **Whatever is chosen, four code changes come first** (section 3). They
  are the bulk of M19's engineering and are the same for every provider.

## 2. What the system actually is today

Inspected from the code, not assumed:

- **One Python process.** `server.py` is a standard-library HTTP server
  bound to `127.0.0.1`, which also serves the built React app from
  `static/`. There is no separate frontend server - so a separate
  frontend host (e.g. Vercel) would add a vendor without removing anything.
- **The worker is a thread inside that process.** The durable mandate
  worker (Task 12.2) persists runs in Postgres and survives restarts, but it
  is single-process by design: it has no cross-process locking, because
  there has only ever been one worker.
- **Documents live on local disk** (`~/DealLabData`, 614 MB today). The
  database is small (≈ 50 MB).
- **Sign-in is a development stub** (the identity switcher). Authorization
  itself (`authz.py`, D16) is real and server-side, and stays.
- **Dependencies are few**: `anthropic`, `psycopg2`, `openpyxl`, `xlrd`,
  `python-dotenv` (Python 3.10). Easy to containerise.
- **AI features in use**: document citations, the **Files API** (Excel
  workbooks, and since this week oversized PDF sets) and **server-side
  code execution** (Excel analysis). These matter for the Saudi question
  below.

## 3. Changes needed before any hosting (provider-independent)

1. **Split the worker into its own process** and make job claiming safe
   when more than one process exists (`SELECT … FOR UPDATE SKIP LOCKED`).
   Needed so analyses run independently of the web server and survive
   browser closure *and* a web restart - an M19 exit-gate item.
2. **Move document storage behind an interface** with two backends: local
   disk (unchanged for development) and private object storage (R2 or S3),
   with encryption at rest and short-lived signed download links. Needed
   because separate web and worker services cannot share one disk.
3. **Real sign-in** replacing the dev identity switcher in hosted
   environments, mapped onto the existing users, organizations and deal
   roles - plus the minimal organization and team screens (surfaces
   #23-24) needed for two real users.
4. **Configuration and secrets from the environment only**, one set per
   environment (local, staging, pilot), nothing secret in the repository.

Each is testable locally before any provider is touched.

## 4. The options compared

All four PaaS options fit the code (a Python web process + a Python worker +
Postgres). None has a Gulf region. The differences are smaller than they
look; the table is a summary of the reasoning below it.

| | Railway + Neon (hypothesis) | Railway + Railway Postgres | Render | Fly.io | Vercel + separate API | AWS |
|---|---|---|---|---|---|---|
| Fits the code | Yes | Yes | Yes | Yes | No gain - React is already served by Python | Yes |
| Long-running worker | Separate service | Separate service | Background worker service | Machines | Needs another host anyway | ECS task / container |
| Managed Postgres | Neon: branching, point-in-time restore | Postgres on a volume, same vendor | Managed, same vendor | Managed from $38/mo | n/a | RDS |
| Nearest region to KSA | Amsterdam / Frankfurt | Amsterdam | Frankfurt | Frankfurt | n/a | UAE, Bahrain; **KSA Dec 2026** |
| Operational effort for a solo founder | Low | Lowest | Low | Medium | Medium (two platforms) | High |
| Staging cost (infra) | ≈ $20-45 | ≈ $15-35 | ≈ $25-45 | ≈ $45-60 | ≈ $45+ | ≈ $60-120 (est.) |
| Lock-in | Low (containers, standard Postgres, S3-compatible R2) | Low | Low | Low | Medium | Medium |
| Path to Saudi-regulated | Move later | Move later | Move later | Move later | Move later | **Best**, once the KSA region opens |

**Why the hypothesis over Railway's own Postgres**: Neon gives
point-in-time restore and cheap database branches, which directly serve two
M19 exit-gate items (demonstrate backup restoration; separate environments)
for a few dollars more. Railway's own Postgres is simpler (one vendor) but
leaves backup and restore more to us.

**Render** is the close alternative: web service, background worker and
managed Postgres from one vendor, Frankfurt region, flat plan pricing
($7-25 per service at small sizes; $25/month workspace Pro plan). Choosing
it instead changes little; if the founder prefers one vendor over two, pick
Render.

**Fly.io** works but asks more of the operator (machine management), and
its managed Postgres starts at $38/month - more cost and effort for no gain
at this stage.

**Vercel + a separate Python host** only makes sense if the React app were
server-rendered or needed an edge network. It isn't and doesn't; it would
add a second deployment and cross-origin configuration.

**AWS** is the strongest long-term home for a Saudi-regulated customer
(in-Kingdom region from December 2026, Bedrock for Claude), but it is the
most work to run safely for one person, and its Claude offering lacks the
Files API and code execution this product uses (section 6). Not the right
first step; the right *later* step if a regulated customer is signed.

## 5. Recommendations

### 5.1 Simplest safe private staging

Railway (web service + worker service) in **EU West (Amsterdam)**, Neon
Postgres in **Frankfurt**, R2 bucket with **EU jurisdiction**, Clerk
(free tier: basic organizations and roles included), GitHub Actions for
tests and deploys, Sentry free tier. Access restricted to named users.
**Synthetic data only** - real customer data stays prohibited until a
separate formal approval (M19 exit gate). Anthropic API unchanged.

### 5.2 Early non-regulated pilot

The same stack, promoted: Railway Pro, Neon Launch with point-in-time
restore, Sentry Team, a separate production environment and database
branch, daily backups verified by a restore drill, per-organization budget
limits on AI spend (M19's share of usage controls). Anthropic's
`inference_geo` stays `global` unless a customer asks for US-only (10%
premium). Clerk Pro ($25/month) only if a pilot needs enterprise single
sign-on.

### 5.3 Saudi residency-sensitive or regulated customer

Honest position as of September 2026:

- **App and data in-Kingdom: possible soon.** Google Cloud Dammam is live
  (purchased through CNTXT for KSA-billed customers); Azure Saudi Arabia
  East opens November 2026; AWS's Saudi region December 2026. Hosting the
  application, database and documents there is a well-understood move.
- **AI inference in-Kingdom: not available anywhere today.** Anthropic's
  own API offers only `us` or `global` processing. Bedrock offers Claude in
  the UAE and Bahrain regions only through global routing. Google's
  regional endpoints serve older models only; current models are
  global, US or EU. Whether Claude will be offered from the new Saudi
  regions has not been announced.
- **Feature gap on the cloud channels.** Bedrock and Vertex do not support
  the Files API or server-side code execution - both used here (Excel
  analysis, large PDFs). Moving the AI step onto either means re-engineering
  the Excel path (e.g. reading workbooks in our own code rather than in
  Claude's sandbox).
- **Legal route meanwhile.** Under the Saudi PDPL, sending personal data
  abroad needs safeguards (standard contractual clauses or similar, a
  transfer risk assessment); SDAIA has no published adequacy list. For
  customers under NCA's Cloud Cybersecurity Controls (government, critical
  national infrastructure) or with contractual in-Kingdom requirements,
  assume it is a blocker until in-Kingdom Claude inference exists.

Recommendation: do not build for this now. Record it as a sales
qualification question ("can your documents be processed outside the
Kingdom?") and revisit when AWS/Azure KSA regions open and Claude's
availability there is known.

## 7. Migration and rollback

**Migration, in order**:
1. Section 3's code changes, locally, behind switches that keep today's
   local mode working unchanged (local disk, dev identities, in-process
   worker). Tests for each.
2. Provision staging (only after approval). Deploy from GitHub Actions.
   Load synthetic data only.
3. Prove the M19 exit gate in staging: two users complete the workflow;
   tenant-isolation and document-access tests; a long job survives browser
   closure and a worker restart; a backup restore drill; logs and alerts.
4. Security review (independent or documented).
5. Only then, a separate founder decision to allow real customer data.

**Rollback**: the local application is never removed and keeps working
throughout - staging is additive. The database schema changes are additive
and idempotent (the existing pattern), data can be exported with
`pg_dump`, and documents copied back from object storage with standard S3
tools. Leaving any one provider means redeploying the same container
elsewhere and restoring a database dump.

## 8. Decisions needed from the founder

1. Approve the staging stack (hypothesis as refined here) **or** choose
   Render as the single-vendor alternative.
2. Approve the staging budget: ≈ $20-45/month infrastructure plus an AI
   testing budget (suggest a hard cap, e.g. $100/month).
3. Confirm EU regions (Amsterdam/Frankfurt) for staging and early pilots.
4. Confirm Saudi-regulated customers are out of scope until in-Kingdom
   Claude inference exists.
5. Authorize starting section 3's code changes (no spend; local only).
