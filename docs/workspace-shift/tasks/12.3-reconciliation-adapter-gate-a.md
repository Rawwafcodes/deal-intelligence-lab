Status: complete

registry, pinned manifest and shared findings") plus the roadmap's own
Gate A checkpoint ("prove one existing reconciliation completes through
the generic runtime and shared UI, including persistence, citations,

## User outcome
A mandate can now be commissioned to actually reconcile a selected group
of a deal's real PDFs against its real Excel workbooks — the same
analytical capability the pre-existing static reconciliation page already
offers, now reachable through the mandate composer/detail UI, with a
plan that pins the exact document versions it was approved against, a
durable run that survives the browser closing, and findings that land in
the exact same shared workspace/findings system every other reconciliation
already uses — not a second, mandate-only copy.

## Scope
**1. `mandates.py` gained a second, real capability** -
`reconciliation.cross_format` (`side_effect_class: "external_paid_call"`,
distinct from `fixture.echo`'s `"read_only"` - an honest label, not a
cosmetic one). Its executor (`_reconciliation_executor`) is a thin
adapter, not a second implementation: it calls, in order, the *exact*
three functions `server.py`'s pre-existing `_handle_reconciliation` route
already calls -
`cross_format_analysis.validate_selection`/`run_cross_format_analysis`,
`cross_format_analyses.create_cross_format_analysis`, and
`workspaces.get_or_create_workspace` - so Gate A's "no parallel
mandate-only finding silo" holds structurally: this *is* the same
finding-materialization path the static page already uses, not a copy of
it. A failed outcome still persists the audit record (matching the
existing route's own behavior) before failing the attempt/run/mandate -
the failure is real, but the record of what was attempted is not lost.

**2. A new template, `reconciliation`** (one capability stage,
`examples/reconciliation-template.json`'s own stage vocabulary) -
deliberately just the `reconcile` stage, not the illustrative template's
full `reconcile -> review -> draft -> approve` pipeline: a
`draft_from_reviewed_findings` capability doesn't exist yet (that's a
separate, unauthorized future task), and building a human-checkpoint
stage around one real capability adds nothing 12.1 didn't already prove
generically with the fixture template.

**3. `propose_plan` gained an optional `stage_inputs` parameter** - the
first time a plan actually needs input from outside the mandate's own
objective. `_default_input_for_stage` now recognizes
`reconciliation.cross_format` and requires `stage_inputs["reconcile"]
["document_ids"]` (a non-empty list) to be supplied by the human
proposing the plan - there is no planner yet to derive a source selection
from (12.4 is still out of scope) - and **pins each document's current
`DocumentVersion` id into the stage's own input at propose time**
(docs/03: "pinned sources"). `_reconciliation_executor` **enforces** that
pin at execution time, not just records it: if a document's current
version no longer matches what the plan pinned (someone replaced it after
approval), the attempt fails with a clear, specific error instead of
silently reconciling against unexpected content - real enforcement,
proven by `test_pinned_version_drift_fails_the_attempt_without_calling_the_provider`
(the mocked provider is asserted **never called** in that case).

**4. `server.py`**: `_handle_propose_plan` accepts an optional
`stage_inputs` object in the request body, validated as a dict and passed
through unchanged - no new route, no new authorization surface.

**5. Frontend (`MandateDetail.tsx`)**: when the `reconciliation` template
is selected, the "Propose a plan" card fetches and renders the project's
real documents as two checklists (PDFs / Excel workbooks), requires at
least one of each before enabling "Propose plan", and passes the
selection as `stage_inputs.reconcile.document_ids`. This is Gate A's own
"shared UI" requirement, not an API-only proof: `listDocuments` was added
to `api.ts` (the React scaffold had no document-listing call at all
before this task).
