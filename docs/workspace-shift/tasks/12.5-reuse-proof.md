## User outcome
A human (or the real LLM planner from Task 12.4) can now propose a second,
meaningfully different mandate flow - "Cross-format reconciliation with
human review" - built entirely from two already-registered, already-live-
proven building blocks: the real reconciliation capability and the
generic human-checkpoint mechanism. A mandate using this template is not
marked complete the instant the real, paid reconciliation call succeeds;
it pauses with the real findings already sitting in the shared workspace,
and only completes once a human has actually reviewed them and recorded a
decision. No new capability was registered and no executor code changed -
this is configuration, not implementation, of a second flow.

## Scope
**1. `mandates.py` gained one new template, `reconciliation-with-review`**
- two stages: `reconcile` (`kind: "capability"`, `capability:
"reconciliation.cross_format"` - byte-for-byte the same stage shape the
plain `reconciliation` template already uses) and `review` (`kind:
"human_checkpoint"`, `depends_on: ["reconcile"]` - the exact stage kind
`fixture-echo-with-review` already proved). **No new capability. No new
executor. No change to `_run_stages`, `_default_input_for_stage`,
`validate_plan_stages`, the Worker, the budget ledger, or
`propose_plan_llm`.** Registering the template is the entire backend
change beyond one doc-comment update to the module docstring.

**2. `mandate_planning`/`propose_plan_llm` needed zero code changes** -
verified, not assumed: `propose_plan_llm` builds its `TemplateSummary`
list from `list_templates()` and computes `needs_documents` via
`_document_selection_stage`, both already generic. A dedicated test
(`test_llm_planner_can_select_the_review_template`) proves the planner
can propose this template with no planner-side change.

**3. Frontend generalization, found necessary during implementation**:
`MandateDetail.tsx`'s manual-proposal document checklist was gated on
`selectedTemplate === "reconciliation"` (a single hardcoded template key,
explicitly flagged in Task 12.3's own code comment as a temporary hook
pending exactly this kind of generalization: *"a real multi-capability
composer would generalize it, but with exactly one capability needing
explicit input, that generalization has nothing yet to prove itself
against"*). With a second template now needing the same document
selection, that hardcoded check would have silently hidden the checklist
for `reconciliation-with-review`. Replaced with a capability-driven check
- `CAPABILITIES_NEEDING_DOCUMENT_SELECTION` (mirroring `mandates.py`'s own
`_CAPABILITIES_NEEDING_DOCUMENT_SELECTION` set) tested against whichever
template's stages the human has actually selected - so any future
template built on the same capability, or a future second capability
needing documents, is handled by the same one code path without a repeat
of this exact fix.

## Exclusions

and validate it as its own bounded task before registration") - not
silently assumed done here. **No change to the plain `reconciliation`
template** - both templates remain registered and selectable; a human or
the planner chooses between "no in-mandate review gate" and "requires
one" based on the objective, not a replacement of one by the other. **No
new database table or column** - a template is a code-level registry
entry (docs/04: "in-memory, code-level... like a plugin registry, not
user data"), so this task has no schema footprint at all. **No new
paid-call type** - the run's own execution reuses `reconciliation.
cross_format` verbatim; the one live run this task performed is the same
kind of call 12.3 and 12.4 each already made once, not a new category.
**No deployment, no push, no `git commit`** (the user may choose to
commit this task's changes separately, as with 12.4).

## Reuse
This task is close to entirely configuration, by design - the roadmap's
own point. The capability is 12.3's, unmodified. The `human_checkpoint`
stage kind, the Worker's pause/resume handling, the budget ledger, and
crash recovery are all 12.1/12.2's, unmodified and unre-tested here except
where the *combination* specifically needed proving (see Acceptance). The
LLM planner is 12.4's, unmodified. The only genuinely new lines of
backend code are the ~20-line template registration; the only frontend
change replaces one hardcoded string comparison with a small, reusable,
capability-keyed check.

## Security and intelligence boundary
No new access-control surface: the new template's one capability stage
goes through the exact same `permission_check`/`_authorized_project` gate
`reconciliation.cross_format` already had. No new data reaches the model:
the reconcile stage's input is pinned document versions exactly as
before; the review checkpoint sends nothing to any provider at all (a
`human_checkpoint` stage has no capability, no executor, no network call
of any kind - it only ever waits for a human-typed decision, recorded
locally). The human review this template adds is a genuine gate, not
cosmetic: `_run_stages` returns immediately after recording the
checkpoint's `awaiting_human` attempt, the mandate stays `active` (not
`completed`), and nothing about the already-materialized findings changes
whether or when a human resumes - reviewing findings in the shared
workspace UI and recording a mandate-level review decision are two
independent, both-real actions, not one masquerading as the other.
