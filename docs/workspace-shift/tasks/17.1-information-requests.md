# Task 17.1 — Information Requests in React
Status: complete
Authorization: founder directive, 2026-09-27 (Phase A1 of
`17.0-product-integration-program.md`).
Dependencies: none beyond already-implemented `workspaces.py` request
routes (Milestone 9) and the existing `Findings.tsx` workspace-picker
pattern (2026-09-18 frontend unification).

## User outcome
From the Findings screen for a deal (which already picks a workspace),
a user can see that workspace's information requests, create a new one,
optionally link it to one or more existing findings, see its priority,
assigned recipient and status, record/read a management response and a
reviewer follow-up, and change its status - all without leaving the
React app or typing a legacy URL.

## Required reading
`workspaces.py`'s `WorkspaceRequest` dataclass and
`list_requests`/`get_request`/`create_request`/`update_request`
functions (lines ~270-1260); `server.py`'s
`_WORKSPACE_REQUESTS_COLLECTION_RE`/`_WORKSPACE_REQUEST_ITEM_RE` routes
and their `_handle_create_request`/`_handle_update_request` handlers
(~line 3289); `Findings.tsx`'s existing workspace-picker/bundle-fetch
pattern, which this task extends rather than replaces.

## Scope
1. `frontend/src/lib/api.ts`: add `WorkspaceRequest` interface (mirrors
   `workspaces.py`'s dataclass exactly: `id`, `workspace_id`, `question`,
   `related_finding_ids`, `priority`, `assigned_recipient`, `status`,
   `management_response`, `reviewer_followup`, `created_at`,
   `updated_at`), `REQUEST_PRIORITIES`/`REQUEST_STATUSES` constant
   arrays mirroring the backend's own (`low`/`medium`/`high`;
   `draft`/`sent`/`answered`/`closed`), and `listRequests`,
   `createRequest`, `updateRequest` functions hitting the exact existing
   routes.
2. `Findings.tsx`: add a "Requests" section below the findings list, for
   the same selected workspace - list, create (question + priority +
   assigned recipient + optional related-finding links), inline status
   change, and management-response/reviewer-followup display/edit.
   Related findings are cross-referenced by title against the already-
   fetched `bundle.findings` list (no new fetch).

## Exclusions
- No new backend route, table, or column. `assigned_recipient` is a free
  -text field on the real backend (not a linked user id) - the UI treats
  it as free text too, honestly, rather than inventing a user picker the
  backend doesn't support.
- **No due-date field.** The directive's own A1 description asked for a
  due date; `WorkspaceRequest` has no such field on the real backend.
  Adding one would be new schema, out of this task's bounded scope -
  disclosed here rather than silently dropped or faked in the UI.
- Activity-feed integration is **not** included in this task's own
  scope, despite A1's "see request changes reflected in
  Overview/Activity where existing backend data supports it": by direct
  inspection, `server.py`'s `_project_activity_feed` (the function
  backing both Overview's and Activity's feeds) only merges task
  comments, work-product submissions and review decisions - it does not
  read `workspaces.list_audit_log` at all, for requests or anything
  else. Wiring that in is a small, separable, additive backend change
  (reusing the already-persisted `workspace_audit_log`, which already
  records `request_created`/etc.) and is recorded as follow-on work in
  `17.0`'s tracker rather than bundled into this UI-only commit.
- No change to `workspace.html` (left in place, unlinked, per the
  program's own ground rules).
