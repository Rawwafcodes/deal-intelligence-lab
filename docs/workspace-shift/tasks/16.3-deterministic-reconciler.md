# Task 16.3 — Deterministic reconciler
Status: complete
Authorization: founder said "next" immediately after Task 16.2's
completion summary, which had named 16.3 as the more natural next step
(each of its rules must be "justified by the golden set," directly
consuming Task 16.1's own output). Same M16 override recorded in

Dependencies: Task 16.1 (`golden_set.py`) - this rule's regression fixture
is tied to the golden set's own seeded `numerical_conflict` case. No
dependency on Task 16.2 (`assertion_ledger.py`) - the two are independent
consumers of different upstream data (16.2 promotes M14.2's real review
output; 16.3 operates on caller-supplied structured facts).

## User outcome
Given two already-labeled numeric facts from two different sources that
claim to represent the same real-world quantity, the system can
deterministically (no LLM call) flag a material disagreement between
them, present both facts' full evidence without summarizing, and let a
human dismiss the flag with a recorded reason - or, if the same two
sources are checked again later, get back the same finding rather than a
fresh duplicate or a silently-reopened dismissed one.

## Scope
New module `reconciler.py`, implementing exactly one rule
(`numerical_conflict_same_label_v1`) per the spec's "one rule at a time":
1. `NumericFact` - a frozen dataclass for one already-labeled numeric
   claim (`label`, `value`, `unit`, `source_type`, `source_id`,
   `locator`). Producing one (deciding the label, and that two facts from
   two sources claim the same thing) is explicitly the caller's job, not
   this module's.
2. `RuleDefinition` - a frozen dataclass making the spec's seven required
   per-rule properties inspectable in code, not only prose: `rule_id`,
   `defect_type` (from Task 16.1's `golden_set.DefectType`),
   `description`, `preconditions`, `normalization_assumptions`,
   `tolerance`, `tier`, `evidence_presentation`, `dismissal_policy`. The
   seventh property (regression fixtures) is the test file itself, not a
   data field.
3. `evaluate_numeric_conflict(project_id, fact_a, fact_b, *,
   relative_tolerance=0.005)` - returns `None` if the precondition isn't
   met (different normalized label, or different normalized unit - both
   deliberately out of this rule's scope) or the values agree within
   tolerance; otherwise creates (or, if this exact source pair was
   already evaluated, returns) a persisted `ReconcilerFinding`.
4. `dismiss_finding(finding_id, *, dismissed_by, reason)` - requires a
   non-empty reason; dismissal is permanent (re-evaluating the same pair
   returns the still-dismissed finding, never silently reopened).
   `get_finding`/`list_findings` are the read surface, project-scoped
   with optional `rule_id`/`status` filters.
5. `server.py`: one new import, one new `init_reconciler_db()`
   registration line.

## Exclusions
- **No fact-extraction pipeline.** This task does not parse PDF/Excel
  content into `NumericFact` values - that would require new NLP/
  extraction infrastructure this codebase doesn't have, is exactly the
  ambiguous "which two things correspond" problem this rule is scoped to
  avoid, and is arguably M16.4's benchmarking territory, not 16.3's.
  `NumericFact` instances must be supplied by a caller.
- **No unit or currency conversion**, and no rule for the
  `unit_currency_mismatch` defect type. A precondition mismatch here
  (different normalized units) causes this rule to silently skip the
  pair rather than attempt a conversion - building a correct, general
  unit/currency converter is real, separate, harder work, deferred until
  it has its own justified rule.
- **No second rule.** Only `numerical_conflict_same_label_v1` exists.
  Nine of the ten golden-set defect types (everything except
  numerical_conflict and staleness, the latter already covered by M15 -
  see Baseline) have no reconciler rule yet.
- **No HTTP route, no frontend surface, no wiring into any existing
  workflow** (e.g. `mandates.py`'s capability registry, or the
  M14.2 review pipeline) - nothing in this codebase produces
  `NumericFact` values yet, so there is no real caller to wire this
  into. Same reasoning as Tasks 16.1/16.2's own exclusions.
- **No "reopen" action** for a dismissed finding - the spec's own
  "Override and dismissal reason" line describes one action (dismiss
  with a reason), not a dismiss/reopen pair; adding a symmetric reopen
  was judged out of scope until a real workflow needs it.
- **No stale-finding refresh.** If the same two sources are evaluated
  again with different values, `evaluate_numeric_conflict` returns the
  original finding's original snapshot unchanged, not an updated one -
  disclosed explicitly below, not silently accepted as correct behavior
  for every future use.

## Reuse
Reuses Task 16.1's `golden_set.DefectType` enum directly (this rule's
`defect_type` field, and its own regression test's defect-type
comparison) rather than inventing a parallel vocabulary, and reuses the
"a reason is required for a negative decision" pattern already
established twice in this codebase (`reviews.record_decision`,
`assertion_ledger.dispute_entry`).

## Security and intelligence boundary
No new identity, input, or tool surface, and no LLM/paid call anywhere in
this module - the entire rule is local arithmetic and string
normalization. No route exists, so no server-level authorization check
was needed; `list_findings`/`get_finding` are project-scoped functions
ready for whatever route eventually calls them.

## Acceptance
`tests/test_reconciler.py`, 14 tests across three classes, all passing:
- **Rule arithmetic/preconditions** (`ReconcilerRuleTests`): a genuine
  conflict beyond tolerance is flagged with the correct relative
  difference; a difference within the 0.5% default tolerance is not
  flagged; different normalized labels are never compared; different
  normalized units are never compared (the deliberate unit-mismatch
  exclusion); label/unit normalization ignores case and whitespace;
  unitless facts (both `unit=None`) are still comparable.
- **Persistence** (`ReconcilerPersistenceTests`): a flagged conflict is
  actually persisted and independently fetchable; re-evaluating the same
  source pair (in either argument order) returns the identical finding,
  never a duplicate; dismissal requires a non-empty reason and raises
  `FindingNotFoundError` for an unknown id; a dismissed finding stays
  dismissed on re-evaluation rather than reopening; `list_findings` is
  project-scoped (a second project sees none of the first's findings)
  and filters correctly by `rule_id`/`status`.
- **Golden-set regression fixture** (`ReconcilerGoldenSetRegressionTests`,
  the spec's own required seventh property): confirms exactly one
  `numerical_conflict` golden case exists and that its prose still
  contains the exact figures ($50,000,000 / $52,000,000) this test's
  hand-authored `NumericFact`s mirror - so the fixture and the golden
  case can't silently drift apart - then confirms those facts are
  actually flagged by the rule. A second test makes the "no other defect
  type has structured facts yet" disclosure executable rather than just
  a prose claim.

**Limitations, disclosed rather than glossed over**:
- **No measured false-positive/false-negative rate**, per the spec's own
  explicit instruction not to claim zero without evidence - this task
  makes no such claim. The 0.5% tolerance is a conservative, unvalidated
  starting default; the rule's own boolean logic is exact given correct
  inputs, but whether real upstream fact-labeling would be reliable
  enough to avoid nuisance flags is genuinely unmeasured, since nothing
  yet produces `NumericFact`s from real documents.
- **Only one rule of ten defect types exists.** This does not, on its
  own, demonstrate the reconciler approach generalizes - each further
  rule (per the spec) is its own separately-justified task.
- **No real caller exists yet.** Like Tasks 16.1 and 16.2, this is
  substrate: a real workflow producing `NumericFact`s and consuming
  `ReconcilerFinding`s (most plausibly wired through the assertion ledger
  - two disputed/confirmed ledger entries with the same normalized label
  could feed this rule directly - or a future structured-extraction
  capability) has not been built.
- Re-evaluating an already-evaluated source pair never refreshes the
  finding's snapshot even if the underlying values changed - flagged
  explicitly in Exclusions, not discovered later.
