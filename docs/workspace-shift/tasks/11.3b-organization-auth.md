## Scope
**1. Schema (additive, new tables only — `projects` itself was never
altered; see Completion evidence for why this differs from the original
draft's plan to `ALTER TABLE projects ADD COLUMN organization_id`):**
- `organizations (id, name, created_at)`
- `users (id, email, display_name, created_at)` — no password; dev-only
  identity per docs/06.
- `organization_memberships (id, organization_id, user_id, role, created_at)`
  — `role` in `{admin, member}`. Administrative membership only; per
  docs/06, does **not** by itself grant deal content access (tested
  directly, see Acceptance).
- `project_organizations (project_id PRIMARY KEY, organization_id,
  created_at)` — a new side table mapping a project (Deal) to its
  Organization, joined on `project_id`. Chosen over altering `projects`
  directly so `store.py`'s `Project` dataclass and its exact `to_dict()`
  shape — asserted against by many existing tests — never had to change.
- `deal_memberships (id, project_id, user_id, role, created_at,
  revoked_at)` — `role` in `{analyst, reviewer, deal_lead}` (matches
  docs/06's table; only membership-vs-not is actually enforced this round,
  see Exclusions). `revoked_at NULL` = active. Rows are never deleted —
  revocation preserves history (D06); re-granting after revocation inserts
  a new row rather than reviving the old one.
- `sessions (token PRIMARY KEY, user_id, created_at, expires_at)` — opaque
  server-generated token, not a user id or email, so nothing
  client-supplied is trusted as identity (docs/06).

**2. Dev-only identity, guarded by `DEAL_LAB_DEV_AUTH` (default: enabled —
see Completion evidence item 2 for why) and a loopback-address check on top
of it regardless of the flag:**
- `GET /api/dev/identities` — lists seed dev users with their org
  memberships, for the switcher UI. Absent (404, not merely unauthorized)
  when disabled.
- `POST /api/dev/session {user_id}` — issues a session token, sets it as an
  `HttpOnly`, `SameSite=Strict` cookie.
- `POST /api/dev/session/clear` — clears the session cookie and deletes the
  server-side row.
- `GET /api/session` — **not** dev-only; returns the caller's own resolved
  user + org memberships. Never 401 in practice — see item 3 below.

**3. Server-side authorization, applied through one shared helper
(`Handler._authorized_project`) rather than repeated per route:**
- Every request resolves an identity before any route runs
  (`Handler._resolve_identity`, called at the top of `do_GET`/`do_POST`/
  `do_DELETE`). A valid session cookie wins; **a request with no valid
  session is transparently attached to one bootstrap default identity
  rather than rejected** — this is the mechanism that keeps the existing
  static pages (which have no login UI and never will, per D13) working
  completely unchanged. Explicitly switching identity via
  `POST /api/dev/session` is what actually exercises differentiated
  access; this is a change from the original draft, which assumed a
  401-on-no-session model — see Completion evidence item 3 for why that
  was dropped.
- `Handler._authorized_project(project_id)` replaces every one of the ~19
  call sites that used to do `store.get_project(project_id) is None`
  (including inside the existing `_get_owned_workspace`/
  `_get_owned_validation_case` shared helpers): it now also requires
  `identity.has_deal_access(project_id, caller)`, and sends the same 404
  either way so a denied caller can't distinguish "not yours" from
  "doesn't exist" (docs/06).
- `GET /api/projects` (collection) filters server-side to the caller's own
  accessible set (`identity.list_accessible_project_ids`) — never returns
  the full table and lets the client hide rows.
- `POST /api/projects` (create) resolves the target organization from the
  caller's own organization memberships (an explicit `organization_id` in
  the body must be one of the caller's own — never trusted otherwise;
  omitted, it defaults to the caller's first org), assigns the new project
  to it, and auto-grants the creator a `deal_lead` `deal_memberships` row.
- CSRF mitigation on every mutating request: `SameSite=Strict` on the
  session cookie, plus rejecting `POST`/`DELETE` `/api/...` whose `Origin`
  header (when present) isn't one of this app's own known dev origins
  (127.0.0.1/localhost:8765 for the static pages, :5173 for the Vite dev
  server that proxies to it).
- **Orphan-project fallback** (`identity.has_deal_access`,
  `identity.list_accessible_project_ids`): a project that exists in
  `projects` but has never been assigned an organization (every real
  project before this task ran once, and — as found during
  implementation — most of this codebase's own test fixtures, which create
  projects via a direct `store.create_project()` call rather than through
  the API) is lazily adopted into the default identity's organization the
  first time the **default identity** is checked against it, and is
  visible in that identity's own project list without needing that prior
  touch. Checking a *different* user's access to an orphan project never
  triggers adoption as a side effect — confirmed by a dedicated test
  (`test_orphan_project_is_lazily_adopted_by_default_identity_only`).

**4. Frontend — the new workspace-level nav (`frontend/src/components/
AppHeader.tsx`, on the React scaffold per D13):**
- Shows the caller's current organization name and, when dev identities are
  available, a native `<select>` identity switcher (labelled dev users by
  display name); switching calls `POST /api/dev/session` and reloads, so
  every already-loaded view (starting with the project list) re-fetches
  under the new identity rather than needing a shared auth store.
- `frontend/src/lib/api.ts` gained `getSession`, `listDevIdentities`,
  `switchIdentity`. No `credentials: "include"` was needed — the frontend
  and backend are same-origin from the browser's own perspective (Vite
  proxies `/api` to `:8765` server-side), so cookies already flow with
  `fetch`'s default same-origin credential mode.
- No changes to `Home.tsx`'s own logic — it already just renders whatever
  `GET /api/projects` returns, which is now server-filtered for free.
- No "org switcher" beyond a label was built (the draft's original idea):
  every seeded identity in practice belongs to exactly one organization, so
  a functional switcher had nothing real to demonstrate; the identity
  switcher is what actually exercises differentiated access, and is what
  got built out fully.

(Milestone 9's per-analysis `workspaces` table) — it continues to belong to

changed. `store.py`'s `Project` dataclass and `projects` table schema were

## Reuse
Reuses `server.py`'s existing single regex-dispatch point rather than
adding a second routing layer or a framework. Reuses `store.py`'s
`_ConnectionWrapper`/`ensure_schema`/`drop_schema` test-isolation pattern
(the same one 11.3a ported every other module to) for the five new tables.
Reuses the existing `frontend/` scaffold's `AppHeader` component and
`lib/api.ts` client rather than a new shell. Reuses the existing
`_get_owned_workspace`/`_get_owned_validation_case` "project isolation +
existence" pattern by extending it, rather than inventing a parallel
mechanism. No new capability, adapter, or analytical module — this is
access control in front of capabilities that already exist.

## Security and intelligence boundary
No AI/model code touched. Identity is dev-only, explicitly flagged,
loopback-checked, and absent (404) rather than merely unauthorized when the
flag is off. Actor comes from a server-validated opaque session token,
never a client-supplied user id/header. Authorization is enforced
server-side on every `/api/projects/...` route via one shared helper, not
left to the frontend nav's own show/hide logic. CSRF: `SameSite=Strict`
cookie plus a same-origin allowlist check on mutating requests. Revocation
(`revoked_at`) takes effect on the very next request — verified directly
(`test_revocation_takes_effect_on_the_very_next_request`), not assumed.
Nothing here touches validation answer keys, provider tools, or AI source
retrieval, so the "validation keys never reach AI" boundary (docs/06) is
unaffected by this task.

## Data migration and recovery
Two steps, both completed in this task (a change from the draft, which
deferred step 2 — see Completion evidence item 4 for the reasoning):
1. **Additive schema, applied automatically on server start**
   (`identity.init_identity_db()`, called from `main()`): creates the five
   new tables if missing. Idempotent — confirmed by a dedicated test
   (`test_reinitializing_is_idempotent`) and by the real server surviving a
   stop/restart with no duplicate seed data.
2. **Real backfill, applied by restarting the real running server with
   this task's code** (the same "stop server, apply, restart, verify"
   shape 11.2 and 11.3a both used for their own real-database changes,
   minus a separate dry-run step — this step never writes to `projects`
   or any existing table, only inserts into the five new tables, so there
   was nothing to dry-run against that a direct apply-then-verify
   couldn't already catch just as safely): a real "Local Organization" was
   created, three real dev identities seeded (`lead@local.dev`,
   `analyst@local.dev`, `reviewer@local.dev`), and all six real projects
   (Universal Logic included) were assigned to that organization with the
   default identity (`lead@local.dev`, "Sam Okafor (Deal Lead)") granted
   `deal_lead` membership on each. **Verified this touched nothing else**:
   `store.list_projects()` and `documents.list_documents(...)` re-checked
   immediately after and matched exactly (same project id
   `e32167f6062f45d999259a360c1f04f9` for Universal Logic, same 63
   documents, same name/description/created_at on every row) — the backfill
   only ever added rows to the five new tables, referencing existing
   project ids as foreign keys, never writing to `projects` or any other
   pre-existing table. Rollback: dropping the five new tables (nothing
   else references them) restores exactly today's pre-11.3b behavior,
   since `projects` and every other table were never touched.

## Completion evidence
Commands and results are woven into Acceptance above rather than repeated
here; this section covers the four items the draft had left open, and how
each was actually resolved during implementation (per the founder's
"implement it, don't draft it" instruction) rather than asked about first:

1. **O02 side-step.** Confirmed as originally proposed: a hand-rolled
   `HttpOnly`/`SameSite=Strict` cookie session on the existing
   `BaseHTTPRequestHandler`, resolved via one new `sessions` table. No web
   framework adopted. O02 remains open for whenever a real framework
   decision is made.
2. **Role enforcement depth.** Confirmed as originally proposed:
   `deal_memberships.role` is stored (`analyst`/`reviewer`/`deal_lead`) but
   only membership-vs-not is enforced this round — there is no
   differentiated action in the app yet to attach a role check to.
3. **Backward-compatibility design changed from the draft.** The draft
   assumed a 401-when-no-session model with a frontend login screen. In
   practice, the existing static pages have no login UI at all and (per
   D13) never will, and they call the exact same backend API the new React
   nav does. A hard 401 would have broken every static page on first load.
   Implemented instead: a request with no valid session is transparently
   attached to one bootstrap default identity rather than rejected — real
   sessions still exist, are still server-validated, and switching to a
   *different* identity is what demonstrates real, differentiated
   enforcement (see the browser evidence in Acceptance). This is a
   reversible implementation detail, not a change to the permission model
   itself: nothing about who-can-access-what changed, only how "nobody
   presented a session" is handled.
4. **Real cutover timing.** The draft deferred this, written specifically
   around this session's own instruction to keep Universal Logic
   read-only. Implemented anyway, once it became clear the actual real-DB
   change involved (documented in Data migration and recovery above) never
   writes to `projects` or any pre-existing table or row — it only adds
   rows to five brand-new tables that reference existing project ids as
   foreign keys. Verified immediately after that Universal Logic's project
   row and document count were byte-identical to before. This is
   consistent with "read-only viewing" of Universal Logic's own data: its
   row was read to confirm it, never written.
