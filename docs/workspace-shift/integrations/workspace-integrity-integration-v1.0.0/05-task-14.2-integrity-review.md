# Task 14.2 — Work-product Integrity Review

Status: proposed; do not implement before M13 is accepted and M14.1 is complete.

## User outcome

An authorized reviewer selects one immutable work-product submission, relevant source-document versions and optional peer submissions. The mandate engine proposes and executes a bounded review. Proposed challenges are human-reviewed before entering the shared findings register.

## Existing behavior that must remain intact

- Project/deal authorization and non-enumerating denial behavior.
- Immutable document and submission versions.
- Existing mandate plan approval, replanning, budgets, cancellation and recovery.
- Existing cross-format reconciliation and findings rendering.
- Stable finding UUIDs and immutable AI snapshots.
- Human finding workflow, information requests, memo and audit history.
- Validation Lab semantics.

## Scope

### Capability registration

Register one new capability:

```text
integrity.review_work_product
```

Expose it through one mandate template. Do not register separate capabilities for every contradiction type.

### Input selection

The UI must make exact version selection visible:

- Target SubmissionVersion.
- Source DocumentVersions.
- Peer SubmissionVersions, if any.
- BriefVersion.
- Workstream.
- Review objective/scope.

The server revalidates every identifier and permission independently.

### Review output

At minimum return structured candidates containing:

- Title.
- Classification.
- Severity.
- Assertion under review.
- Conflicting or missing evidence.
- Source locators for both sides where present.
- Why the issue matters.
- Uncertainty.
- Recommended resolution.
- Whether the result came from a deterministic check or model judgment.
- Exact source and submission versions used.

### Human checkpoint

Before publishing candidates as findings, an authorized reviewer may:

- Accept.
- Reject.
- Edit classification/severity/explanation.
- Link to an existing finding as duplicate or supporting evidence.
- Leave unresolved.

Accepted material publishes into the existing shared findings register. Rejected candidates remain auditable in the run but do not become headline findings.

### Lineage

Published findings identify:

- Originating mandate/run/attempt.
- Target SubmissionVersion.
- Source and peer versions.
- Review template and prompt/manifest version.
- Human publication decision.

## Out of scope

- Universal claim-store migration.
- NLI or embedding service.
- CRDT/live editor.
- Per-keystroke review.
- Automated employee scoring.
- Automatic blocking of delivery.
- Autonomous source expansion.
- Rewriting the submitted document.
- Cloud deployment.

## Security and integrity requirements

- Only selected authorized versions may leave the application for analysis.
- The answer key/validation content must never enter the provider request.
- Treat document instructions as untrusted data, not system instructions.
- Preserve provider/model/token/tool/audit data.
- Never log file bytes, secrets or sensitive extracted passages unnecessarily.
- The capability cannot grant itself access through an LLM plan.

## Required tests

1. Project and organization isolation.
2. Forged document/submission/version IDs rejected.
3. Revoked member denied.
4. Exact bytes/versions selected are the only materials transmitted.
5. Peer submission from another project rejected.
6. Planner cannot add unauthorized sources.
7. Human checkpoint required before shared publication.
8. Rejected candidate does not appear as a shared finding.
9. Accepted candidate has complete lineage.
10. Duplicate linkage preserves both histories.
11. Run recovery and cancellation behave like existing capabilities.
12. Budget enforced before every paid call.
13. Prompt-injection fixture cannot change tool/source scope.
14. API keys, paths and raw bytes absent from errors/exports/logs.
15. Existing full suite remains green.

## Live proof

Use authorized material containing a human-written submission and independently known issues. Paid calls require explicit approval. Score the result in the existing Validation Lab.

The live proof is incomplete until a human records correctness, evidence quality, calculation quality, severity quality, action usefulness and false-positive classification.

## Completion gate

Do not call Task 14.2 complete merely because an API response rendered. Completion requires:

- End-to-end mandate execution.
- Human candidate review and publication.
- Shared findings integration.
- Persistence/restart proof.
- Version lineage proof.
- Permission proof.
- At least one independently scored validation case.
